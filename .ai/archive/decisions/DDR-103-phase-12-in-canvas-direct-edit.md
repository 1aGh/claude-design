## Context

The original Phase-12 plan (2026-05-23) targeted the pre-Phase-3.4 HTML dev-server and gated all work behind a v1.0/v1.1 user-feedback **survey** (Task 0: proceed only if ≥30% of active users want direct manipulation). It also made the source-rewrite strategy ("inline style vs new class vs smart-detect") the central undecided question, and a Task 4 that bound multi-peer inspector edits to a Phase-10 structured CRDT.

Three shipped changes made most of that moot: Phase 3.4 (`apps/studio/` TS+Bun rewrite), Phase 3.6 / DDR-019 (TSX canvases + `editAttribute()` — an AST-aware single-attribute source rewriter that already does inline-`style={{}}` merges + `className` swaps, atomic, per-file-locked), Phase 13 (`data-cd-id` stable DOM→source IDs), and Plan C / DDR-097 (the Inspector + Layers + CSS panels, shipped display-only, with an explicit "live CSS knobs land in Phase 12" callout). The substrate is ~85% built; what remains is wiring + one tree UI + a new `editText` engine fn.

## Decision

1. **The user-survey gate (original Task 0) is WAIVED.** Demand is already established empirically: Plan C shipped the panels display-only and named "live CSS writeback (Phase 12)" as a deferred follow-up by hand. We do not run a survey; we build the writeback. No survey artifact is required to proceed.

2. **Write strategy = inline `style={{}}` merge (CSS) + escaped `JSXText` overwrite (text), both via the `canvas-edit.ts` engine.** The "where do we write the change" question the original plan agonized over is already answered by `editAttribute`'s `style.<prop>` path (DDR-019): the knob writes/overwrites a single CSS key inside the element's inline `style={{}}` object, creating the object if absent. This is *consistent with how canvases are actually authored* — they are almost entirely inline literal `style={{}}` already (e.g. `.design/ui/Agency Hero.tsx` uses `color:'#16161c'`, `fontSize:19`, zero `var(--token)`), so the editor's writes look identical to hand-authored code. Writing into a CSS file was rejected: canvases have no per-canvas stylesheet, no Tailwind (zero-dep invariant), and adding one is a new convention + build wiring for no gain. Token-aware knob *values* (a swatch/scale that writes `var(--token)` when the DS defines tokens) ride on the same inline path and keep edits on-system where tokens exist; className/token-level *editing* is deferred. Text editing adds `editText(abs, id, text)`: find the element by `data-cd-id`, overwrite its single `JSXText` child via magic-string, **entity-escape `< > { }`** (the text lands in source `.tsx`, so raw braces/angle-brackets would be a code-injection into the canvas), and **refuse** (throw `CanvasEditError`) on mixed/expression children — leaf-text only. `data-cd-id` is positional but text doesn't change element index, so no id recompute.

3. **Both write endpoints are main-origin-only (`POST /_api/edit-css`, `POST /_api/edit-text`).** They mirror the Phase-22 `/_api/canvas` precedent exactly: registered in `http.ts` routes, **absent** from `CANVAS_SAFE_API` and from `server.ts`'s `startCanvasServer` route allowlist, so the untrusted canvas-iframe origin can never reach a source-write endpoint (DDR-054). The CSS-knob UI lives in the shell (main origin) and calls them directly; the inline text editor reaches them via the existing `dgn:*` bus → shell relay. `test/canvas-origin-gate.test.ts` asserts both are 403 from the canvas origin (alongside the existing `/_api/canvas` assertion).

4. **Phase-10 CRDT integration (original Task 4) is DROPPED.** Phase 10 was superseded + de-referenced (commit `340b2ed`). Edits are single-writer per canvas; `editAttribute`/`editText`'s existing per-file mutex serializes concurrent writes safely. Multi-peer co-editing of inspector ops is not a v1 goal.

5. **Layers drag-to-reorder is SPUN OFF to `phase-12.1`.** The browsable, click-to-select Layers tree (Webflow Navigator style — label resolution via `data-dc-element` → aria → tag, per-type icons, hover-highlight) IS in scope this phase: it's a client-only DOM walk over the existing `dgn:*` bus + `dom-selection.ts` resolver (`select-by-id` calls `selSet.replace`, which already round-trips through `dgn:'select-set'` → `_active.json`). But *reorder* means moving JSX element nodes within their parent's children — node-move AST surgery `editAttribute` (attribute/text-only) doesn't do, plus the positional `data-cd-id` recompute on the next pipeline pass. That's its own risk surface and gets its own plan.

## Consequences

- The inline-style write overrides any class/token styling for that one property via CSS specificity (inline wins). Documented; acceptable for v1 cosmetic tweaks. A future "promote inline → token/className" pass can refactor.
- Elements whose `style` attribute is not an inline `{{…}}` object (e.g. `style={someVar}`), or text nodes with mixed/expression children, are not directly editable — the endpoint returns a structured refusal and the UI reverts the knob/edit with a "use /design:edit" hint. Honest-refusal over corrupt-source-write is the invariant.
- Because the writeback reuses `editAttribute`, the `/design:edit` Step-3a fast path and the in-canvas editor share one source-rewrite implementation — a fix to either benefits both (DDR-019 single-source).
- The whole feature adds **no canvas-origin surface**: the tree + preview bus are postMessage-only; the two new HTTP routes are privileged main-origin. The DDR-054 trust boundary is unchanged.
