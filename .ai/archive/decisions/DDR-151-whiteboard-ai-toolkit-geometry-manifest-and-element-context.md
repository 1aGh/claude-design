## Context

The user wanted a "robust tool" for AI whiteboard use — not just reading which artboard a note sits on, but which UI **element**, and not just creating a sticky at hand-picked coordinates, but pinning one next to a real button and composing whole tidy templates (retro, kanban, social calendar, roadmap, brainstorm, checklist, user-flow) the way FigJam would. Most of the drawing primitives already existed (DDR-100): `create sticky/shape/text/section/arrow`, `connect` (magnetic binds), `--flow` auto-layout. Three gaps stood between that and what was asked for:

1. `read-annotations --canvas-state` tagged an annotation's overlapping *artboard*, but nothing joined it to the DOM element it visually covers.
2. Both verbs need `{id,x,y,w,h}` rects to place/tag anything, but no file on disk actually supplies them: `.meta.json` `layout.artboards[]` is position-only since DDR-027 (size is JSX-authoritative), and `_canvas-state/<slug>.view.json` is camera-only (DDR-115). `--near`/`--canvas-state` were effectively inert without a caller-supplied rect file — and (discovered mid-implementation) `/design:new`'s own ingest path had been pointing at a **dead** legacy `_canvas-state/$SLUG.json` format that no producer populates, so it silently never tagged an artboard in practice either.
3. The verbs were buried in `skill design`'s prose and had no template/composition layer — an agent had to hand-author every op with no guarantee of tidiness.

## Decision

### 1. Geometry source — a `canvas-rects` verb reading a headless/live render, static fallback when no server

Full artboard rects (width/height) and *all* element rects only exist in the live DOM. `maude design canvas-rects <path>` reads a new `window.__maudeCanvasRects()` hook (installed as a module-load side effect in `canvas-lib.tsx`) via a live/headless render: agent-browser primary (mirrors `screenshot.sh`'s own engine-resolution convention exactly, since `playwright` is a **devDependency** here, not guaranteed present on an end-user's production install), a dedicated `playwright` shim as fallback when agent-browser is absent. With no dev server reachable, it degrades to a **static, artboard-only** manifest — mirroring `DesignCanvasInner`'s `initialArtboards()` merge byte-for-byte (JSX `width`/`height` size-authoritative, `.meta.json` position override, including the same legacy-w/h back-compat tolerance) via a regex-over-known-vocabulary reader in the same house style as `read-annotations.mjs`. *Rejected:* a new `/_api/canvas-rects` HTTP endpoint — the server is headless and can't compute rects without a browser, and a new route would needlessly widen the DDR-054 canvas-safe surface. *Rejected:* the client pushing a persisted `rects.json` the way `_active.json` is pushed — adds staleness + write-amplification for no benefit over an on-demand pull.

The client hook itself needed one supporting change: `liveViewport` (canvas-lib.tsx's module-scope RC3 mirror of the current pan/zoom, previously only set after the user's first gesture) is now ALSO seeded on initial mount, so a fresh headless capture — which never gestures — still sees a correct viewport instead of `null`. This is a strict improvement to the existing RC3 contract, not a new mechanism.

### 2. Element anchor identity — reuse the comment system's identity, not a new one

An element in the manifest carries the SAME anchor shape the comment-pin system already uses (`dom-selection.ts`): the pipeline-stamped `data-cd-id` scoped by artboard (`scopedCdSelector`) plus an occurrence `index` (`selectorIndex`) for a repeated component. No new selector-minting logic — the manifest's element-walk is a plain-DOM enumeration (`[data-cd-id]`, filtered to interactive/leaf-with-text nodes, capped at 400 with a `elementsTruncated` flag) that calls the SAME exported pure functions comments already rely on. This makes an annotation's element anchor resolve the same way a comment pin does, and can't drift from it since there is only one implementation.

### 3. `read-annotations --rects` resolves the DEEPEST element via smallest-containing-rect

With no live DOM to walk (this reader is headless, regex-based, DOM-free by design — mirroring `sanitizeAnnotationSvg`'s own discipline), "deepest element under a point" has no direct equivalent. The chosen proxy: the smallest-area element whose world rect contains the annotation's center. A card and the button inside it both qualify; the button's smaller rect wins — the standard technique when only bounding boxes (not a live render tree) are available. When resolved, the element also upgrades the existing W3C-style `target.selector` from a bare `AnnotationIdSelector` to a `CssSelector` naming the element — the artboard-only lane (`--canvas-state`) is preserved byte-for-byte when `--rects` isn't given.

### 4. `annotate --board` is a generic 3-layout engine; named presets are skill fixtures, not code

`--board` accepts `layout: "columns"` (default; `"grid"`/`"lanes"` alias it — one titled section per group, cards stacked inside, an empty `cards: []` still gets a clean evenly-spaced blank section for the team to fill live), `"radial"` (a central topic with cards ringed around it — brainstorm), or `"flow"` (delegates STRAIGHT to the existing `flowToOps` auto-layout, so a user-flow diagram is not a second implementation of the same layered layout). The seven named rituals the user asked for (retro, kanban, social-media calendar, roadmap, brainstorm, checklist, user-flow) are NOT hardcoded verb flags — they're spec fixtures documented in the new `whiteboard` skill that the agent fills with the user's real content and passes through the SAME generic engine. *Rejected, scope-cut:* the plan's original per-card `pin?` field (pinning one card of a grid-laid-out board to a specific element) — reconciling automatic grid placement with a per-card pin target added real complexity for a rare case; a card needing a pin can be authored as a plain `--ops` create using the (already-shipped) op-level `pin` field instead.

### 5. `move`/`set-text`/`set-color` — full DOM-parser fidelity, decided via a mid-execution user check-in

DDR-100 deliberately omitted a general `update` op for LWW honesty. This adds three narrow, id-preserving ops, but HOW to implement them was a genuine fork raised mid-build: a quick approximation (recreate from the flattened `read-annotations` reader's fields only) would silently drop any hand-authored formatting (custom fontSize, bold/dashed, rotation) a human set via the UI — a real correctness risk `annotate.mjs`'s DOM-free design had never had to face before. Given the choice, **the user chose full fidelity over the shortcut**: `annotate.mjs` now imports `svgToStrokes` (the canonical DOM-based parser) and, on first use in a batch, calls `GlobalRegistrator.register()` (`@happy-dom/global-registrator`) to parse the on-disk SVG, then **`GlobalRegistrator.unregister()` immediately after the parse returns** — before control ever reaches the batch's later loopback-gated PUT — so happy-dom's globalThis patch (fetch/Response/Request/URL, not just `DOMParser`) never persists past the one parse. The raw SVG is also run through `sanitizeAnnotationSvg` on READ (previously only gated on write) before it reaches the parser at all — defense-in-depth for the fact this file can be peer-written (DDR-054) or git-committed by anyone. This is only the first time a batch actually contains a move/set-text/set-color op, so the common create/connect/group/delete-only path pays zero cost. The target is parsed with every field intact, patched, and re-serialized through the canonical serializer.

Two real bugs surfaced during verification of this design, both fixed and regression-tested before this DDR was finalized: (a) chaining two ops against the same pre-existing id in one batch (e.g. `move` then `set-text`) silently dropped the first patch, because the resolver read the stale cached pre-batch original instead of an already-queued in-batch patch; (b) a first attempt at avoiding the fetch-monkeypatch concern (below) by patching only `globalThis.DOMParser` on a scoped `happy-dom` `Window` instance, instead of the full `GlobalRegistrator.register()`, silently broke parsing — happy-dom's own internals (e.g. `querySelector`'s error-construction path) reach through `this.window` for more than just `DOMParser`, so a partial patch leaves them broken in a way the outer `catch { return [] }` in `svgToStrokes` swallows into a false "no strokes found." The register/unregister pairing (not a partial patch) is the fix that's actually correct.

**Security review findings from this feature's `/flow:validate` fan-out, and what was fixed:** the security-auditor (defender) and ethical-hacker (attacker) passes both independently found the same two concrete bugs, plus one architectural residual the attacker pass surfaced that this feature widens but did not create:
- **Path traversal in `_canvas-rects-static.mjs`** (both agents) — `--rel` was joined into `designRoot` with no containment check, unlike the sibling lookups in `read-annotations.mjs`/`annotate.mjs` (which flatten via `fileSlug()` — not applicable here since `--rel` must stay a real nested path to locate the actual `.tsx`). Fixed with a `resolve()` + `startsWith(designRootAbs + sep)` containment assert, mirroring `inspect.ts`'s `mtimeFor()` pattern. Regression-tested.
- **`--board`'s `groups[]`/`cards[]` had no size cap before expansion** (both agents) — `MAX_ANNOTATIONS_BYTES` only rejected after full expansion + serialization, so a pathological spec could burn CPU/memory first. Fixed with `BOARD_MAX_GROUPS`/`BOARD_MAX_CARDS_PER_GROUP`/`BOARD_MAX_TOTAL_CARDS`/`BOARD_MAX_FLOW_NODES` caps checked before expansion. Regression-tested (4 cases: too many groups, too many cards in one group, total-across-groups, and the `flow` layout's node cap).
- **`GlobalRegistrator.register()`'s fetch monkey-patch persisting past the parse** (defender's B2, and the concrete half of the attacker's F2) — addressed by the register/unregister pairing described above; a regression test pins the library contract (`fetch` is restored to the exact pre-register reference, not just "a" fetch).
- **Dependency exactness** — `happy-dom` and `@happy-dom/global-registrator` are now pinned to an exact version (`20.10.1`, not `^20.9.0`) given happy-dom's 2025–2026 CVE cadence in this exact "parses untrusted content" category — three disclosed CVEs as of this writing (CVE-2025-61927, CVE-2025-62410, CVE-2026-33943), all patched in the pinned version (the third only reachable with JS evaluation enabled, which `ensureFullStrokes` explicitly disables). The point of the exact pin is to not silently drift onto a future unpatched one; this repo's Dependabot (weekly, patch+minor, auto-merge) is the process that keeps it current going forward.
- **A follow-up re-verification pass surfaced 2 more concrete gaps in the same area, both fixed and regression-tested:** (a) `MAX_ANNOTATIONS_BYTES` (1 MB) was checked only on the merged OUTPUT, never on the file as read from disk — a file already at/near the cap (peer-written per DDR-054, or committed by anyone) would still be read in full and DOM-parsed on every `move`/`set-text`/`set-color`; fixed with a read-time `Buffer.byteLength` check in `main()`, before the content ever reaches `ctx.rawSvg`. (b) The `--board`/`--flow` size caps above covered `groups`/`cards`/`nodes` but not the relationship arrays — `connections[]` (columns/radial) and `edges[]` (flow, both the top-level `--flow` verb and `--board`'s `layout:"flow"`) had no cap at all, and `createConnect` mints a fresh arrow (+ optional label) stroke per entry regardless of how few distinct nodes are involved; fixed with `BOARD_MAX_CONNECTIONS` (400) and `FLOW_MAX_EDGES` (400), the latter enforced once inside the shared `flowToOps()` so neither caller can bypass it (which also closed a **pre-existing**, not-introduced-by-this-feature gap: the top-level `--flow` verb had no node/edge cap at all before this pass, since DDR-100 never added one).
- **Residual, NOT fixed by this feature, carried forward from DDR-085 and now more load-bearing (attacker's F1):** `canvas-rects`/`--rects` surfacing up to 400 elements' real rendered DOM text (ordinary UI copy that syncs to peers by default, DDR-079) meaningfully *widens* — not merely restates — the prompt-injection trifecta residual DDR-085 already flagged as an open follow-up item for annotation/brief text. This is not architecturally closeable from within this feature for the semantic-injection risk specifically (it needs either an outbound-restricted context for untrusted-content ingestion, or a human confirmation gate before any outbound action following such a read — both are session/orchestration-layer decisions, not something `annotate.mjs`/`read-annotations.mjs`/a skill's markdown can enforce on their own) — though the read-time size cap above shows a *bounded-resource-cost* dimension of the same general residual IS code-fixable, and was fixed. Mitigated for the semantic-injection dimension with an explicit, unmissable MUST-NOT rule in `skill whiteboard`'s trust-model section (no outbound-capable action in the same turn as ingesting this content) — a documentation-level control, consciously **not** a code-enforced one. **The user was asked directly and chose to ship with this residual documented**, matching DDR-085's own precedent of shipping with the same class of residual. This is the one open item this DDR does not consider closed.
- Two items scored below the severity floor, noted but not blocking: `canvas-rects.sh`'s `PORT` value (read from `_server.json`) isn't validated as digits-only before URL construction — an exact mirror of `screenshot.sh`'s pre-existing identical pattern, so left consistent with its sibling rather than fixed in isolation; and `_canvas-rects-static.mjs`'s regex-based reader has no adversarial-fixture test pinning non-finite-geometry rejection (the code itself is correct — verified by the defender pass — just untested against a hostile fixture).
- **Open, NOT fixed — production-install packaging gap (flagged by the defender re-verify pass, confirmed independently against a real global npm install of `@1agh/maude@0.40.0` on this machine):** `apps/studio/package.json` is a nested workspace manifest that the npm tarball does not ship (confirmed via `npm pack --dry-run`), and a real global install's `apps/studio/` directory has no `node_modules` at all — every OTHER bin script (`read-annotations.mjs`, etc.) works today because none of them import a real third-party npm package, only local `.ts` source; `ensureFullStrokes()`'s `await import('@happy-dom/global-registrator')` is very likely the *first* runtime third-party-package need in this bin-script family that isn't routed through the `BOOT_VERBS` compiled-binary path (`cli/commands/design.mjs`), and would throw an unhandled module-not-found error on a real end-user install the first time a `move`/`set-text`/`set-color` op runs. See the plan's Task 6 addendum / STATE.md for the disposition decision — this is a functional/reliability gap, not a security one, and needs its own resolution before this feature can be considered release-ready for non-dogfooding users.

### Packaging — a new `whiteboard` skill + a new `/design:board` command

DDR-085 precedent overloads existing verbs (brief-board folded into `/design:new`) rather than adding new ones. This feature adds instead: the bidirectional read-understand-author-verify loop over the FigJam layer is a workflow distinct from component editing (`/design:edit`), and the user explicitly chose the full two-way toolkit over a cheaper packaging-only option when asked. The low-level verbs and the full read/write/template spec live in skill `whiteboard`; `skill design`'s prior ~30-line annotation section shrinks to a 3-line pointer at it.

## Consequences

- **Positive:** `--near`/`--in`/`--canvas-state` go from effectively-inert (no rect producer existed) to genuinely useful; `/design:new`'s brief-board ingest gains a real artboard-tagging path where it previously silently had none (the dead legacy reference is now fixed as a side effect, not a regression it introduced — it was already broken). Element-level context is the literal capability the user asked for ("nad kterým artboardem a elementem").
- **Dependency change:** `happy-dom` + `@happy-dom/global-registrator` moved from `apps/studio` devDependencies to dependencies (annotate.mjs is a production runtime script, unlike the prior test-only usage). Lazy-loaded, so it only affects install size, not the common-path runtime cost. The `pnpm-lock.yaml` regeneration this required incidentally also caught pre-existing, unrelated lockfile drift (root `optionalDependencies` for the `@1agh/maude-<slug>` platform packages, stale since the last version bump) — left in since a lockfile can't be partially staged and the fix is correct.
- **Scope residual:** `move` has no support for arrows/pen (no single position) or anchored text (position derives from its host) — `delete` + `create` remains the fallback for those, matching the pre-existing vocabulary's own escape hatch.
- **Trust model extension:** element context widens what an ingest loop reads (real rendered DOM text/tags), but not the trust boundary — `read-annotations`'s output, including `element.text`/`element.tag`, is untrusted content, never instructions, exactly as note text and the `author` field already were (DDR-085's Phase-22 framing, DDR-054's canvas-untrusted-to-peers designation). No new HTTP route was added anywhere in this feature — `canvas-rects` is a CLI verb only (DDR-062), and the `annotate` egress stays loopback-only by construction (unchanged from DDR-100).
- **No new runtime-state taxonomy entries needed (DDR-115):** verified by reading the actual `isMaudeRuntimeState` regex (not a naive grep) — `/design:board`'s own `_history/<slug>/rects.json` scratch file is already covered by the existing `_(?:history|trash|draw|smoke|canvas-state|state|chat|comments|untrusted)` alternation, present identically in all three lists.
