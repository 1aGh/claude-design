# DDR-186: Web artboards — flex-first contract, breakpoint duplicate (copy not variant), grid track editor on the existing edit-css lane

**Status:** Accepted
**Date:** 2026-07-18
**Tags:** canvas-lib, artboard, web, grid, breakpoints, ux

## Context

`feature-1-artboard-kinds-foundation` (DDR-181) added `kind="web"` to the `ArtboardKind` union and the overlay-registry mount point, but left the kind's actual behavior as a placeholder: no authoring contract, no breakpoint vocabulary, no way to test reflow, and no on-canvas grid editing (the `feature-grid-track-editor.md` stub, split off Stage M of `feature-element-editing-robustness`, was parked pending this plan). `feature-3-web-artboards` is the third of the kind-family plans (after DDR-181 foundation, DDR-182 print) and absorbs that stub as its own T5.

Four questions needed answers before implementation: (1) what does "flow-first" mean operationally for generation + editing, given the codebase already bans `vw`/`vh`/`@media` inside an artboard for isolation reasons; (2) does testing another breakpoint create a new artboard or a linked/synced variant of one; (3) does a CSS-Grid track editor need new server-side write infrastructure, or does the existing single-property `/_api/edit-css` lane already suffice; (4) how does a gutter-drag resolve a `fr`/`%` track's new size when those units have no fixed px meaning until the browser lays the grid out.

## Alternatives considered

**Flow-first enforcement:**
- **A structural lint that rejects absolute positioning inside a `kind="web"` artboard outright** — pros: hard guarantee; cons: overlays (badges, floating CTAs) are legitimate absolute-positioned content in real web pages, and a hard block would just push authors to non-obvious CSS to route around it. Rejected.
- **Advisory-only: `design-system-keeper` Pass A.10 flags unjustified absolute positioning (no preceding JSX comment) as a warning, same severity ladder as Pass A.7's viewport-escape scan** — picked. Matches this codebase's established posture (Pass A.7 already treats a legitimate full-bleed exception as commentable, not blocked) and composes with the existing `/design:new`/`/design:edit` brief-cue + awareness-step layer rather than adding a second enforcement mechanism.

**Breakpoint model:**
- **A new, web-specific preset table with its own numeric ladder** — rejected: `SCREEN_PRESETS` (mobile 390 / tablet 834 / laptop 1280 / desktop 1440) already exists for the "+ Artboard" flow and these ARE standard web breakpoints; a second table with different numbers would just be two sources of truth for the same concept with no benefit (unlike print, which genuinely needed a new mm-based `PAPER_PRESETS` table — physical paper sizes have no px-native representation to reuse).
- **Reuse `SCREEN_PRESETS` verbatim, relabel the picker's option text for `kind="web"` to read as breakpoints ("Mobile — ≤390px breakpoint") instead of exact-box sizes, and commit width-only (not height) since a web artboard hugs** — picked.
- **Desktop-first cascading/linked breakpoints (Framer's model — a mobile variant inherits desktop styles until overridden)** — pros: this is genuinely how professional responsive-design tools work, and the deep-research citation (`framer.com/blog/responsive-breakpoints`) documents it; cons: requires a variant/override data model and sync semantics that don't exist anywhere in this codebase's JSX-is-truth authoring model (DDR-027) — every artboard is a fully independent, self-contained `<DCArtboard>`; retrofitting inheritance would be a foundational change, not a feature. **Rejected for this plan, explicitly** (Design Decision 3) — flagged as a future DDR if real usage demands it.
- **"Duplicate at width…" = a structural COPY, agent (or the clone's own `@container` rules) adapts content afterward** — picked. Consistent with every other duplicate-style affordance in this codebase (`⌘D`/`applyDuplicateElement` is also a plain copy, not a linked instance).

**Duplicate-artboard engine shape:**
- **Extend `applyInsertArtboard`'s template-string-builder to also accept a "clone from source" mode** — rejected: that function builds a deliberately EMPTY artboard from scratch (Stage I4's own contract: "the new artboard must be empty… a clean frame the user fills"); bolting a clone path onto it would violate that contract for its existing callers.
- **Verbatim `source.slice(start, end)` clone with no attribute rewriting, mirroring `applyDuplicateElement`** — rejected as-is: an artboard's `id`/`label`/`width` are real, explicit JSX attributes (unlike `data-cd-id`, which is transpile-stamped and absent from source) — a byte-verbatim clone would collide on `id` immediately.
- **`applyDuplicateArtboard`: verbatim-clone the artboard's full source span, then patch ONLY `id`/`label`/`width` via a small isolated `MagicString` pass over the extracted substring (offsets translated by subtracting the span's own start), splice the patched clone in as the NEXT SIBLING (not appended after the last artboard)** — picked. New id is `${sourceId}-${width}`, de-duplicated against every existing id with a numeric suffix (deterministic + legible, e.g. `landing-390`, rather than a random suffix). Splicing right after the source (not at file-end) means the clone inherits the very next default-grid slot (`synthDefaultGrid`, canvas-lib.tsx, JSX-render-order-indexed) — "positioned beside the source" falls out of the EXISTING default-grid mechanism for free, with no new `patchCanvasMeta` position-writing code needed.

**Grid track editor write path:**
- **A new `/_api/grid-template` (or similar) route with server-side track-list validation** — rejected: `/_api/edit-css`'s generic single-CSS-property writer (`api.ts` `editCss()`) already accepts ANY valid property name against a plain string value (`JSON.stringify`-escaped, 256-char cap) with zero property-specific special-casing — `grid-template-columns: "200px 1fr 100px"` is, to that layer, indistinguishable from any other CSS value. Confirmed via direct code read and a live end-to-end test (`POST /_api/edit-css` with a real `grid-template-columns` value round-tripped to source and re-rendered correctly) — no new server code was needed.
- **A new dedicated undo/write lane for the grid overlay** — rejected: `grid-template-columns`/`grid-template-rows` were simply added to the shell's existing `resizeElement` allowed-prop list (`client/app.jsx`), the SAME lane Stage D (resize) and Stage J (padding/gap) already ride — consistent with how `padding-*`/`gap` were added there for Stage J with "no new write surface."

**Gutter-drag value math (the `fr`/`%`/`auto` problem):**
- **Reimplement the CSS grid-sizing algorithm to compute exact px allocations for `fr` tracks** — rejected: duplicates browser behavior that's already available for free.
- **Read the browser's own RESOLVED track sizes via `getComputedStyle(el).gridTemplateColumns` (which the spec requires browsers to resolve to concrete px, even for `fr`/`auto`/`%` tracks) for GEOMETRY (gutter placement), and re-derive a new AUTHORED value for DRAG math via the ratio `targetResolvedPx / currentResolvedPx` applied to the track's own authored `fr`/`%` value — proportional re-derivation, the same approach a flex-grow-style drag UI uses** — picked. `px`/`em` tracks stay additive (1 world px of drag = 1 authored unit), matching the existing padding/gap drag convention exactly; `auto`/`min-content`/`max-content` tracks are not draggable at all (no numeric value to scrub) and are excluded from the touched set.
- **Shift = symmetric drag semantics** — matched to THIS codebase's own established meaning of "symmetric" (`paddingSideSet`'s Alt: both touched sides become the SAME dragged value, not an inversely-linked splitter) rather than the alternative "gutter-as-resizable-splitter" model some design tools use, for local consistency.

## Decision

We pick: **web artboards are ordinary, independent `<DCArtboard>`s authored flow-first with an advisory (not hard-blocking) drift check; "Duplicate at width…" is a structural copy (never a linked/inherited variant) whose engine clones-then-patches only `id`/`label`/`width` and relies on the EXISTING default-grid placement mechanism for adjacency; the CSS-Grid track editor (Inspector track-list UI + on-canvas gutter drag + cell-placement fields) rides the pre-existing generic `/_api/edit-css` single-property lane with zero new server-side write surface, resolving drag geometry from the browser's own computed track sizes rather than re-deriving CSS grid math.**

- `kind="web"`'s contract (flow-first layout, `fixed` omitted so height hugs, `@container`/`cqw`/`cqh` for in-artboard responsiveness, `vw`/`vh`/`@media` still banned) is documentation + a keeper advisory pass, not new runtime enforcement — the artboard's existing hug-height (`heightFloor`/`ResizeObserver` re-measurement) and container-type:inline-size machinery (both pre-existing, DDR-181/foundation) already do the structural work; this plan's job was making the AUTHORING discipline explicit, not building new rendering machinery.
- The breakpoint-band chip (T2, "≤ Npx") is decorative, always-on chrome (no visibility toggle, unlike print's opt-in bleed/trim/margin overlay) because it's a single small corner label with nothing to visually collide with — the opt-in-toggle precedent exists specifically because print's guides visually cover artboard content.
- `applyDuplicateArtboard` (canvas-edit.ts) and its disk wrapper/API-op/HTTP-route (`/_api/duplicate-artboard`) follow the identical shape every other structural op in this codebase uses: `resolveCanvasAbs` → rate-gate → validate → `activity:suppress` → read `before` → apply → read `after` → best-effort `history.writeSnapshot` → `logUndo` → return `{ok, artboardId, seq}`. Main-origin-only (absent from both the `CANVAS_SAFE_API` allowlist and `startCanvasServer`'s routes map), same DDR-054 trust posture as `/_api/insert-artboard`/`/_api/delete-artboard`.
- The grid gutter-drag overlay (`use-grid-track-handles.tsx`) is gated on computed `display: grid`/`inline-grid` (never on the JSX `kind` — a grid container can exist inside a `digital` artboard too) and coexists with the Stage-D resize-handle overlay on the SAME single-element selection (unlike Stage-J's spacing overlay, which is mutually exclusive with the equal-spacing dots by selection-count, the resize and grid-gutter overlays are BOTH live simultaneously for one selected grid container) — kept non-colliding by z-index tiering (grid gutters at 4, same layer as Stage-J's padding/gap handles, both below Stage-D's frame-edge handles at 5/6) rather than any new hit-test exclusion logic.
- Only tracks AUTHORED inline via `grid-template-columns`/`grid-template-rows` (parseable by `grid-track-handles.ts`'s `parseTrackList` — a plain space-separated list) get on-canvas drag handles; `repeat()`/`minmax()`/a stylesheet-authored grid fall back to the Inspector's raw-text field. This is the same inline-style-only constraint every other curated on-canvas knob in this codebase already has (these tools edit JSX-authored inline styles, never `_components.css` classes).
- On-canvas corner-drag cell-span (the stub's own "manual cell placement… with a corner-drag to span across cells on the canvas" wording) was NOT built — the Inspector's `grid-column`/`grid-row` free-text fields (start/span syntax) cover the same capability without the added 2D hit-testing complexity a resizable span handle would need. Disclosed scope trim, not a silent gap.

## Consequences

**Positive:**
- Zero new server-side write infrastructure for the grid editor — confirmed live (a raw `POST /_api/edit-css` with a `grid-template-columns` value round-tripped correctly to source and re-rendered the grid with new track sizes) before any client UI was even wired, derisking the biggest unknown early.
- "Duplicate at width…"'s adjacency ("beside the source") required no new position-writing code at all — it's an emergent property of splicing the clone next to its source in file order, which the pre-existing render-order-indexed default-grid (`synthDefaultGrid`) already places adjacently.
- The web-kind authoring contract composes with (rather than duplicates) the existing artboard-isolation ban and the existing `design-system-keeper` pass architecture (A.10 slots in alongside A.5–A.9 with the identical severity-ladder conventions).
- 22 new unit tests cover the pure track-parse/serialize/geometry/drag-math module (`grid-track-handles.ts`) independent of any DOM/React harness, plus new integration tests for `applyDuplicateArtboard` (engine) and `/_api/duplicate-artboard` (HTTP round-trip incl. CSRF-rejection + 422-on-unknown-id) and the canvas-origin-gate unreachability assertion.

**Negative / trade-offs:**
- No on-canvas corner-drag cell-span — a user placing a child into a specific grid cell types `grid-column`/`grid-row` values rather than dragging a visual handle. Documented above, not silently missing.
- The gutter-drag's proportional re-derivation for `fr`/`%` tracks is a UI convenience approximation (re-deriving the share ratio from before/after resolved px), not an exact inverse of the CSS grid-sizing algorithm — acceptable for an interactive drag (the value settles to something reasonable and is always further adjustable), flagged here so a future maintainer doesn't mistake an edge-case rounding wobble for a bug.
- `em`-unit track drag is treated as px-equivalent (no font-size-aware conversion) — same simplification this codebase already accepts elsewhere for drag-scrub ergonomics.
- Desktop-first cascading/inherited breakpoints (the Framer model) remain explicitly out of scope — a user who wants that workflow still duplicates + manually adapts each breakpoint today.
- Live verification of the exact on-canvas Cmd+click element-selection + pointer-drag gesture (for the Inspector panel and the grid gutter handles specifically) was not automatable with the available browser-automation tooling in this session (it lacks modifier+mouse-click composition) — verified instead via (a) the pure-math test suite, (b) a live end-to-end write+reflow through the exact same `/_api/edit-css` commit lane the drag overlay uses, and (c) the context-menu-driven "Duplicate at width…" flow (which doesn't require element selection) end-to-end live, including the resulting file diff and on-canvas render. The underlying drag mechanics (pointerdown/rAF/postMessage-commit) are structurally identical to Stage D/J's already-shipped, already-dogfooded overlays.

## Revisit when

- Real usage demands desktop-first cascading breakpoints — needs its own DDR (a variant/inheritance data model is a foundational change, not a feature, per the alternatives section above).
- On-canvas corner-drag cell-span is requested — extend `use-grid-track-handles.tsx` with a second handle class (cell corner, not gutter) rather than forking the module; the pure-geometry split (`grid-track-handles.ts`) already isolates the math a corner-drag would need (per-track resolved sizes → cell bounding box).
- `repeat()`/`minmax()` on-canvas drag support is requested — `parseTrackList`'s current "bail to `[]` on anything unparseable" behavior is deliberately conservative; extending it needs a real track-function parser, not a regex tweak.
- The live Cmd+click + pointer-drag gesture needs automated regression coverage — route through the `desktop-e2e` (WebdriverIO) harness (real OS-level input, not CDP synthetic events) rather than `agent-browser`, which this session confirmed lacks modifier+mouse-click composition.
