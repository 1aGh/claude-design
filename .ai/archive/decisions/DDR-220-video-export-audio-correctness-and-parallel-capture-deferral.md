# DDR-220: Video export — audio correctness at the source, parallel capture deliberately deferred

- **Date:** 2026-08-12
- **Status:** Accepted (implemented — commits `3becccd9`, `354ec5c4`, `6b1b7a63`; plan `.ai/plans/feature-fast-video-export.md`)
- **Tags:** studio, exporters, video, remotion, web-renderer, audio, correctness, degraded, parallelism, gpu, determinism
- **Related:** [DDR-148](./DDR-148-video-comp-remotion-authoring-capture-export.md) (the video-comp capture spine + the renderMediaOnWeb audio addendum this extends), [DDR-157](./DDR-157-video-export-renderer-overflow-fallback-and-render-sized-timeout.md) (the overflow-fallback + render-sized timeout this generalizes the degradation contract for). RCA (gitignored): `.ai/logs/rca/issue-mp4-audio-export-html5audio-silent-degrade.md`; addendum on `.ai/logs/rca/issue-video-mp4-rendermediaonweb-stack-overflow.md` disambiguates the two failure classes.

## Context

`.ai/plans/feature-fast-video-export.md` opened against a real report: a 9:16 comp's MP4 export took ~15 min and shipped silently muted. Rev 1 of the plan attributed this to DDR-157's `RangeError` overflow class and proposed a bigger V8 stack. Both premises were wrong — see the RCA and its addendum. The real cause was `remotion`'s `<Audio>` **being** `<Html5Audio>`, which `renderMediaOnWeb` rejects with a typed, decidable error; the export degrading to the frame-step fallback (video-only) explains both the ~40× slowdown and the silence, but the *trigger* was a one-line import mistake, not deep DOM nesting.

A divergent bookend debate (BUILDER/SHIPPER/BREAKER) ran before the RCA settled the attribution, converging on: instrument first, bump `@remotion/*` + disable page responsiveness before any capture work, fix correctness defects before parallelism, parallelize (if at all) at the encoded-segment boundary, keep both capture paths, treat JPEG as a knob not a contract. BREAKER held a dissent (confidence 8): parallel capture stays unsafe until a stated, linted frame-purity contract exists for agent-generated comps — Maude has no `delayRender()`/`continueRender()` equivalent the way Remotion's own CLI does. This DDR records what actually shipped and which parts of the debate's converged plan were deliberately left undone, and why.

## Decision

### 1. Audio renders in the SAME `renderMediaOnWeb` pass as video — not a separate pass

The plan's own Task 3 (written before the RCA landed) proposed muxing a *separate* audio-only `renderMediaOnWeb` render into the frame-step output, so a renderer failure wouldn't cost the audio track. That turned out unnecessary: `exporters/video-render-lib.ts` already renders video+audio in one `renderMediaOnWeb` call (DDR-148's own addendum, commit `c0e58f2d`, predates this plan), and once the *actual* root cause (the Html5Audio rejection) is caught before that call ever runs (Decision 2 below), the renderer path succeeds with audio intact for every comp that isn't hitting DDR-157's genuine overflow class. Building a second render pass to protect against a bug that no longer reaches the renderer would have been solving a problem correctness fixed elsewhere — deliberately not built.

### 2. Correctness backstop is pre-flight refusal + a post-export artifact assertion, not a runtime handshake

`exporters/unsupported-media.ts` (`scanUnsupportedMedia`, walking one barrel-re-export hop) statically scans the target canvas for `Audio`/`OffthreadVideo` imported from `'remotion'` **before Chromium launches** — `exporters/video.ts` refuses the export outright for `<Audio>` (a vanished music bed is worse than a refused export) and pre-stamps `degraded` for `OffthreadVideo` (often legitimately silent b-roll). `exporters/degraded.ts` gives `ExportResult`/`ExportJob`/`_export-history.json` a first-class `degraded` field instead of a `console.error`-only signal — `client/export-center.jsx`'s `DegradedNote` renders it as a panel row and completion toast, so `status: 'done'` and "clean" are no longer indistinguishable. `hasAudioStream()` is the last-word backstop: even when every upstream signal says fine, a produced container with no audio stream when audio was requested is marked degraded from the bytes themselves — catching audio-loss classes not yet met (this generalizes DDR-157's "signal the degradation to the UI" follow-up beyond its own overflow trigger).

`video-comp.tsx`'s seek bridge also lost its silent-failure mode independently of the above: a seek that never lands is now a bounded retry (`SEEK_ATTEMPTS`), counted (`__maude_seek_failures__`), and — under the capture shim's `strict` mode — a thrown, export-killing error instead of a resolved no-op. This closes the "a later seek settles it" hazard the plan's "premise Rev 1 inherited without checking" section identified: serially benign, but every worker's first seek on a cold page under any future parallel capture.

### 3. GPU acceleration ships opt-in and OFF by default — a measured, not assumed, answer

Task 8's spike measured `chrome-headless-shell` (what Maude ships) against `--enable-gpu`, full Chromium, and system Chrome, differentially probing `hardwareAcceleration: 'prefer-hardware'` support and PNG/JPEG `captureScreenshot` cost. Finding: `chrome-headless-shell` is the *one* configuration that cannot reach a hardware encoder (forces ANGLE/SwiftShader; Chromium reports `ACCELERATED_VIDEO_ENCODE` disabled); `--enable-gpu` flips it, but the same page then rasterizes to a materially different PNG (84 KB vs 187 KB — a visual change to every export) for a stage that isn't the bottleneck anyway (~50 ms of a ~1050 ms frame). Shipped as `MAUDE_CAPTURE_GPU=1`, deliberately off by default — a design tool changing how it renders is not something to smuggle in behind a perf flag. `hardwareAcceleration: 'prefer-hardware'` itself is never set as a config default (WebCodecs §7.9: an ignorable hint, can render a config unsupported); `--enable-features=AcceleratedVideoEncoder` is confirmed Linux-only and not added.

### 4. JPEG frame-step intermediate ships as an opt-in knob, default PNG, no default flip

`options.frameFormat === 'jpeg'` threads `--frame-format jpeg` through to `_video-playwright.mjs`'s `frameStepCapture`, which takes a `type: 'jpeg', quality: 90` screenshot instead of PNG and passes the format through to `video-encode-lib.ts`'s `addVideoFrame(b64, format)`. Scoped to plain video only — a `--dump-frames` debug dump always stays lossless PNG (it's for human inspection), and GIF never gets a lossy intermediate stacked under its own palette quantization. The default does **not** flip: Task 9's own settling measurement (ΔE2000 on a high-contrast-edge mask, post-H.264, only shipping the default flip if max ΔE2000 < 2.0 **and** Task 1's telemetry shows transport owning > 30% of per-frame cost) has not been run. The knob exists so that measurement can happen without a code change once telemetry from real exports accumulates.

### 5. Parallel capture is architecturally viable but deliberately NOT built — BREAKER's dissent stands

Task 7's falsification spike (two 30-frame MP4 segments, keyframe-forced, demuxed via `EncodedPacketSink`, remuxed through `EncodedVideoPacketSource`) confirmed a re-encode-free join is possible in mediabunny (`encodersConstructedDuringJoin: 0`). That answers "is this worth building" — yes — but does not answer the gates the debate's converged position required before shipping it: codec negotiated once in the parent (not per-worker, since six workers under six different memory pressures can resolve six different codecs today), clip-equality assertion, a **stated and linted frame-purity contract** for agent-generated comps (Maude has no `delayRender()`/`continueRender()` equivalent the way Remotion's own CLI does — BREAKER's held dissent, confidence 8, versus BUILDER/SHIPPER's confidence 6 for shipping behind correctness fixes alone), a memory-derived worker count (Remotion's `min(8, cpus/2)` comes from a dedicated CLI process at composition resolution, not a `deviceScaleFactor: 2` page inside a desktop app also hosting a dev server, an ACP session, and the canvas browser), and a recorded under-load determinism run. None of those gates are built. This DDR records the decision explicitly so a future session doesn't re-run the falsification spike from scratch: the join mechanism works, the surrounding safety contract does not exist yet, and building the contract is a separate feature's worth of work.

The `pageResponsiveness: 'disabled'` win (Remotion's documented setting for a headless, UI-less capture page — the default `'medium'` yields the event loop every ~33 ms for a courtesy no one benefits from) and the `@remotion/*` bump from `4.0.486` to `4.0.507` (PR #9101's native nested-HTML-in-canvas detection on Chromium 152+, 4.0.499's opacity-leak fix) both shipped ahead of and independent of the parallel-capture question — they help the renderer path regardless of whether segment parallelism ever lands.

## Consequences

- **Positive:** the reported failure class (silent mute + 40× slowdown from a wrong import) cannot recur — it's refused at pre-flight with the one-line fix stated in the error. A genuinely different degradation (DDR-157's overflow, or anything else) is still caught, still exports a real file, and is now always visibly `degraded` in the job record, the history ledger, and the UI — never just a stderr line in a desktop app nobody is tailing. GPU and JPEG decisions are backed by measurement, not guesses, and are recorded even where the measured answer was "no" (no hardware encoder reachable on the shipped engine).
- **Negative / accepted:** an export that hits DDR-157's overflow class still loses audio — this DDR did not build the "separate audio pass" that would have preserved it, because the far more common trigger (Html5Audio) no longer reaches that path at all, and building speculative resilience for an overflow class the plan's own research calls "on the order of hundreds of nested precompositing boundaries — not a typical hand-authored scene" was judged not worth it against the frame-purity-contract work still owed for parallelism.
- **Deferred, not abandoned:** parallel capture (Task 7/5) and the frame-purity lint it depends on remain open — this DDR is the record of *why* they're not in this slice, so a future session picking it up starts from the falsification spike's result instead of re-deriving it.

## Alternatives considered

- **Ship the separate audio-render-pass architecture anyway** (plan's original Task 3) — rejected once the actual root cause was known: it would have added a second `renderMediaOnWeb` invocation, a mux step, and new failure surface to protect against a bug that pre-flight refusal already prevents from reaching the renderer.
- **Default to JPEG frame-step screenshots now, on the theory that transport is obviously the bottleneck** — rejected; Rev 1's own cost table assertion that this was "below the noise floor" was never measured, and the plan explicitly gates the default flip on a ΔE2000 + telemetry measurement that hasn't run yet.
- **Build parallel capture behind only the correctness fixes (BUILDER/SHIPPER's post-revision position, confidence 6)** — rejected in favor of BREAKER's higher-confidence dissent: the failure a missing frame-purity contract enables is invisible and load-dependent, exactly the shape that survives testing on an idle machine and reappears in production.
- **Raise `--stack-size` in `_pw-launch.mjs`** (Rev 1's original headline fix) — rejected per DDR-157's own file: the frame-step fallback reuses the same page the renderer just failed in, and a stack that overruns the OS thread guard page turns a catchable `RangeError` into a renderer-process crash, regressing muted-file to no-file.
