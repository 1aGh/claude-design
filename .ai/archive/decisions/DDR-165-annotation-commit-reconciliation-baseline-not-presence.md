# DDR-165: Annotation-state concurrency fixes — chain-owned accumulator + baseline-aware reconciliation, never presence-only

**Status:** Accepted — 2026-07-11 (implemented via `/flow:execute` + two live-bug follow-ups, plan `.ai/plans/feature-bulk-media-insert.md`).
**Extends:** [DDR-088](DDR-088-canvas-media-vocabulary-and-asset-write-surface.md) (the `assets/<sha8>` store every `image`/`mediaref` stroke's href/src resolves into), [DDR-054](DDR-054-linked-mode-trust-model-and-task-4-hardening.md) (the collab-echo path this touches crosses the untrusted-canvas-iframe boundary — read-only, never a write source).

## Context

Maude Studio's canvas annotation layer (`annotations-layer.tsx`) keeps a `strokes` array in React state, mirrors it into `strokesRef` on render, and persists the whole array as one SVG per PUT (`/_api/annotations` replaces, never patches). Every mutation — draw, delete, move, or an async media-intake completion (image decode, video/audio upload) — reads a "before" snapshot, computes an "after," and commits.

Dropping several files from Finder at once fires N independent async completions (`Image.onload`, `uploadAsset().then(...)`), each racing to read `strokesRef.current` and commit. The user reported this live as "1 shown, sometimes 2, sometimes N" — non-deterministic data loss. The plan's original fix (Task 2) added a Promise-chained accumulator (`media-commit-chain.ts`, mirroring `client/app.jsx`'s `structuralWrite`/`editApplyChainRef`) so concurrent completions serialize against each other instead of racing on a shared ref. **This was necessary but, twice over, not sufficient** — live dogfooding against the real desktop app surfaced two further bugs in the same reconciliation territory, both with the same shape: a helper judged "is this id accounted for?" by checking **presence** in some other array, when the correct question was "is this id's *value* current, and did *this specific operation* mean to remove it?"

## Decision — every reconciliation step compares against a baseline, never against bare presence

### 1. The chain's own memory beats a live-but-stale snapshot (`media-commit-chain.ts` `reconcile()`)

The chain's idle-reset originally trusted a fresh `getSnapshot()` (`strokesRef.current`) the moment its queue drained, folding in only ids `remembered` had that `fresh` was fully missing. But `fresh` can contain the **same id** as `remembered`, with a **stale value** — e.g. an image stroke's optimistic `blob:` href, freshly re-rendered, sitting one render tick behind the chain's own later commit that already swapped it to the real `assets/<sha8>` path. "Id present → trust fresh" silently reverted the swap, and the reverted `blob:` href then got filtered out entirely one layer up by the persistence-layer's ephemeral-href guard (§3) — reproducing the exact "file vanishes" symptom the original fix was supposed to have closed. Live-tested before/after: a single 3-file drop lost one file 5/8 runs; after preferring `remembered`'s value for every id the chain itself owns (folding in from `fresh` only ids the chain has never touched), 10/10 clean, plus two 45-file stress runs at 0/45 loss (previously ~5 lost every run).

### 2. Local-mutation reconciliation needs the mutation's own baseline, not just its result (`reconcileCommit`)

A second, independent bug hit the exact same class: after (1) shipped, `putStrokes` guarded every `setStrokesState(next)` with a helper that folded any id `prev` (React's live-rendered state) had but `next` (this commit's result) didn't — reasoning "not caught up yet, keep it." That reasoning is exactly backwards for a delete: an id in `prev` but not in `next` is **precisely** what every deletion looks like. Backspace correctly PUT the smaller, deleted set to the server, then immediately un-deleted it locally — invisible until a reload picked up the server's already-correct copy. The fix threads the mutation's own baseline (`opBefore` — literally the `before` this specific command's `after` was computed from, plumbed through `StrokesPutFn`'s new optional second argument from `createAnnotationStrokesCommand`'s `do()`/`undo()`) so the helper can ask the right question: an id in `opBefore` but not `next` was deliberately removed by **this** mutation and must stay removed regardless of what `prev` shows; an id in `prev` but absent from **both** `opBefore` and `next` is a genuinely concurrent addition from a different in-flight commit and gets folded in. Presence-only comparison cannot make this distinction — it needs the third array.

### 3. Foreign echoes get the analogous fix, scoped to what a broadcast could never know (`reconcileForeignEcho`)

The collab-echo path (`Y.Map.observe`) had the identical ambiguity one layer over: an id missing from a peer's broadcast could mean "peer deleted it" (respect it) or "peer's snapshot predates our own not-yet-synced local addition" (revive it). There's no shared `opBefore` across peers to disambiguate with, so the fix narrows differently: only fold back a locally-missing-from-incoming stroke when it is **still ephemeral** (`isEphemeralHref` — an unswapped `blob:`/`data:` href, i.e. provably not yet PUT anywhere a peer could have seen it). Anything else absent from a foreign broadcast is treated as a real, respected deletion — by us or by them.

### 4. Self-echo suppression needs history, not just the latest write (`recentSelfSvgsRef`)

A related fix in the same pass: the collab-echo guard originally remembered only the single most recent SVG string it authored, to recognize (and ignore) the round-trip of its own writes. Under a rapid batch of commits, an *earlier* commit's server-broadcast echo can arrive after a *later* commit already moved that single pointer forward — the earlier echo no longer matches, gets misread as foreign, and rolls state back. Fixed with a bounded history (`Set`, cap 64) checked via `.has()`.

### 5. The batched single-commit annotation-insert path (Part B, `createMediaFromAssetPaths`) needs none of this

Bulk-inserting N already-resolved asset paths (Task 11) probes every dimension via one `Promise.all` and calls `commitStrokes` exactly once — correct by construction, since there is no per-item async gap for a race to live in. This is the control case proving the chain/reconciliation machinery above is earning its complexity: it exists only for the genuinely async, per-item-completion paths (image decode, upload), not for anything that can resolve everything up front.

### 6. The same ambiguity had a THIRD, unfixed site: delete-during-upload resurrection (`resolveImageUploadSwap`)

An adversarial review of the shipped fix (`/flow:done`'s code-review gate) found that `createImageFromFile`'s post-upload swap — the "fold the optimistic stroke back in if `before` doesn't have it yet, because that's just render lag" logic from §1/§2 — had exactly the same ambiguity as §2, unaddressed: if the user drops an image, then hits Backspace on it *before the upload resolves*, the id is legitimately gone, not lagging, and the old code re-inserted it anyway once the upload landed — syncing the resurrection to every collab peer. Presence-only reasoning can't tell "not rendered yet" from "deleted seconds ago" any better here than it could in §2; fixed the same way, with an explicit baseline instead of an inference: `deleteStrokes` now records every id it removes into a bounded `deletedStrokeIdsRef` (cap 128, mirroring `recentSelfSvgsRef`'s shape), and the swap (extracted as the pure, unit-tested `resolveImageUploadSwap`) checks and consumes that marker *before* falling back to the render-lag assumption. `createMediaReference` (video/audio) has no equivalent bug — it never creates an optimistic entry pre-upload, so there's no id for a delete to race against.

## Consequences

- **The generalizable lesson:** any time a reconciliation step asks "does the other array have this id," check whether "no" can mean *deletion* as validly as *not-yet-arrived* — if both are possible, presence alone is insufficient and the step needs a baseline (a `before`, an ownership marker like `isEphemeralHref`, an explicit deleted-ids marker) to tell them apart. **This bit three times in one feature** — twice caught by live dogfooding (§1, §2), once caught only by a deliberate adversarial code-review pass (§6) — worth grepping for the same shape (`prev.filter(x => !otherSet.has(x.id))`-style folding, or "assume absence means lag") elsewhere in the codebase if a similar resurrect-on-delete bug surfaces, and worth running that adversarial pass *before* shipping, not just live-testing the happy path.
- **`StrokesPutFn`'s `before` param is required**, not optional — the only production caller (`createAnnotationStrokesCommand`) always supplies both directions, and an earlier draft's optional-with-silent-fallback version was flagged by review as dead-but-risky (a future caller could skip it and silently lose the delete-vs-stale disambiguation); made required so a missing baseline is a type error, not a silent regression.
- **Known accepted residual (not this DDR's problem to solve):** neither `reconcileCommit` nor `reconcileForeignEcho` is a true CRDT/OT merge — two peers concurrently editing the *same* stroke (one deletes, the other edits, both before seeing the other's write) can still produce a result neither intended. This is a pre-existing property of the "replace the whole SVG" persistence model (not introduced by this fix) and is out of scope; a real merge would need per-stroke operational transform, which nothing in this codebase does today.

## Security fan-out (`/flow:done` closing gate, 2026-07-13)

A defender (`security-auditor`) + adversarial (`ethical-hacker`) pass ran over all three commits before closing this out.

- **Defender pass: clean.** No findings above Info — confirmed the untouched server-side `sanitizeAnnotationSvg`/asset-write gates still cover every new/changed path, the new Tauri `pick_media_files` command has no capability beyond the existing single-file `pick_media_file`, and multi-file upload reuses the existing per-file validation unchanged.
- **F1 (Medium-High → FIXED).** The delete-during-upload resurrection bug, §6 above. Fixed and unit-tested (`resolveImageUploadSwap` in `test/annotations-layer.test.ts`).
- **F2 (Medium — tracked, accepted).** `recentSelfSvgsRef`'s self-echo suppression compares exact SVG string content. Because the collab model is a single shared last-writer-wins value (not per-stroke CRDT), a *foreign* write that happens to converge to byte-identical content to something in the local peer's own recent-write history (most plausibly: an undo/redo genuinely returning to a prior shared state) would be misread as a self-echo and skipped. The desync window is self-healing — the next real edit from anyone produces fresh content and resyncs normally — so this is a narrow, bounded correctness gap, not a lasting exploit; a proper fix would need a monotonic per-write id threaded through the broadcast (server + `ws.ts` + `Y.Map` schema change) rather than content-equality, which is out of scope for this bugfix pass. Tracked here for whoever next touches the collab-echo protocol.
- **F3 (Low — tracked, accepted).** Multi-file upload (`doUploadMany`) has no aggregate batch byte cap beyond the existing per-file cap — self-DoS risk only on a single-user local dev server, not remote-attacker-reachable. Same category as DDR-164's F4 (cost ceiling); a follow-up, not a blocker.
- **F4/F5 (confirmed not exploitable).** `reconcileForeignEcho`'s ephemeral-href fold-back only ever resurrects from *local* state (never attacker-controlled `incoming`), and `pick_media_files` carries no capability beyond the pre-existing `pick_media_file`.
