# DDR-132: Fast repo open/switch — per-user SWR disk cache for GitHub identity + TTL/dedupe for the remote ahead/behind probe

- **Date:** 2026-06-29
- **Status:** Accepted (implemented — `.ai/plans/feature-git-perf-identity-and-remote-cache.md`)
- **Tags:** dev-server, github, identity, git, performance, cache, swr, token, security, native-only, sidecar
- **Related:** [DDR-108](./DDR-108-github-token-loopback-bridge.md) (NEVER-cache-the-token invariant — the keychain is the single source of truth), [DDR-109](./DDR-109-native-shell-security-model.md) + [DDR-054](./DDR-054-linked-mode-trust-model-and-task-4-hardening.md) (token stays main-origin + loopback only; this cache must not widen its reach), [DDR-045](./DDR-045-real-disk-path-resolution-for-compiled-dev-server.md) (disk paths via real-disk resolution, never `__dirname` inside the compiled binary), [DDR-119](./DDR-119-native-owns-the-workspace-web-is-a-repo-bound-companion.md) (native owns the workspace; the web read-only badge path is untouched), [DDR-131](./DDR-131-remote-draft-checkout-and-refresh-model.md) (the ssh→system ahead/behind routing this cache wraps). Code: `apps/studio/github/identity-cache.ts` (new), `apps/studio/github/endpoints.ts` (`identity()` SWR), `apps/studio/git/service.ts` (`remoteAheadBehind` TTL+dedupe, `invalidateRemoteProbe`).

## Context

Opening, restarting, or **switching** repos in the native studio felt slow because each did a fresh network round-trip to GitHub ("Checking GitHub…") plus a network `git fetch` for the ahead/behind nudge. The root cause is the sidecar lifecycle: a repo switch **respawns the dev-server sidecar** with a new `--root` (`apps/desktop/src-tauri/src/sidecar.rs` `switch_project` kills + respawns; the webview re-navigates). The server is therefore a **fresh process per repo**, so any in-memory cache is lost on every switch.

On that fresh boot two things hit the network on the hot path:

1. **Identity** — `IdentityBar` mounts → `GET /_api/github/identity` → `getIdentity(token)` → `GET api.github.com/user`, with **no cache**. "Checking GitHub…" on every open/switch/restart, despite login/name/avatar essentially never changing.
2. **Remote ahead/behind** — `app.jsx` `refreshRemoteSync` → `GET /_api/git/status?remote=1` → `remoteAheadBehind` → a network fetch. Fires on repo-known, every Changes-panel open, and a 60 s tick, re-running on effect churn with no dedupe or TTL.

The loopback **token bridge** (`github/token.ts`) was investigated and deliberately left uncached — DDR-108's invariant ("NEVER cache the token; the keychain is the single source of truth") stands; the bridge is local + instant and is not a real cost center.

## Decision

1. **Identity SWR disk cache, per-user, keyed by a token-hash (`github/identity-cache.ts`).** Cache `{ login, name, avatar_url }` to a single per-user file — `$XDG_CACHE_HOME/maude/github-identity.json` else `~/.maude/github-identity.json` — as `{ key, identity, at }`. The `key` is `sha256(token)` truncated to the first **16 hex chars**, derived in-memory per request; the **token itself is never written**. `identity()` serves the cached record **immediately** on a key match and fires a fire-and-forget background revalidation that rewrites the file; a cache miss (first-ever, or a different account/token ⇒ different key ⇒ miss) does one fresh fetch + write. Because identity is per-user **public** profile data (not secret), a shared per-user cache is correct and sidesteps the `.design/` runtime-state gitignore machinery entirely. File is 0600, dir 0700; the disk path uses `os.homedir()`/`$XDG_CACHE_HOME` (never `__dirname` — DDR-045). A 401 surfacing **during revalidation** drops the entry (`clearCached`) so the next call re-fetches/re-prompts.

2. **Remote-probe TTL cache + in-flight dedupe, in-memory (`git/service.ts`).** Memoize `remoteAheadBehind` keyed by `` `${dir}\0${remote}\0${branch}` `` with a **45 s TTL**, and coalesce concurrent callers onto one shared in-flight promise. Only the **resolved** value is cached; a throw clears the in-flight slot so a later call retries (failures are never cached). The cache wraps the **whole** function — both the iso and the system-git (ssh / forced) engines, and it composes cleanly with the concurrently-landed DDR-131 transport hardening (`classifyRemoteUrl` / `isTrustedTokenHost`): the inner `remoteAheadBehindUncached` refuses `unsafe`/non-GitHub remotes (`{0,0}`, no spawn) and the cache simply memoizes whatever the hardened body returns. A tiny `invalidateRemoteProbe(dir)` is called at the entry of `gitPush` / `gitPull` / `gitFoldDraft` so the nudge re-probes immediately after a publish/get-latest/fold. This is **per fresh process** and deliberately never persists — a repo switch respawns the sidecar and a fresh repo deserves one fresh probe.

3. **Token caching stays out (DDR-108 invariant).** Per-repo local-status caching is also out of scope — local `git status` is network-free and fast, and the identity cache already wins the cross-repo case.

## Consequences

- **Good:** repo switch / restart paints the identity from a disk read with **no `api.github.com/user` round-trip** on the hot path; the "Checking GitHub…" spinner is gone for the returning user. The probe stops re-fetching on every panel toggle / effect re-run within a session, while still updating immediately after the user's own push/pull/fold and within 45 s of a teammate's. Local `gitStatus` already paints before the remote probe resolves (the remote-sync effect is a separate, `gitStatus?.repo`-gated `app.jsx` effect writing a separate `remoteSync` slice) — confirmed, no client change needed.
- **Security (verified by `security-auditor` + `ethical-hacker`):** the **token is never written to disk** — only its sha256 prefix, as the cache key. A token swap / different account yields a different key ⇒ a clean miss ⇒ a fresh fetch, so the file can never serve account A's profile to account B. The file/dir are owner-only (0600/0700). The cache does not widen the token's reach (DDR-054/108/109): identity is public profile data, the value cached is not the token, and the web (non-native) read-only badge path (DDR-119) is untouched.
- **Cost / accepted:** a stale identity can persist at most one SWR cycle (served once, then revalidated). The TTL means a teammate's brand-new commit can be up to 45 s late in the nudge — acceptable for a passive banner, and `invalidateRemoteProbe` makes the user's own actions instant. The `~/.maude` cache file is a new per-user artifact (not project-scoped, not gitignored — it lives outside any repo).
- **`gitListBranches` updatedAt cost — measured, cheap:** Task 4 quick-measured the iso-engine per-branch `readCommit` for the recents `updatedAt` at **~4.5 ms for 61 branches** (parallel single-object HEAD reads, no log walk). No bounding needed.
- **Verification ceiling:** native-only dev-server internals (identity/status performance) — the standard 5-platform `scenario-runner` doesn't apply. Verification is the unit tests (identity: cache round-trip + token-never-persisted + key-mismatch-miss + corrupt-JSON-miss; probe: TTL-serves-the-cached-object + invalidate-re-evaluates + concurrent-coalesce, asserted via **object identity** since the DDR-131 transport gate refuses the offline local remote — the real fetch/count path is dogfood-verified, the same offline ceiling DDR-131 records for `gitFetchRemote`) plus the manual native dogfood. Intentional divergence, recorded here per the acceptance checklist.
