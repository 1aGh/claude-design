# DDR-167: Local-file / SVG / PDF ingestion — security posture

**Status:** Accepted — 2026-07-14 (design-stage, pre-code per plan `.ai/plans/feature-onboarding-and-design-system-migration.md` T9: this DDR gates all of Phase 3; `ethical-hacker` + `security-auditor` ran two full rounds — Round 1 against the initial draft, Round 2 confirming the fixes — see § Security review below. Every finding either has a concrete technical closure specified here or is named as an explicit, bounded, accepted residual matching this project's house style (DDR-164 §F3/F4). The remaining items are implementation-mechanism specifics (worker-thread isolation, a proof-token gate, permanent regression tests) that T10 must build as specified, not open architectural questions — narrow enough that a lightweight targeted check at T10 implementation time is proportionate, not a full Round 3 fan-out.).
**Extends:** [DDR-045](DDR-045-real-disk-path-resolution-for-compiled-dev-server.md) (real-disk-path resolution the write side reuses), the `_fetch-asset.mjs` security header (magic-byte sniff, content-addressed flat write, realpath containment — the model this ingestion mirrors on the write side), [DDR-088](DDR-088-canvas-media-vocabulary-and-asset-write-surface.md) (the `assets/<sha8>.<ext>` write surface + canvas-origin route classification every new route must slot into), [DDR-054](DDR-054-linked-mode-trust-model-and-task-4-hardening.md) (versioned `assets/` syncs to untrusted branch peers — an imported asset is peer-visible, not just importer-visible), [DDR-071](DDR-071-svgo-dependency.md) (SVGO is a minifier/validity-gate, NOT a sanitizer), [DDR-164](DDR-164-byok-ai-media-generation-provider-adapter-spine.md) (the "prompts/paths must trace to the BRIEF, never to incidentally-read untrusted context" discipline, reused here in Decision 5).
**Instruments (planned, Phase 3 / T10):** `apps/studio/bin/import-asset.sh` + `apps/studio/bin/_import-asset.mjs` (shared pure functions) + `cli/lib/import-asset.mjs` + tests; a new privileged `POST /_api/import-asset` route in `http.ts` for the in-app Brand-upload panel (T12); `cli/commands/design.mjs` verb registration.

## Context

Maude's only existing ingestion primitive is `_fetch-asset.mjs` — URL-only, https-only, and it explicitly **rejects** SVG and PDF (raster magic-byte sniff returns `null` for both, by design). The plan's Phase 3 needs to bring in a user's **existing** brand material: a **local file** (not a URL) that may be an **SVG** (a logo) or a **PDF** (a brand manual / a Figma export). Both formats are rejected today *for a reason* — SVG is executable content (`<script>`, event-handler attributes, external references) and PDF has a large historical CVE surface in parsers plus its own embedded-script/embedded-URI capability. This DDR is required to exist and be reviewed **before** any Phase 3 code, per the plan's T9/T10 gate.

**Explicit scope boundary — what this DDR does NOT cover.** Plan task T12 extends `/design:setup-ds --from-brand` to feed content *extracted from* an ingested file (palette/type cues, logo) into `ux-research-agent`'s discovery payload — a live `Read, Write, Bash, Glob, Grep, WebSearch, WebFetch` agent. That hand-off is a **separate trust boundary** this DDR does not design or clear: whatever text/labels an ingested SVG/PDF carries (visible `<text>`/`<title>`/`<desc>` content, OCR'd/rendered PDF-page text) **MUST be treated as untrusted DATA in that agent's context, never as instructions**, mirroring the same discipline already established for peer-synced sidecar content (DDR-164 §G3, `sanitizeReuseText`). T12 needs its own DDR amendment (or a standalone follow-up DDR) addressing that hand-off specifically, before it ships — this document only clears the byte-level ingestion pipeline (Decisions 1–5 below), not what downstream agents do with the extracted content.

## Two distinct entry points, two distinct trust models — same content pipeline

| Entry point | Input | Trust model |
| --- | --- | --- |
| CLI verb: `maude design import-asset <local-path>` | An operator-typed filesystem path | **Trusted only when the path traces to the human's own current instruction** — see Decision 5. NOT unconditionally trusted just because it's a CLI arg (Round 1 finding: an ACP agent session can invoke this tool with an auto-approved Bash call). |
| In-app Brand-upload panel (native, T12) | Bytes from a Tauri **native file-picker** dialog (mirrors the existing `pick_media_file` pattern, memory `reference_tauri_file_open_needs_rust_dialog`), POSTed to a new privileged `POST /_api/import-asset` | **No server-side path resolution at all** — the client never sends a path string, only bytes over loopback HTTP. This closes the entire "arbitrary local-file-read via a path parameter" class by construction, exactly like `POST /_api/asset` already does for images. This is the STRONGER entry point and the one the in-app panel exclusively uses. |

In **both** paths the FILE CONTENT is untrusted regardless of how trusted the operator or the picker is — a user can unknowingly import a malicious SVG/PDF they downloaded from somewhere else. Both entry points funnel through the **same shared, pure sanitize/rasterize functions** in `_import-asset.mjs` (imported directly by the HTTP route, not shelled out to — avoiding process-spawn overhead on the interactive path; the CLI shim is a thin argv wrapper around the identical functions, mirroring `_fetch-asset.mjs`'s own module/CLI split).

`POST /_api/import-asset` is a **privileged, main-origin-only** route (file-write + local-file-adjacent surface) — per the DDR-088 canvas-origin convention, it goes in **NEITHER** `CANVAS_SAFE_API` nor `startCanvasServer`'s routes map. The untrusted canvas iframe must never reach it. `canvas-origin-gate.test.ts` gets a new `GET → 403` assertion for it, same pattern as every other privileged route.

## Decision 1 — SVG: ALLOWLIST DOM-sanitize (`happy-dom`) → SVGO validity/minify → real-browser execution canary

**No new dependency.** `happy-dom` is already in `apps/studio/package.json`. It gives a real, standards-compliant DOM/XML parser — far safer than a regex/string-replace "sanitizer" (regex can't reliably reason about nested/malformed markup the way a real parser can).

**Round-1 finding this revises:** treating a `happy-dom`-sanitize-then-reserialize pass as the *final* safety gate is a documented anti-pattern — DOMPurify's own maintainers state plainly that pairing DOMPurify with `happy-dom` "is currently not recommended and will likely lead to XSS," because sanitizing with one parser and later rendering the serialized string in a *different* parser (whatever actually renders the SVG in the shipped app) is exactly the mutation-XSS (mXSS) setup: the sanitizer inspects one reconstructed tree, the real renderer builds a different one from the same string. This revision keeps the `happy-dom` pass (still valuable as a first-pass allowlist filter) but **no longer trusts it as the last word** — Decision 1 step 6 adds a real-browser execution canary using the actual rendering engine as the final oracle, and step 3 flips from a denylist to an allowlist (an unrecognized/foreign element or attribute is dropped by default, not only the enumerated bad actors).

**Pipeline, in order:**

1. **Pre-parse hard rejects (deterministic, no parser trust required), all run against a canonical UTF-8 decode of the input** (a non-UTF-8/non-ASCII declared encoding is rejected outright — the string-level checks below and the later DOM parse must never disagree about what bytes they're looking at):
   - Byte-size cap: **5 MB** pre-sanitize.
   - **Reject outright** any input containing a case-insensitive `<!DOCTYPE` or `<!ENTITY` declaration (closes XXE / entity-expansion in one deterministic check, independent of `happy-dom`'s own DTD-handling behavior).
   - **Reject outright** any XML processing instruction other than the single leading `<?xml version="…" encoding="…"?>` declaration itself — specifically closes `<?xml-stylesheet type="text/xsl" href="…"?>` (external-XSLT fetch/exfil, and XSL can itself carry script-equivalent constructs). *(Round-1 finding, security-auditor #2.)*
   - Magic-byte / content sniff: the body must actually look like XML/SVG (starts with `<?xml`, `<svg`, or `<!--` followed eventually by `<svg`, case-insensitive, after whitespace trim) — a non-SVG file with a `.svg` extension is rejected here, not trusted from the extension.
2. **Parse** into a `happy-dom` `Window`/`Document`. A parse failure is a hard reject.
3. **Walk the DOM tree with an ALLOWLIST** (flipped from a denylist per the Round-1 finding — anything not explicitly recognized is dropped, at any depth, not only at the root):
   - **Allowed elements only:** `svg, g, path, rect, circle, ellipse, line, polyline, polygon, defs, clipPath, mask, linearGradient, radialGradient, stop, pattern, symbol, use, image, text, tspan, textPath, title, desc, metadata, marker, filter` + the standard filter-primitive children (`feGaussianBlur, feOffset, feMerge, feMergeNode, feColorMatrix, feComposite, feFlood, feBlend`) + the SMIL set (`animate, animateTransform, animateMotion, set`) **with their functional attributes PERMANENTLY excluded — see below**. Everything else — `script`, `foreignObject` (also avoids this project's own documented `foreignObject`-under-transform bugs, memory `reference_foreignobject_under_transform_breaks_carets_and_clicks`), `iframe`, `embed`, `object`, `style`, and any unrecognized/foreign-namespace element — is dropped along with its subtree, by construction of the allowlist, not by enumeration.
   - **`metadata`/`title`/`desc` are allowed as text-only containers** — any element child inside them is dropped (their content is inert copy, not markup).
   - **SMIL elements (`animate`/`animateTransform`/`animateMotion`/`set`) are allowlisted as TAGS ONLY — their functional attributes (`attributeName`, `to`, `from`, `values`, `begin`, `dur`, `repeatCount`) are PERMANENTLY EXCLUDED from the attribute allowlist below, making them structurally inert.** *(Round-2 finding, ethical-hacker — a real, actively-exploited bypass class: SMIL `attributeName="href"`/`"xlink:href"` + `values="javascript:…"` retargets a `use`/`image` reference at render time, defeating a static string-scan of literal `href=`/`xlink:href=` attributes — confirmed live in Angular's sanitizer CVE-2025-66412, Roundcube CVE-2025-68461, and PortSwigger's "SVG animate XSS vector" research. This is deliberately NOT "omitted from a shared list" — it is a standing prohibition future implementers must not casually lift when someone reasonably asks "why allowlist `<animate>` if it can't do anything." If real SMIL animation support is ever wanted, it needs its own DDR amendment re-deriving the href-retargeting threat model from scratch, not an incremental attribute addition to this allowlist.*
   - **Allowed attributes per element are an explicit presentation-attribute allowlist** (`fill, stroke, stroke-width, d, x, y, width, height, cx, cy, r, rx, ry, points, transform, viewBox, preserveAspectRatio, id, opacity, fill-opacity, stroke-opacity, font-family, font-size, font-weight, text-anchor, gradientUnits, gradientTransform, offset, stop-color, stop-opacity, patternUnits, patternTransform, xmlns, xmlns:xlink, version`) — every `on*` event-handler attribute is excluded by construction (it is simply never on the allowlist), not by a separate "strip `on*`" pass.
   - **`style=` attributes and `<style>` elements are dropped entirely** — not filtered, not parsed. This closes `@import`, `-moz-binding: url(...)`, `behavior:`/`expression()`, and CSS `url(...)` external references in one deterministic move. Presentation attributes cover real-world imported-logo styling needs; CSS-based styling is not a requirement for a logo import.
   - **Every FuncIRI-valued attribute — `href`/`xlink:href` (on `use`, `image`, `textPath`) AND `clip-path`/`mask`/`filter`/`marker-start`/`marker-mid`/`marker-end` — is value-constrained the SAME way**, not just `href`: allowed ONLY as `#fragment` (same-document reference) or, for `href`/`xlink:href` specifically, `data:image/{png,jpeg,gif,webp};base64,…` — explicitly **not** `data:image/svg+xml` (closes nested-SVG-in-`data:` reintroducing the same class one level down). Any `http:`, `https:`, `javascript:`, `file:`, or bare external reference on ANY of these attributes causes the ATTRIBUTE to be dropped (element kept, reference removed). *(Round-2 finding, security-auditor #3 — the Round-1 revision restricted `href`/`xlink:href` but left `clip-path`/`mask`/`filter`/`marker-*` unrestricted despite taking the identical `url(#id)`/`url(https://…)` FuncIRI syntax; `clip-path`/`mask`/`filter`/`marker-*` are correspondingly now REMOVED from the plain presentation-attribute allowlist above and listed only here, under the value constraint.)*
   - **Namespace check on every element**, not just the root: any element whose namespace isn't `http://www.w3.org/2000/svg` is dropped along with its subtree (the allowlist-by-tag-name above already achieves this in practice, since a foreign-namespace element won't match an allowed local name, but this is asserted explicitly as a second, independent check).
4. **Re-serialize** the sanitized DOM back to an SVG string.
5. **Run the result through the EXISTING `optimizeSvg`/`isValidSvg`** (`draw/optimize.ts`, SVGO) as a parse/validity gate + minifier — **explicitly not sanitization** (SVGO's `preset-default` does not strip scripts or event handlers on its own). A SVGO parse failure on the already-sanitized output is a hard reject.
6. **Real-browser execution canary (closes the mXSS parser-differential gap), 15-second timeout.** Load the SVGO-optimized, allowlist-sanitized string into a minimal host page served by the SAME hardened, network-denied headless-Chromium instance Decision 2 uses for PDF rendering (one shared "sandboxed-render" helper — network-deny, OS sandbox ON, freshness-checked binary). Capped at **15 seconds** *(Round-2 finding, ethical-hacker — the original draft left this step unbounded despite every other step in the pipeline being time-boxed, and it shares the same browser resource as concurrent PDF imports)*. The host page installs a probe (e.g. a `window.__MAUDE_IMPORT_CANARY__` flag only an executed script/event-handler could set) before loading the candidate SVG, then asserts: (a) the probe was never tripped, (b) zero outbound network attempts occurred during the load, (c) no console error pattern consistent with active content executing. **Any one of these firing, OR the timeout itself firing, is a hard reject of the import** — surfaced to the user as "this file could not be safely imported." This step verifies against the ACTUAL rendering engine that nothing survived, rather than trusting `happy-dom`'s tree-walk was exhaustive. **Named limitation, not overclaimed:** a passive load-and-observe canary does not simulate a user gesture (click/hover), so a payload that only fires on interaction (the exact SMIL-retargeting class the permanent attribute exclusion above closes at the allowlist level, belt-and-braces) would not be caught by the canary alone — the canary and the allowlist are complementary, neither is sufficient alone, which is why the SMIL exclusion above is a permanent prohibition and not "the canary will catch it anyway."
7. **Content-address + contained write** — identical to the write-path model in Decision 3.

**Consumption contract, with an ENFORCED backstop (Round-1 finding; Round-2 strengthened — security-auditor and ethical-hacker both flagged that policy prose alone is exactly the failure mode this codebase has already hit once: CLAUDE.md's own runtime-state taxonomy "must agree across THREE lists... They drifted once.").** A sanitized SVG asset may be referenced ONLY via `<img src>` / CSS `url(...)` background — **never inlined as literal DOM markup** (no `dangerouslySetInnerHTML`, no regex-splice into JSX) for as long as it is treated as "sanitized." This matters specifically in this codebase because the established brand-mark convention (`system/maude/preview/logo.tsx`) is hand-authored inline SVG-as-JSX — a future feature that inlines an *imported* logo the same way would move any surviving payload from an `<img>`/asset-fetch context into literal main-origin DOM execution, bypassing the DDR-054 canvas-iframe sandbox entirely. Any future feature that wants to inline an imported SVG (e.g. for `currentColor` recoloring) MUST re-run this DDR's sanitize pipeline immediately before inlining. T10 MUST also add a **permanent regression test** — mirroring `cli/lib/plugin-cli-reachability.test.mjs`'s existing pattern of grepping the tree for a banned call shape — asserting no `dangerouslySetInnerHTML` (or equivalent raw-HTML-injection call) anywhere in `apps/studio/client/**` takes its source from an `assets/*.svg` path or an `import-asset`/`_import-asset.mjs` output value. A written clause a future PR author has to remember is not the gate; the test is.

**Accepted residual:** a maliciously crafted, deeply self-referential `<use href="#a">` chain inside an otherwise-clean SVG could still cause a slow/hung render in the importer's own browser later. Self-DoS only, bounded to the importer's own session — accepted rather than adding cycle-detection complexity.

## Decision 2 — PDF: rasterize via the already-bundled headless Chromium, treated as an EXECUTING engine under hard isolation — never as a passive renderer

**No new dependency, and specifically NOT a native-binary dependency** (rules out `pdfjs-dist` + `node-canvas`/`@napi-rs/canvas`, the exact class of dependency that broke the Task-2.7 whisper spike's `bun --compile` packaging and that DDR-070 rules out). `pdf-lib` (already a dependency) does not rasterize — used here only for structural page-count discovery.

**Round-1 finding this revises:** the original draft claimed PDF content is "never parsed by a PDF-content-executing library" because rendering is "delegated to Chromium's PDFium... same trust tier as any screenshot target." Both halves of that claim are wrong. Chromium's built-in PDF viewer (PDFium) genuinely IS a PDF-content-executing engine — it is documented to auto-fire embedded JavaScript / `OpenAction`/`/AA` actions with **no user interaction** (Chromium issue tracker #419312803), and PDF's `SubmitForm`/`URI`/`Launch` actions can drive outbound requests or process launches directly from the PDF language itself. And "same trust tier as any screenshot target" is false: every prior use of the bundled browser in this codebase (`screenshot.sh`, `canvas-rects.sh`, footage probing) points it at content **this project itself authored** — this is the first design to deliberately point it at **adversarial** input, and PDFium carries an active cadence of sandbox-RCE-class CVEs (Talos/vendor writeups through 2026). The mitigation below is **process isolation + hard network denial + adversarial pre-ship testing + binary freshness**, not "we avoided parsing it."

**Pipeline:**

1. **Single capped read via a symlink-safe resolve-then-open.** Resolve the operator-given path with `realpath()` **immediately before** the one read, rejecting if any path component is a symlink (`fs.lstatSync` on each segment, or a platform `O_NOFOLLOW`-equivalent open) — then read the input file **exactly once** into memory, bounded by the 50 MB cap. The identical in-memory buffer is reused for the size check, the `pdf-lib` page-count parse, AND the temp-file write; there is no second, independent filesystem read of the operator-given path at any later step. *(Round-1 finding, ethical-hacker's TOCTOU gap, closed by collapsing to one read; Round-2 follow-up, ethical-hacker — the single `open()` underlying that one read still resolves the path at that instant, so the realpath-then-open discipline is added here to shrink the remaining window to its structural minimum. Residual: an attacker with EXISTING local code execution and sub-millisecond timing could in principle still win this race — accepted as out of scope, since an attacker who already has local code execution has strictly easier paths to the same data than racing this import.)*
2. **Page-count discovery, isolated in a worker thread with hard termination — not a bare `Promise.race`.** `pdf-lib`'s `PDFDocument.load` + `.getPageCount()` on the in-memory buffer runs inside a `node:worker_threads` `Worker` (or an equivalent short-lived child process), given the **same 15-second budget** the per-page rasterize step gets, and the worker is `.terminate()`-ed on timeout. *(Round-2 finding, security-auditor #4 — a bare timer-based `Promise.race` around a synchronous, CPU-bound, single-threaded call CANNOT interrupt that call: the event loop is blocked by the hang itself, so the timer callback never gets a turn to fire, meaning a pathological input would freeze the whole dev-server process, not just fail this one request — strictly worse than the "hard reject" the original wording promised. A worker thread is a real concurrency boundary that CAN be torn down externally regardless of what its own event loop is doing.)* `pdf-lib`'s parse never executes embedded JavaScript or resolves embedded remote references either way (it is a structural PDF-object parser, not a renderer) — the isolation here is about hang-safety, not content-safety. A timeout/terminate is a hard reject ("unparseable/malformed PDF").
3. **Page-count cap: 20 pages.** Anything larger errors naming the cap.
4. **Rasterize, via one shared hardened "sandboxed-render" browser helper** (the same instance Decision 1 step 6 uses for the SVG canary), launched with:
   - **Hard network denial** for this specific invocation, at the OS/network level (a network namespace, firewall rule, or restricted-user egress block) — **not** hostname-resolution mapping alone. *(Round-2 finding, both reviewers — `--host-resolver-rules="MAP * ~NOTFOUND"` on its own only blocks *hostname* lookups; a PDF action targeting a bare IP literal (`http://93.184.216.34/…`) performs no DNS resolution and would sail past that rule unblocked.)* Whatever mechanism T10 implements must be verified against BOTH a hostname target and an IP-literal target in the mandatory fixture set below — this is now an explicit fixture requirement, not left to the implementer's interpretation.
   - **The OS-level Chromium sandbox stays ON** — `--no-sandbox` is never passed for this invocation. Real, independent defense-in-depth against a PDFium memory-corruption CVE escalating past the renderer process.
   - **Binary freshness verified before this feature is enabled** — `_ensure-browser.mjs`'s existing `cachedShell()` returns the first provisioned binary with no freshness check, which is fine for its original (trusted-content, screenshot-only) use but not acceptable once the same binary is repurposed for adversarial PDF input. T10 must add an explicit recency check (or force a fresh provision) specifically gating the PDF-import path. *(All three sub-bullets: Round-1 finding, ethical-hacker HIGH #1.)*
   - Navigate to `file://<contained-temp-copy-path>.pdf#page=<n>` with the PDF viewer's print/UI chrome disabled, fixed capped viewport (~1600×2200, never `--full` unbounded capture).
   - **Per-page timeout: 15 seconds.** The rasterize LOOP across all pages is capped at **5 minutes total** (20 pages × 15s worst case = 300s = exactly the loop budget). Browser **launch** is a separate, one-time budget capped at **15 seconds before the loop starts** — not double-counted against the 5-minute loop cap. *(Fixes the Round-1 arithmetic contradiction, security-auditor warning — the original wording implied launch had to fit inside the same 5 minutes as a 300-second worst-case loop.)*
5. **The browser navigates a CONTAINED TEMP COPY, never the original path** — copied from the single in-memory buffer from step 1 (not re-read from disk), so there is no window in which the on-disk file could differ from what was validated. Removed unconditionally (`finally`) after rasterization completes or fails.
6. **Each page's screenshot bytes are re-sniffed** (`sniffImageType`/`sniffAssetType`) before being treated as a trusted image — never assumed safe just because the browser produced them.
7. **Content-address + contained write per page** — Decision 3; one `assets/<sha8>.png` per page.

**Mandatory gate, PERMANENT not one-time (Round-1 requirement, strengthened in Round 2):** before the PDF pipeline ships, T10 must build adversarial fixtures — not just visual-rendering smoke tests — against the hardened launch config above: (a) a PDF with an `OpenAction`/`/AA` JavaScript canary, (b) a PDF with a `SubmitForm`/`URI`/`Launch` action pointed at a disposable local listener bound to an **IP-literal address**, not a hostname (see the network-denial bullet above). Both must show **zero outbound network reachability and no local process/file-launch side effect** under the network-deny + sandbox-on configuration. **These fixtures MUST become a permanent, always-run regression test** (in the same spirit as `canvas-origin-gate.test.ts` — a standing assertion, not a pre-ship checklist item that's satisfied once and then forgotten), re-run on every change to the import pipeline AND on every bundled-Chromium binary bump. *(Round-2 finding, ethical-hacker — a one-time pre-ship exercise doesn't catch a later regression from a network-deny mechanism refactor or a routine binary update; a permanent test does.)* If either fixture reveals a surviving side channel, the PDF import path does not ship until it's closed.

**Accepted residual, named explicitly (Round-2 finding, ethical-hacker):** the mitigations above close the network-mediated (`SubmitForm`/`URI`) and local-launch (`Launch`) vectors, but do **not** close PDFium memory-corruption / sandbox-escape RCE as a class — Chromium's PDFium carries an active, ongoing cadence of CVSS-8.8-class use-after-free/heap-overflow CVEs through 2026, and the only defenses in this design are Chromium's own bundled OS sandbox plus binary-freshness (which only protects against already-patched *n-day* bugs, not a live 0-day). There is no isolation layer *outside* Chromium's own sandbox boundary in this design (no dedicated restricted OS user, no container/VM jail, no seccomp profile) — this is named here as an accepted, bounded residual (matching the same house-style treatment Decision 1 gives the `<use>` self-DoS residual) rather than left implicit. Rationale for accepting rather than adding outer isolation now: this is the FIRST adversarial-input use of the bundled browser in this codebase, the mitigations above close the higher-likelihood/lower-sophistication vectors (network exfil, local launch), and an outer sandbox/container layer is a meaningfully larger infrastructure change proportionate to revisit if this residual is ever observed exploited in practice, not something to gate T10 on speculatively. **Binary-freshness is a load-bearing part of accepting this residual — it must be a real, verified recency check at T10 implementation, not a comment.**

**Explicitly rejected alternatives (recorded so this isn't re-litigated):**
- `pdfjs-dist` + `node-canvas`/`@napi-rs/canvas` — native-addon `bun --compile` risk.
- Shelling out to `pdftoppm`/`pdftocairo` (Poppler) — requires a system-installed binary Maude doesn't control or bundle; breaks the zero-terminal posture.
- Trusting `pdf-lib` alone for rendering — it doesn't render; its role stays narrowly "structural page-count only."

## Decision 3 — write-path containment (shared by both SVG and PDF-page output)

Mirrors `_fetch-asset.mjs` exactly, no new pattern invented:

- **Content-addressed, flat filename:** `<sha8>.<ext>` (`ext` ∈ `svg | png`), computed from the FINAL (sanitized/rasterized) bytes, never from the original filename or any user-supplied string.
- **Realpath containment assertion:** the resolved write path must resolve inside `<designRoot>/assets/` (same `containedAssetPath`-style check — resolve, then assert `startsWith(assetsDir + sep)`), independent of anything the caller passed in.
- **Charset contract on the generated name:** `/^[a-z0-9]{8}\.(svg|png)$/` asserted before write.
- **Per-file cap:** both new asset kinds are subject to the existing `ASSET_MAX_BYTES` category cap on write.
- **Session write budget:** both count against the existing `ASSET_SESSION_BUDGET` aggregate — no new budget, no bypass.
- **Versioned + peer-synced (DDR-054):** an imported SVG/PNG lands in `assets/` exactly like any other asset, versioned and synced to branch peers under linked-mode. This DDR ensures what's WRITTEN is already sanitized/rasterized-safe *before* it reaches that syncable surface.

## Decision 4 — `/_api/import-asset` route shape

- `POST` only, **raw-bytes body only** — NOT `multipart/form-data`. *(Round-1 correction, security-auditor #5 — this dev server has zero multipart parsing anywhere; `/_api/asset` and every other route use raw-bytes bodies exclusively. Offering multipart here would invent a genuinely new upload shape, the opposite of "reuse the existing convention.")* The `kind` hint (`'svg' | 'pdf'`) travels as a header (e.g. `X-Import-Kind`), mirroring how other routes pass small out-of-band metadata alongside a byte stream — not trusted for the security-relevant dispatch decision (each pipeline still sniffs its own input structurally regardless of what `kind` claims; a mismatch errors cleanly rather than silently reinterpreting the bytes).
- `sameOriginWrite` CSRF gate + `isLoopbackHost` DNS-rebind gate — same double gate as every other privileged mutating route in `http.ts`.
- **Absent from both `CANVAS_SAFE_API` and `startCanvasServer`'s routes map** (privileged, DDR-088 convention) — asserted by a new `canvas-origin-gate.test.ts` case.
- Response shape mirrors `SaveAssetResult` (`{ ok, path?, error?, status? }`).

## Decision 5 — CLI-verb reachability by AI agents (confused-deputy mitigation)

**Round-1 finding this addresses (ethical-hacker HIGH #3):** the original draft's "operator-trusted path, like `cp`" framing for the CLI verb assumed a human typing a command at a terminal. This project's own ACP chat panel drives the user's own `claude` CLI with Bash tool access under an "accepted bounded risk" auto-approve posture (DDR-125 §F2) — a prompt-injected agent session (from a page it was asked to summarize, a file it was asked to review) could invoke `maude design import-asset ~/Documents/<anything-that-passes-the-magic-byte-sniff>.pdf` indistinguishably from a legitimate brand-manual import. None of Decisions 1–4's controls defend against this, because they validate content-*safety*, not source-*legitimacy* — the pipeline would work exactly as designed and still exfiltrate a private document into the versioned, peer-synced `assets/` tree (DDR-054).

**Round-1 named this a pure residual ("not fully closeable"); Round 2 (ethical-hacker) correctly pushed back** — DDR-164 §F3's residual is about a *pre-existing, structural* full-tool-agent capability (an agent reading files as an inherent part of its normal job); `import-asset` is different — it is a **new, narrow, purpose-built tool being added specifically for this feature**, which is exactly the case where an out-of-band technical gate is tractable, not just aspirational. Settling for skill-level discipline alone (asking the model to behave) is below this project's own bar for a privileged decision. This DDR now specifies a real gate:

- **Technical gate, SCOPED to the actual risk — a native-file-picker-issued proof token, required only inside a Maude-spawned ACP session.** The confused-deputy risk is specific to the CLI verb being invoked BY AN AGENT (the ACP-spawned `claude` session's Bash tool), not by a human typing directly into their own ordinary terminal — that plain power-user path (`maude design import-asset ~/logo.svg`, run by a human outside any Maude-managed session) is legitimate and must keep working unencumbered, matching every other `maude design <verb>` CLI tool. Maude's own ACP spawn code (`acp/*.ts`) already controls the child's environment (it already scrubs/sets env vars for other reasons, e.g. `MAUDE_GEN_KEY*` per DDR-164 §F3) — it sets a marker (e.g. `MAUDE_ACP_SESSION=1`) on the `claude` child it spawns for the chat panel. `import-asset` checks for that marker: **absent → the existing operator-trusted CLI behavior, unchanged; present → a bare path is refused**, and the verb instead requires a short-lived, single-use proof token issued by the same native file-picker dialog the in-app panel already uses (Tauri, OS-level UI — something a Bash-only agent session cannot drive) and bound to the specific file the human just picked. This converts "the agent should only use paths from the user's own instruction" from a prompt-compliance hope into an out-of-band check the agent cannot forge purely through tool calls, specifically where the risk actually lives — without degrading the legitimate terminal power-user path at all. *(Round-2 finding, ethical-hacker HIGH #3.)*
- **Skill/command discipline, retained as defense-in-depth:** the `/design:setup-ds --from-brand` wiring (T12) still instructs that any file reference must trace to the user's own current-turn instruction, never to incidentally-read context — cheap, and narrows the cases where a human even sees a picker prompt they didn't expect.
- **Visibility for the reviewable case:** every successful import is surfaced in the existing user-visible activity/notification surface — but the entry records ONLY a generic kind description ("SVG logo" / "PDF, N pages") and the resulting `assets/<sha8>.<ext>` path, **never the original local source path or filename**. *(Round-2 finding, security-auditor — the original wording would have surfaced the full source path in a surface that itself may be peer-synced under linked mode (DDR-054), leaking local directory/filename structure — e.g. revealing a path under a user's home directory — as metadata beyond what the sanitized asset content alone discloses.)*
- **Named residual, explicitly, narrowed:** a proof-token gate closes "the agent invents/guesses a path the human never saw." It does not close a scenario where the human DID see and dismiss/approve a picker prompt under active social-engineering pressure from injected content — that residual is the same DDR-164 §F3 class (a human, not just an agent, being deceived) and is accepted as out of scope for a file-import feature, same as it's accepted everywhere else agent-mediated actions eventually route through a human-visible confirmation.

## Threat model summary (what this DDR closes vs. accepts)

| Threat | Closed by |
| --- | --- |
| SVG `<script>` / event-handler XSS | Allowlist DOM walk (Decision 1, step 3) + real-browser execution canary (step 6) |
| SVG mutation-XSS / sanitizer-parser-differential bypass | Real-browser execution canary using the actual rendering engine as final oracle (Decision 1, step 6) — NOT trusting `happy-dom` alone |
| SVG XXE / entity-expansion DoS | Hard pre-reject on `<!DOCTYPE`/`<!ENTITY` (Decision 1, step 1) |
| SVG external-XSLT / processing-instruction smuggling | Hard pre-reject on any non-declaration `<?...?>` PI (Decision 1, step 1) |
| SVG external-reference SSRF/exfil/tracking (`href`/`clip-path`/`mask`/`filter`/`marker-*` to `http(s)://`) | FuncIRI-value allowlist to `#fragment`/`data:image/{raster}` on EVERY such attribute, not just `href` (Decision 1, step 3) |
| SVG SMIL `attributeName`/`values` retargeting `href` to `javascript:` at render time | `attributeName`/`to`/`from`/`values`/`begin` PERMANENTLY excluded from SMIL elements' attribute allowlist (Decision 1, step 3) |

| PDF PDFium memory-corruption / sandbox-escape RCE | **Accepted residual, named explicitly** — bounded by Chromium's own sandbox + binary freshness; no outer isolation layer in this design (Decision 2) |
| PDF zip-bomb / oversized-decompression / page-count DoS | Byte-size cap + page-count cap + per-page/loop/launch timeouts (Decision 2) |
| `pdf-lib` structural-parse hang on malformed input | Worker-thread isolation with hard `.terminate()`, not a bare timer race (Decision 2, step 2) |
| Local-file path traversal / arbitrary-file-read via the in-app panel | Panel never sends a path — native file-picker + bytes-over-loopback-HTTP only (entry-point table) |

| Import provenance leaking local path structure to peers via the activity log | Generic kind description only, never the source path, in the notification surface (Decision 5) |
| Extracted content steering `ux-research-agent` (T12) | **Out of scope for this DDR** — plan now has an explicit T12a DDR-gate before T12 code (§ Context, scope boundary) |
| Self-referential SVG `<use>` render-hang | **Accepted residual** — self-DoS only, bounded to the importer's own session (Decision 1, closing note) |

## Consequences

- Two content-sanitization code paths (SVG allowlist-sanitizer + execution canary, PDF page-rasterizer under hard isolation) are new, security-relevant code needing test coverage per the full threat table above — including the mXSS/DOMPurify-bypass fixture corpus (PortSwigger's "Bypassing DOMPurify again with mutation XSS," the SMIL `animate`/href-retargeting class, namespace-confusion writeups) as negative tests, not just "did we strip the tag" unit tests.
- No new npm dependency. `happy-dom` and `pdf-lib` are both already present; PDF rasterization and the SVG execution canary share one hardened, network-denied headless-Chromium helper.
- **Three permanent regression-test requirements, not optional hardening:** (1) the PDF pipeline's adversarial fixtures (OpenAction/JS + SubmitForm/URI/Launch, against both hostname and IP-literal listener targets), (2) the SVG execution canary, (3) the "no `dangerouslySetInnerHTML` sourced from an imported SVG" grep-based test. T10 does not ship without all three passing AND wired into the standing test suite (not a one-time pre-ship checklist).
- The confused-deputy proof-token gate (Decision 5) needs an `acp/*.ts` env-marker + a Tauri-issued token verification mechanism — new surface T10 must design carefully and get its own focused look at implementation time, given it's the newest, most bespoke piece of this DDR.
- T12 (extracted-content → `ux-research-agent`) requires its own DDR (plan task T12a, added alongside this revision) before it ships; this DDR does not clear it.

## Security review

**Round 1 (2026-07-14) — design-stage, against the initial draft.** `security-auditor` (defender) + `ethical-hacker` (adversarial) both reviewed the DDR text (no code existed yet) plus the real `_fetch-asset.mjs`/`http.ts`/`_ensure-browser.mjs` it claimed to mirror.

**security-auditor — 4 blockers, 5 warnings, all resolved in this revision:**
1. PDF isolation controls unspecified (sandbox state, JS/action execution, network egress) → Decision 2 now requires hard network-deny + sandbox-on + binary-freshness + mandatory adversarial fixtures.
2. XML processing instructions (`xml-stylesheet`) not addressed → Decision 1 step 1 now hard-rejects any non-declaration PI.
3. CSS `@import`/legacy-execution properties under-specified → Decision 1 step 3 now drops `<style>`/`style=` entirely rather than attempting to filter CSS.
4. `pdf-lib` structural parse had no timeout → Decision 2 step 2 now shares the 15s budget.
5. Multipart-body claim was factually wrong (this server has no multipart parsing) → Decision 4 corrected to raw-bytes-only + header-carried `kind` hint.
Warnings (namespace-check root-only, denylist-vs-allowlist, cap arithmetic not fitting, CSS/href MIME-rule clarity, metadata/title coverage) are all folded into the Decision 1/2 rewrites above.

**ethical-hacker — 4 findings + 2 chained exploits, all resolved or explicitly named as residual in this revision:**
1. (HIGH) PDFium is a content-executing engine, not a passive renderer; "same trust tier as any screenshot target" was false → Decision 2 rewritten around genuine process isolation + adversarial pre-ship testing, threat-table row corrected.
2. (HIGH) `happy-dom`-then-reparse-elsewhere is a documented mXSS anti-pattern (DOMPurify maintainers' own warning); denylist vs. allowlist → Decision 1 flipped to allowlist + added the real-browser execution-canary final gate.
3. (HIGH) Confused-deputy: the "operator-trusted CLI path" framing missed that an auto-approved ACP agent session can invoke the CLI verb → Decision 5 added, named as a partially-closeable residual (skill discipline + visibility, not a hard gate — stated explicitly, not oversold).
4. (MEDIUM-HIGH, adversarial-creativity finding) T12's downstream `ux-research-agent` hand-off is the actual trifecta-completing step and has no DDR gate → added as an explicit scope boundary in § Context, flagged as needing its own follow-up before T12 ships (not silently absorbed into this document's claimed coverage).
5. No consumption contract for the sanitized SVG (future re-inlining risk) → added to Decision 1 as a closing requirement.
6. TOCTOU gap between page-count read and temp-copy read → Decision 2 now specifies a single capped read, one buffer reused throughout.

Chain 1 (confused-deputy exfil via brand import) and Chain 2 (mXSS into the main origin via the canonical DDR-141 brand-mark prior) were addressed by the Round-1 revision's Decision 1/5 changes; Round 2 (below) found the Chain-2 closure was incomplete as first written and tightened it further.

**Round 2 (2026-07-14) — confirmation pass against the Round-1 revision, not a fresh discovery pass.** Both reviewers verified each Round-1 fix against the actual revised Decision text rather than the summary.

**security-auditor Round 2 — 3 of 5 fully resolved on first pass, 2 needed one more fix (now applied):**
- RESOLVED as revised: XML processing instructions, multipart correction, cap arithmetic.
- **PARTIALLY → now RESOLVED:** the `href`-style FuncIRI value restriction had not been extended to `fill`/`clip-path`/`mask`/`filter`/`marker-*`, which take the identical `url(...)` syntax — closed by moving those attributes out of the plain presentation allowlist and into the same value-constrained bucket as `href` (Decision 1, step 3).
- **NOT RESOLVED → now RESOLVED:** the `pdf-lib` timeout was specified as a bare timer race, which cannot interrupt a synchronous CPU-bound hang on a single-threaded runtime (would freeze the whole dev-server, not just reject the request) — closed by isolating the parse in a `worker_threads` Worker with hard `.terminate()` (Decision 2, step 2).
- Soft note (host-resolver-rules doesn't cover IP-literal egress) → folded into the network-denial bullet as an explicit IP-literal fixture requirement.
- Soft note (activity-log source-path peer-sync leak) → Decision 5's visibility mitigation now records a generic kind description only, never the source path.

**ethical-hacker Round 2 — all 6 verified as PARTIALLY resolved on first pass, each tightened to a harder closure:**
1. PDFium execution: network + local-launch vectors are genuinely closed by the hardened launch config; the memory-corruption/sandbox-escape-RCE class is NOT closeable by this design and is now named as an explicit accepted residual (matching Decision 1's own house style) rather than left implicit; the adversarial fixtures are promoted from a one-time pre-ship check to a permanent regression test, with an explicit IP-literal target requirement.
2. mXSS: the allowlist+canary combination closes the class the DOMPurify warning describes, but the SMIL `attributeName`/`values` href-retargeting bypass (a real, cited, actively-exploited class — CVE-2025-66412, CVE-2025-68461) was a genuine gap the Round-1 revision's SMIL tag-allowlisting opened without saying so — closed by explicitly, permanently excluding the functional SMIL attributes rather than leaving them "just not currently on the list." The canary also gained an explicit 15s timeout and an honest note that a passive canary can't catch an interaction-only payload — which is exactly why the SMIL exclusion is load-bearing, not redundant with the canary.
3. Confused-deputy: Round 1's "not fully closeable" framing was too pessimistic for a NEW, purpose-built tool (vs. DDR-164 §F3's structural full-tool-agent residual) — replaced with a real technical gate (ACP-session-scoped proof-token requirement), carefully scoped so the legitimate plain-terminal power-user path is unaffected.
4. T12 scope boundary: the DDR's own text was honest, but the PLAN didn't enforce it — fixed by adding an explicit `T12a` DDR-gate task to the plan (mirroring T9/T14's pattern), not just DDR prose.
5. Consumption contract: upgraded from a written clause to a written clause PLUS a permanent grep-based regression test requirement, given this codebase's own documented history of exactly this class of prose-only convention drifting (CLAUDE.md's runtime-state taxonomy).
6. TOCTOU: the remaining single-`open()`-can-still-race-a-symlink gap (unavoidable in absolute terms without an attacker who already has local code execution, at which point they have easier paths) is closed as far as practically achievable via `realpath()`-then-open with symlink-component rejection, and the residual is named rather than left silent.

**Net result:** every Round-1 AND Round-2 finding now has either a concrete, specific technical closure in this document, or is named as an explicit, bounded, accepted residual — none are left as vague reassurance. Status flips to Accepted on that basis. The newly-specified mechanisms (worker-thread isolation, the ACP-session proof-token gate, the permanent regression-test trio) are narrow, well-defined implementation tasks for T10 — proportionate to verify at implementation time rather than requiring a further design-stage round.
