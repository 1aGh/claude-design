# DDR-168 — ACP session always uses Maude's bundled `maude` CLI + `design`/`flow` plugins, never a disk-installed version

**Status:** accepted
**Date:** 2026-07-14
**Supersedes in part:** [DDR-143](DDR-143-acp-session-scoped-plugin-auto-bootstrap.md) Decision 3 ("no-op for power users, hard" — a `scanPlugins()` hit now no longer skips injection); [DDR-166](DDR-166-zero-terminal-acp-cold-start.md) Decision 1 ("appended, not prepended … a user's own newer global `maude` still wins on precedence" — the bundled directory is now prepended instead). Every other decision/guard in both DDRs is unchanged and reaffirmed below.
**Relates:** [DDR-062](DDR-062-plugins-reach-executable-logic-via-maude.md) (`maude design <verb>` convention the plugin markdown depends on matching the CLI's actual flags/behavior), [DDR-123](DDR-123-acp-chat-runs-on-users-claude-cli-subscription.md)/[DDR-129](DDR-129-desktop-acp-adapter-js-closure-not-native-binary.md) (out of scope — the Anthropic `claude` CLI itself is a separate axis, untouched here), [DDR-125](DDR-125-acp-multichat-parallel-and-security-posture.md)/[DDR-144](DDR-144-bundled-screenshot-engine-agent-browser-headless-shell.md) (auto-approve envelope + `settingSources` narrowing this change composes with but does not widen), [DDR-045](DDR-045-real-disk-path-resolution-for-compiled-dev-server.md) (release-locked artifact resolution precedent).

## Context

Every Maude Desktop release compiles a version-matched `maude` CLI from `cli/bin/maude.mjs` and stages the `design`/`flow` plugin markdown trees, both sourced from the exact same working-tree commit as the rest of the app (`apps/desktop/scripts/build-cli-binary.mjs` + `stage-resources.mjs`). Despite that, two pieces of shipped/mid-flight logic let a **disk-installed** version win over the bundled copy inside the ACP chat panel specifically:

1. `plugin-bootstrap.ts`'s `computeSessionPlugins()` (DDR-143 Decision 3) skipped injecting the bundled `design` plugin whenever `scanPlugins()` found it already installed/enabled on the user's disk (`~/.claude/plugins/installed_plugins.json` or `settings.json` `enabledPlugins`).
2. `sidecar.rs`'s `spawn_server()` (DDR-166 Decision 1 / T0b) appended the bundled `maude` CLI's narrow `bin-link/` PATH directory to the sidecar child's PATH, so a user's own newer global `maude` (`npm i -g @1agh/maude`) won PATH-lookup precedence.

Both were deliberate at the time (respect what a power user already has). The repo owner's conclusion: since every release ships an internally-consistent, release-matched `maude` CLI + plugin set — the one thing actually tested against that release's plugin markdown — the ACP session should always use it, never defer to or even check disk state. **This applies only inside Maude Desktop's own ACP chat panel.** A power user running Claude Code directly in their own terminal (a separate session, not spawned by Maude Desktop) still manages their own plugin/CLI versions themselves.

**Explicitly out of scope:** the Anthropic `claude` CLI itself (`probe.ts`'s `resolveClaudePath()`) is untouched — DDR-123/DDR-129's "always drive the user's own `claude`, never bundle/embed it" stands unmodified. This DDR is only about Maude's *own* `maude` CLI and the `design`/`flow` plugin bundles.

## Decision 1 — PATH: prepend the bundled `maude` directory instead of appending it

`sidecar.rs::spawn_server()` now prepends `bin-link/` (the narrow, single-binary directory `stage_bundled_cli_link()` stages — unchanged) ahead of the resolved login-shell PATH, instead of appending it. The bundled `maude` now wins an unqualified PATH lookup for every child the sidecar spawns (in particular the ACP-spawned `claude`'s Bash-tool shell-outs to `maude design <verb>`, per DDR-062), regardless of what else is earlier in the user's own shell PATH.

This is a **position** change only, not a **breadth** change. The shadow-directory risk DDR-166 closed (a same-user attacker shadowing every name in a shared multi-binary directory like `Contents/MacOS`) is about which directory gets exposed for unqualified lookup — `bin-link/` still contains exactly one entry (`maude`), so prepending it adds no new name a same-user attacker could plant and shadow that wasn't already exposed by the append form. The accepted residual is narrower: prepending now means the bundled `maude` also outranks a locked-down/enterprise-pinned `maude` earlier in that same PATH — but only for dispatch *inside the sidecar's own spawned children*, never the user's system-wide PATH or shell.

## Decision 2 — Plugin injection: unconditional, no more `scanPlugins()` no-op gate

`plugin-bootstrap.ts`'s `computeSessionPlugins()` no longer skips injecting the bundled `design` plugin dir when `scanPlugins()` reports it already installed on disk. Every native/bundle-context session (guard #4 unchanged) with a resolved bundled dir gets the bundled copy injected via `_meta.claudeCode.options.plugins`, full stop. `resolveSessionPlugins()` no longer calls `scanPlugins()` for this purpose (`readiness.ts` keeps its own independent call for its own UI row — unaffected).

This directly reverses DDR-143 Decision 3's stated intent. That reversal is deliberate, not an oversight — Decision 3 optimized for "never double-register," a concern this DDR closes a different way (Decision 3 below), not by continuing to skip.

## Decision 3 — Close the double-registration risk structurally: force off any natively-loaded copy of the same plugin id

Removing the no-op gate reopens a real risk BREAKER flagged in the debate that grounded this plan: a power user who *also* has `design@maude` enabled at the `~/.claude` **user** level would get it loaded from two sources at once, since `bridge.ts`'s `newSessionParams()` unconditionally keeps `settingSources: ['user']` in scope (DDR-144 guard #6, for unrelated confused-deputy reasons — that scope stays, it's not being narrowed further).

Fix: whenever `newSessionParams()` is carrying a non-empty `plugins` array (i.e., Maude is actually injecting a bundled copy), it also sets `options.settings = { enabledPlugins: { 'design@maude': false } }` in the same `_meta.claudeCode.options` object. This is confirmed sound against the actual installed adapter/SDK source, not just `.d.ts` doc comments:

- `node_modules/.pnpm/@agentclientprotocol+claude-agent-acp@0.57.0.../dist/acp-agent.js:2803` spreads `...userProvidedOptions` (carrying `_meta.claudeCode.options`) into the SDK `query()` options, and `settings` is not among the fields the adapter overrides afterward (only `cwd`/`mcpServers`/`env`/etc. are) — `_meta.claudeCode.options.settings` reaches the SDK untouched, exactly like `plugins` already does per DDR-143.
- The installed SDK's `sdk.d.ts:1831` documents `options.settings` loading into the **"flag settings"** layer, "highest priority among user-controlled settings" (precedence `user < project < local < flag < policy`).
- `sdk.d.ts:5193`'s `Settings.enabledPlugins` doc comment gives the exact worked example: "to disable a plugin that project settings enable, set it to `false` in `.claude/settings.local.json`" — the flag tier does the same thing one level higher. Setting `enabledPlugins: { 'design@maude': false }` in `options.settings` deterministically overrides a `true` set at the user tier.

Set ONLY when `plugins` is actually non-empty — never unconditionally — so the override is absent (and meaningless) on the npm/web path where `plugins` is always empty, keeping that path's behavior unchanged. `settingSources: ['user']` (DDR-144 guard #6) stays exactly as-is; this is additive, not a replacement.

**Named, accepted residual — the guard is keyed to the literal id `design@maude`, not to "any natively-loaded copy of this plugin's content."** `scanPlugins()` (`readiness.ts`) has, since DDR-143, only ever detected `design@maude`/`flow@maude` by that exact marketplace-qualified id string — a Claude Code plugin registered under a *different* local marketplace alias (e.g. a contributor's own `/plugin marketplace add /path/to/maude` registered as something other than literally `maude`, which Claude Code's `extraKnownMarketplaces` allows freely) was never detected by `scanPlugins()` and so was never protected by DDR-143's original no-op gate either — that gate skipped injection only on an exact `design@maude` scan hit, so a differently-aliased copy already double-loaded alongside the bundled injection *before* this DDR. This DDR does not widen that pre-existing gap; it also does not close it. For the one scenario DDR-143's gate actually targeted — a user with `design@maude` (the real, canonical marketplace id) enabled — Decision 3's guard is now strictly more robust than the old scan-timing-dependent no-op (it holds even if `scanPlugins()`'s registry read fails or races). The differently-aliased case remains covered only by the `MAUDE_NO_PLUGIN_BOOTSTRAP=1` escape hatch (Decision 4) — anyone doing local-marketplace-alias plugin development against the ACP panel should set it, and Task 8's `CLAUDE.md` note says so explicitly.

**Correction after empirical verification (below): the `enabledPlugins:false` override's actual causal contribution to "no double-registration" is smaller than the reasoning above implies.** The SDK/adapter source citations are accurate (the override genuinely rides the wire unclobbered), but live testing against the real installed `claude` CLI shows Claude Code's own plugin loader *already* gives a `--plugin-dir`-injected local plugin unconditional precedence over a same-named `settingSources`-loaded plugin — no duplicate commands, no duplicate `SessionStart` hook firing, and the injected copy's content (not the natively-loaded one's) is what's actually active, **identically whether the override is present or absent**. The override is not harmful and remains correctly scoped (SDK-documented mechanism, present only when `plugins` is non-empty) — kept as defense-in-depth per the SDK's own documented precedence semantics, in case a future adapter/SDK/CLI version's collision-resolution behaves differently than what's empirically observed today. But the concrete "hooks fire twice" impact this decision's earlier text warned about did not reproduce.

## Decision 4 — The `MAUDE_NO_PLUGIN_BOOTSTRAP=1` opt-out remains the local-plugin-dev escape hatch

BREAKER's other concern in the debate — that always-bundled would break this repo's own "test local plugin edits via Maude Desktop's ACP panel" dogfooding path — turns out to already be solved: `MAUDE_NO_PLUGIN_BOOTSTRAP=1` (the pre-existing hard opt-out in `isNativePluginContext()`) reverts to the pre-DDR-143 detect-and-guide posture entirely, letting a contributor's own marketplace-pointed-at-working-tree install load natively instead. It needed a documented pointer so it isn't a silent trap — added to `CLAUDE.md` § "Working on plugin internals locally".

## Guards preserved (unchanged by this DDR)

- Subscription/ToS (DDR-123): `scrubAgentEnv` + `CLAUDE_CODE_EXECUTABLE` pin untouched.
- No environment mutation (DDR-126): still session-scoped `_meta` + a bundled read-only dir; no `~/.claude` write, no package manager, no network.
- Native-only gate (DDR-143 guard #4): unchanged — the web `maude design serve` path still injects nothing.
- Auto-approve envelope (DDR-125 F2): not widened — this changes *which copy* of an already-in-scope plugin loads, not the trust boundary.
- `settingSources` breadth (DDR-144 guard #6): unchanged, narrowed to `['user']` on every session; the new `enabledPlugins:false` override composes with it rather than replacing it.
- Adapter-internal contract fragility (DDR-143 guard #7): the same style of upgrade-guard test now also covers `options.settings` presence, mirroring the existing `plugins` guard.
- Auditability (DDR-143 guard #8): unchanged — injected plugin paths are still recorded as a `role:'bootstrap'` transcript entry.

## Rejected

- **New user-facing toggle for "prefer disk vs. bundled".** Rejected per the grounding debate's SHIPPER synthesis — adds a support/documentation surface for a distinction only power users would even notice, when the release-matched bundle is strictly the better default for 100% of users, power or not.
- **Scan-based suppression heuristics (e.g., version-compare the disk copy against the bundle and only override when older).** Rejected — adds real complexity (a version-comparison surface, a new failure mode when the comparison itself errors) for a benefit ("let a genuinely newer disk copy win") the repo owner explicitly decided against: the bundle is what shipped, tested, and is documented for this release; that should not be silently second-guessed at runtime.

## Security review

`security-auditor` + `ethical-hacker` ran against the actual T-task diff (`sidecar.rs`, `plugin-bootstrap.ts`, `bridge.ts`, `readiness.ts`), per this repo's standard practice for ACP-surface changes.

- **security-auditor: gate MET, 0 blockers.** Confirmed live against the actual installed `claude-agent-acp@0.57.0`/`claude-agent-sdk@0.3.202` source (not just doc comments): `stage_bundled_cli_link()`'s narrow single-entry directory is unchanged by the prepend/append flip (breadth vs. position — only position changed); the `enabledPlugins` override is derived entirely from Maude's own code with no served-project input reachable (`settingSources:['user']` still excludes `project`/`local`); the native/bundle-only gate and web-path no-op are byte-identical; the auto-approve envelope (DDR-125 F2) is unwidened — this changes which artifact backs an already-in-scope plugin id, not the trust boundary.
- **ethical-hacker: initially not sound to proceed, 2 blockers.** (1) The `enabledPlugins` guard is a hardcoded literal (`'design@maude'`), not derived from what's actually injected — a plugin registered under a *different* local marketplace alias than the canonical `maude` isn't caught by it. Investigated and found to be a **pre-existing limitation** of `scanPlugins()`'s exact-id detection (present since DDR-143, not introduced here) rather than a new regression this diff opens — documented explicitly above as a named, accepted residual rather than left as an overclaim. (2) `stage_bundled_cli_link()`'s `remove_file()` + `symlink()` sequence is a TOCTOU: a transient window where `bin-link/maude` doesn't exist, which an in-flight ACP-spawned `claude`'s own PATH lookup could race during a sidecar respawn. **Fixed** — the function now symlinks to a per-process temp name and `rename()`s atomically over the target, closing the window (see Task 2 / Decision 1 code).

Both fixes landed in this diff before merge; the alias-mismatch item is a documented residual (above), not a code fix, matching this repo's own "named, accepted residual" precedent (e.g. DDR-166's Scenario B). Re-verification round confirmed both fixes and the residual disposition, with one additional non-blocking follow-up: the `enabledPlugins` literal in `bridge.ts` is hand-maintained, not derived from the injected plugin set — re-enabling `flow@maude` injection later (a change `plugin-bootstrap.ts`'s own comment calls "a one-line addition") does NOT automatically extend the guard, and no test currently catches that drift. Flagged with an inline landmine comment at the exact line in `bridge.ts`; currently unreachable since flow injection stays off (unrelated, pre-existing 2026-07-03 decision), not a blocker for this DDR.

## Empirical verification (2026-07-14, this session, tested directly against real binaries — not just source/doc-comment reading)

Both mechanisms this DDR changes were live-tested end-to-end, mirroring DDR-166's own precedent of empirically verifying design-stage claims before treating them as proven.

**Plugin-injection precedence (Decisions 2/3) — tested against the real, signed-in, installed `claude` 2.1.207 CLI, no Tauri/desktop build needed.** Built a sandboxed `CLAUDE_CONFIG_DIR` fixture (throwaway temp dir, never the developer's real `~/.claude`) with a genuinely working local-directory marketplace registering `design@maude` — confirmed via `claude plugin list` → `✔ enabled`, not merely a hand-written registry file that might silently fail to resolve. The natively-loaded copy carried a uniquely-named marker command absent from the bundled copy, so the raw `stream-json` `system:init` event's `slash_commands` array (read directly off the wire, before any client-side UI dedup) could prove *which* copy's content actually won, not just whether a name collided:

| Run | `--plugin-dir` injection | `enabledPlugins:false` | Total commands | Marker present | `design:edit` occurrences | `SessionStart` hooks fired |
|---|---|---|---|---|---|---|
| 1 | no | n/a | 69 | **yes** (native copy loaded) | 1 | 1 |
| 2 | yes | no | 68 | no (bundled copy won) | 1 | 1 |
| 3 | yes | yes | 68 | no (bundled copy won) | 1 | 1 |

Run 1 validates the fixture methodology (marker genuinely shows up when only the native copy loads — the fixture isn't silently failing). Runs 2 and 3 are identical: injecting the bundled copy alongside a genuinely-active native copy of the same id produces **no duplicate commands, no duplicate `SessionStart` hook execution, and the bundled copy's content wins** — regardless of whether the `enabledPlugins:false` override is present. This is the source of the "Correction after empirical verification" note under Decision 3 above: Claude Code's own `--plugin-dir` precedence, not our override, is what's actually preventing double-registration in this configuration.

**PATH precedence (Decision 1) — required a real built `.app`, since `stage_bundled_cli_link()` only engages when a compiled `maude` binary is staged next to the running executable (never true under `tauri dev`).** Built the debug bundle (`pnpm test:e2e:desktop:build`), then launched it directly (no WebDriver needed for this check) with two env-var-only sandbox mechanisms — neither is a new debug backdoor, both are real vars the app already honors: `SHELL` pointed at a throwaway script that hands `resolve_login_path()` a fully controlled fake login-shell PATH containing a decoy `maude` (`echo "DECOY-MAUDE-NOT-BUNDLED"`) ahead of `/usr/bin:/bin`; `MAUDE_PROJECT_ROOT` pointed at the repo's own e2e fixture project so no onboarding flow blocks boot. Confirmed via the sidecar's own `[maude] sidecar PATH ← login shell (5 entries)` log line that the fake PATH was genuinely read (not silently ignored), then (via a temporary, since-reverted `eprintln!` immediately before the `command.env("PATH", …)` call — never committed) captured the exact final PATH string the sidecar constructs:

```
/Users/…/Caches/com.maude.app.e2e/bin-link:/tmp/maude-decoy-bin.XXXXXX:/usr/bin:/bin:/usr/sbin:/sbin
```

`bin-link` (the bundled `maude` symlink's directory) is first, the decoy directory second. Re-ran `command -v maude` under this exact PATH string in a real shell (not just visual inspection of the string) — resolves to `bin-link/maude`, a real symlink into `Maude.app/Contents/MacOS/maude`; executing it runs the genuine compiled bundle binary, not the decoy script. This is the direct, load-bearing proof that a same-user attacker (or an old `npm i -g @1agh/maude`) earlier on PATH cannot win PATH-lookup precedence inside the sidecar's own spawned children after this DDR, closing the loop the dev-server-boot smoke test (which hit an unrelated, pre-existing `css-tree` bundling crash in this session's e2e build — orthogonal to this diff, not investigated further here) could not reach.

An unrelated dev-server crash was hit and worked around during this verification (`Cannot find module '../data/patch.json'` — `css-tree`'s vendored data file not resolving inside the compiled `maude-server` binary). Not caused by, or related to, this diff's four touched files; not fixed here — flagged as a separate, pre-existing issue worth its own investigation.

### Verification-methodology limits (surfaced by a `/flow:done` code-review round against the committed diff, not merely a rubber-stamp)

The empirical verification above is real and load-bearing, but it has a scope this DDR should state plainly rather than let the "0 blockers, always the bundled copy" framing overclaim:

- **The "no double-registration" result is a one-time observation of an undocumented third-party (Claude Code CLI) precedence behavior, in one configuration, on `claude` 2.1.207 — not a regression-tested guarantee.** `acp-session-plugins.test.ts`/`acp-plugin-bootstrap.test.ts` assert wire *shape* only (`_meta.claudeCode.options.plugins`/`.settings` present, adapter source still spreads `...userProvidedOptions`, SDK `.d.ts` still declares the fields) — none of them spin up a real session and assert "no duplicate commands / hooks / MCP spawn." A future `claude` CLI update (entirely outside Maude's own release cadence, per DDR-123's "drive the user's own installed CLI") that changes how Claude Code resolves a plugin-id collision would silently reopen double-registration for a power user with `design@maude` natively installed, with **zero test failure anywhere** to catch it. A real CI-level regression test isn't practically buildable today (it would need a real authenticated `claude` CLI in CI, which DDR-123's own "never manage the user's Anthropic credentials" posture rules out) — tracked as an open, accepted verification gap rather than silently assumed closed.
- **Only slash-command dedup was verified — plugin *skill*/*agent* content dedup was not, and structurally can't be via the same method.** The marker-command technique works because `slash_commands` is a flat, comparable array on the wire. `design@maude` also ships skills (`design-system/SKILL.md`, `whiteboard/SKILL.md`) and subagents (the critic panel, `ux-research-agent`), which load as live model-context instructions with no equivalent visible/comparable list — if Claude Code's collision resolution operates at a coarse "supersede the whole plugin object" granularity (consistent with what was observed for commands+hooks), skills are inferred to be fine too, but that's inference from adjacent evidence, not a tested fact. Worth revisiting if a future release depends on a specific skill/agent version being the one active in a session.
- **MCP-server double-spawn is untested because there's nothing to test yet.** Neither `plugins/design` nor `plugins/flow` currently ships an `.mcp.json`/`mcpServers` block (`skipMcpDiscovery: true` on the injected config only prevents the *injected* copy from spawning its own — it says nothing about a natively-loaded copy's separate MCP-discovery path). Dormant today; **the day either plugin gains an MCP server, add a regression test asserting single-spawn under the same collision scenario Runs 2/3 above exercised for commands, before shipping** — don't lean on this DDR's "always exactly one copy" framing for MCP behavior specifically until that's verified.
- **Fixed as part of this same review round:** `readiness.ts`'s plugin-row copy originally read "Bundled with this app — **always** active in the chat session" — unconditionally, including for the alias-mismatch residual case (Decision 3's own named residual) where that claim isn't actually guaranteed. Reworded to "Bundled with this app — loads automatically in the chat session" — still accurate and reassuring for the 99% case, without affirmatively overclaiming exclusivity to the one population (a contributor with a differently-aliased local marketplace install) the code-level guard doesn't cover.

## Consequences

- A power user with an older globally-installed `maude`, or an older marketplace-installed `design@maude`, now gets the release-matched bundled copy inside Maude Desktop's ACP chat regardless — closing the "release just shipped a fix, chat still runs the stale copy" gap this DDR exists to fix.
- The one accepted residual: prepending the bin-link directory means the bundled `maude` now outranks even a locked-down/enterprise-pinned `maude` earlier on PATH, but strictly scoped to dispatch inside the sidecar's own spawned children — never the user's system-wide PATH.
- Contributors testing in-flight `plugins/design`/`plugins/flow` edits through the ACP chat panel specifically now need `MAUDE_NO_PLUGIN_BOOTSTRAP=1` set (documented in `CLAUDE.md`); testing via a separate terminal `claude` session is unaffected either way.
- `readiness.ts`'s `plugins` row detail copy needed a wording pass (Task 5 of the implementation plan) since "Auto-loaded — nothing to install" no longer implies "…because you didn't already have it."
