# DDR-172: Token-file import — mapping contract and ingestion security posture

**Status:** Draft — 2026-07-14 (design-stage, pre-code per plan `.ai/plans/feature-onboarding-and-design-system-migration.md` T11: this DDR gates all of T11's code, same discipline as T9/DDR-167 gated T10. Pending `ethical-hacker` + `security-auditor` review.)
**Extends:** [DDR-167](DDR-167-local-file-svg-pdf-ingestion-security-posture.md) (the sibling ingestion-security DDR for SVG/PDF — this DDR follows its "threat model → mitigation → named residual" structure, but covers a **structurally different** input class: structured JSON/CSS token data, not executable markup), [DDR-045](DDR-045-real-disk-path-resolution-for-compiled-dev-server.md) (real-disk-path resolution), [DDR-043](DDR-043-bias-free-design-plugin-templates.md) (no hardcoded visual defaults — the scaffold fallback path here reuses the same "neutral skeleton" posture).
**Instruments (planned, Phase 3 / T11):** `apps/studio/bin/import-tokens.sh` + `apps/studio/bin/_import-tokens.mjs` (shared pure functions) + tests; a small addition to `apps/studio/draw/palette.ts` (`rgbToOklch` — colorspace normalization, no new dependency); `cli/commands/design.mjs` verb registration. **CLI-only** — unlike T10, there is no HTTP route and no in-app upload panel for this verb (the plan's "Files to Create" list for T11 names only the CLI verb + tests). No canvas-origin route classification story applies.

## Context

Maude's only token-authoring path today is the interactive `/design:setup-ds` discovery flow, which writes `system/<ds>/colors_and_type.css` from `core/colors_and_type.css.tpl` using values chosen through the Stage 1–4 conversation. There is no way to bring in a design system a user **already has** as a file — a `tokens.json` (W3C design-tokens draft), a Style-Dictionary JSON export, or a raw CSS custom-properties file. Plan task T11 builds `maude design import-tokens` to close this gap: parse one of those three formats, map recognized token names onto Maude's documented CSS-variable contract (`--bg-*`, `--fg-*`, `--accent*`, `--border-*`, `--status-*`, `--space-*`, `--type-*`, `--lh-*`, `--radius-*`, `--shadow-*`, `--dur-*`, `--ease-*`, `--font-*` — the family-prefix contract documented in `core/colors_and_type.css.tpl` and enforced by the design-system-completeness-critic), and **scaffold or patch** the target DS accordingly, emitting a mapping report that never silently drops an unmapped token.

**Why this needs its own DDR rather than riding on DDR-167.** DDR-167 covers *byte-level* ingestion of SVG/PDF — content whose defining risk is **execution** (script, embedded actions, parser-CVE memory corruption). Token files are inert, structured data (JSON or a restricted CSS subset) with **no execution surface of their own** — the risk here is different in kind: (a) attacker-controlled *values* being written verbatim into a stylesheet that Maude's own studio-client and every canvas under the DS actually **renders live in a browser**, which is a CSS-injection question, not a script-execution one; (b) unbounded alias/reference resolution in the JSON formats (a DoS class DDR-167 doesn't have, because SVG/PDF have no analogous "resolve this name to another name in the same file" indirection); (c) the standard "parse untrusted JSON, walk keys recursively" prototype-pollution class, which is JSON-specific and absent from DDR-167's XML/binary formats. None of DDR-167's specific mechanisms (execution canary, sandboxed-render, worker-thread isolation for a parser hang) apply here in the same shape, so this DDR re-derives the threat model from scratch rather than inheriting DDR-167's mitigations by reference.

## Decision 1 — Input parsing: format-appropriate parsers, no hand-rolled CSS parser for untrusted input

**No new dependency.** `apps/studio/package.json` already depends on `lightningcss` (used today for client bundling, `apps/studio/build.ts:22`). `_import-tokens.mjs` reuses it — via its parse/visitor API, not the bundler path — to parse a **raw CSS custom-properties input file** into a `{name, value}` declaration list. This is a real, standards-compliant CSS parser, not a regex — the same reasoning DDR-167 applied to SVG (a real XML parser over a regex "sanitizer") applies here: an adversarial or merely malformed input CSS file (unbalanced braces inside a string, an escaped comment terminator, unusual nesting) can defeat a hand-rolled regex extractor in ways a real parser won't. `apps/studio/handoff.ts`'s existing `filterTokensCss()` regex extractor is a deliberate, documented exception for that file's own use case (subsetting **Maude's own, already-trusted** generated stylesheet, not parsing arbitrary external input) — that precedent does NOT extend to this feature, where the input file is, by definition, foreign.

- **W3C design-tokens** (`$value`/`$type`, optional group-level `$type` inheritance, alias syntax `{group.token.path}` inside a `$value` string) and **Style-Dictionary** (`value`/`type`, alias syntax `{group.token.path}`) are both plain JSON — parsed with the native `JSON.parse`, never `eval`/`Function`/a YAML-superset parser. No new dependency needed or wanted.
- **Byte-size cap: 2 MB** on the input file, checked before parsing (mirrors DDR-167's pre-parse cap discipline). A design-token file this size is already generous — Style-Dictionary exports for large multi-brand systems commonly run tens of KB.
- A JSON parse failure, or a CSS parse failure from `lightningcss`, is a **hard reject** with a clear "could not parse as `<format>`" error — never a silent fallback to a different format guess.

## Decision 2 — Alias/reference resolution: cycle-safe, depth-capped, same-file only

Both W3C and Style-Dictionary formats let a token's value reference another token by path (`"{color.brand.500}"`). This is genuinely useful (a `--accent-hover` alias to `--accent` should resolve), but it is also the one part of this format family with no execution-safety analogue in DDR-167 — an unbounded or cyclic resolver is a pure availability bug (stack overflow / infinite loop) waiting in untrusted input.

- **Resolution happens over an in-memory flattened token map built from THIS FILE ONLY.** An alias that doesn't resolve to a token present in the same file is left **unresolved** and the token is reported `unmapped: unresolved-alias` — the resolver never reads, requests, or opens any other file, URL, or path. This closes a "malicious token file references `$ref`/`extends`/an alias path that happens to look like a filesystem path, and a naive resolver tries to open it" class outright: the resolver's only data source is the parsed-in-memory object graph, and any `$ref`/`extends`-shaped key with a string value that isn't a same-file alias path is treated as inert data, never dereferenced as a file or network location.
- **Cycle detection via a per-resolution visited-set.** Resolving token A pushes A onto a `Set` for that resolution chain; encountering an already-visited path is a hard reject of that single token (`rejected: circular-alias`), not a crash — the rest of the file continues processing normally.
- **Max resolution depth: 16.** A chain longer than that is treated the same as a cycle (`rejected: alias-chain-too-deep`) — generous for any real-world token file (Style-Dictionary exports rarely alias more than 2–3 levels deep) while bounding worst-case work to a small constant.

## Decision 3 — Prototype-pollution-safe tree walk

Flattening the parsed JSON into `{path, value, type}` leaves requires recursing over attacker-controlled object keys. The walk explicitly **skips** any key equal to `__proto__`, `constructor`, or `prototype` at every recursion level (both when reading and when the resulting flattened map is later looked up by path) — the standard, minimal-cost mitigation for this exact "recursively walk untrusted JSON keys" shape. This is a one-line guard per recursion step, not a new dependency (`Object.create(null)` for the flattened map's storage achieves the same thing structurally and is used for the map itself).

## Decision 4 — Value-grammar allowlist: the CSS-injection closure (the load-bearing decision in this DDR)

**This is the single highest-value control in this DDR.** Unlike DDR-167's SVG/PDF (write-once artifacts referenced via `<img src>`/rasterized PNG, never inlined as live markup), a `colors_and_type.css` value written by this importer is **immediately and continuously rendered** — every canvas under the target DS, and the studio-client chrome itself if this is the active DS, loads this stylesheet live in a real browser. An attacker-controlled value is therefore a direct CSS-injection vector into a surface Maude actually renders, not a dormant file on disk.

Every value this importer is about to write is validated against an **explicit per-target-family grammar** before it touches the output file. A value that doesn't match its family's grammar is **rejected outright** (`rejected: invalid-value-shape`) — never written, never "cleaned up" or partially accepted:

| Target family | Allowed value grammar |
| --- | --- |
| `--bg-*`, `--fg-*`, `--border-*`, `--accent*`, `--status-*` (colors) | `^#[0-9a-fA-F]{3,8}$` OR `^oklch\([\d.]+%?\s+[\d.]+\s+[\d.]+(\s*/\s*[\d.]+%?)?\)$` OR `^rgba?\(\s*[\d.]+[\s,]+[\d.]+[\s,]+[\d.]+(\s*[,/]\s*[\d.]+%?)?\s*\)$` OR `^hsla?\(\s*[\d.]+\s+[\d.]+%\s+[\d.]+%(\s*/\s*[\d.]+%?)?\)$` — numeric-argument color functions only, nothing else |
| `--space-*`, `--radius-*`, `--type-*`, `--lh-*` (dimensions) | `^-?[\d.]+(px\|rem\|em\|%)$` or bare `0` |
| `--dur-*` (durations) | `^[\d.]+m?s$` |
| `--ease-*` (easing) | `^cubic-bezier\(\s*-?[\d.]+\s*,\s*-?[\d.]+\s*,\s*-?[\d.]+\s*,\s*-?[\d.]+\s*\)$` or one of the CSS easing keywords (`linear`, `ease`, `ease-in`, `ease-out`, `ease-in-out`) |
| `--font-*` (font stacks) | A comma-separated list where every entry is either a **quoted string matching `^"[A-Za-z0-9 _-]{1,64}"$`** (letters, digits, space, hyphen, underscore only — no `\`, no unescaped quote, no CSS-special characters) or one of a fixed generic-family keyword set (`serif`, `sans-serif`, `monospace`, `system-ui`, `ui-monospace`, `ui-sans-serif`, `ui-serif`, `cursive`, `fantasy`) |
| `--shadow-*` | `^(\s*-?[\d.]+px\s+){2,4}rgba?\(\s*[\d.]+[\s,]+[\d.]+[\s,]+[\d.]+(\s*[,/]\s*[\d.]+%?)?\s*\)(\s*,\s*(\s*-?[\d.]+px\s+){2,4}rgba?\([^)]+\))*$` — one or more `<offset-x> <offset-y> [<blur>] [<spread>] <rgba-color>` layers, comma-separated, no other function calls |

Every grammar is **closed under composition with itself only** — no grammar admits `;`, `{`, `}`, `@`, `url(`, `expression(`, `javascript:`, `\`, or an unescaped quote, because none of the permitted constructs (numbers, units, named color functions with numeric arguments, a bounded charset for font names) can produce those characters. This is what closes CSS injection: even a value that survives JSON/CSS parsing intact cannot smuggle a rule terminator, an `@import`, or a `url()` reference into the output file, because nothing that shape is in any grammar. `var(--other-token)` references **from the input file** are deliberately **not** in any grammar and are rejected — an imported token file may reference its OWN other tokens via the format's own alias syntax (Decision 2), resolved to a concrete value before this validation step ever runs; it may not reference an arbitrary Maude-side `--custom-property` name that could later be redefined out from under it.

## Decision 5 — Name-to-variable mapping: heuristic, never silent

There is no reliable way to know that a foreign token author's `"Surface/BG/0"` means the same thing as Maude's `--bg-0` without either (a) a rigid required input schema (defeats the point of importing an *existing* system) or (b) heuristic name matching that can be wrong. This DDR chooses (b), with the failure mode made **loud, not silent**:

- The importer normalizes each flattened token's path (lowercase, delimiter-collapse on `/`, `.`, `-`, `_`, camelCase-split) and matches it against a curated table of recognized naming patterns per target family (e.g. `bg|background|surface` + a ladder-position cue `0|base|default|page` → `--bg-0`; `accent|brand|primary` (when `$type`/`type` is `color`) → `--accent`; `space|spacing|gap` + a numeric scale index → the nearest `--space-N` slot; full table lives in the implementation, not duplicated here — it is data, not a security control).
- **A token whose path matches no recognized pattern is `unmapped`** — never guessed, never force-mapped to "the closest thing." It is written to the mapping report (`{path, detectedType, targetVariable: null, status: "unmapped"}`) and otherwise ignored.
- **A token that maps to a family, but whose value fails Decision 4's grammar, is `rejected`** — reported with the specific grammar violation, never partially applied.
- **A token that maps AND validates, but whose target variable has no existing declaration in the target `colors_and_type.css`** (e.g. the target DS never adopted the `status` family) is `skipped` by default — the importer does not force-insert new declarations into a hand-authored file structure unless the caller passes `--force-insert`.
- Only tokens that are `mapped` land in the output. The mapping report — printed to stdout and, matching this codebase's existing report-artifact convention, written to `<designRoot>/_history/_system/import-tokens-report-<ts>.json` — is a **complete accounting of every input token's disposition**, not just the successes. This is the concrete mechanism behind the plan's "unmapped tokens surfaced, never silently dropped" requirement — a report file, not a prose promise.

## Decision 6 — Colorspace normalization: convert when confident, report when not

The target DS's `config.json` declares `colorSpace` (`oklch | hsl | hex | lab`, default `oklch` per the completeness-critic's V2 check). A mapped color token whose input format doesn't match:

- **hex/rgb → oklch**: converted using a new `rgbToOklch()` added to `apps/studio/draw/palette.ts` (the exact inverse of the existing `oklchToRgb`, same Björn Ottosson constants, same file — no new module, no new dependency). `parseColor()` (already exported from `palette.ts`) handles the hex/rgb parse side.
- **oklch input, oklch target**: passed through via the existing `parseOklch`/re-serialize, value-grammar-validated as usual.
- **hsl or lab input, when the target `colorSpace` is NOT the same format**: conversion is **not attempted** — DDR-172 does not add an hsl↔oklch or lab↔oklch converter in this pass. The token is reported `skipped: unsupported-colorspace-conversion (hsl→oklch)` rather than silently passed through as a mismatched value or silently dropped. This is a real, named capability gap (matching this project's own "accepted residual, named explicitly" convention) — extending conversion coverage is a small, low-risk follow-up, not a blocker for T11.

## Decision 7 — Write-path: atomic, contained, non-destructive

- **Patch mode** (default, target DS already exists): the importer reads the CURRENT `system/<ds>/colors_and_type.css` at the path from `config.json designSystems[].tokensCssRel`, and for each `mapped` + grammar-valid token whose target variable has an existing `--name: ...;` declaration, replaces ONLY that declaration's value via a targeted, closed-vocabulary regex (`/^(\s*--name\s*:\s*)([^;]+)(;.*)$/m`-shaped, operating only on the fixed set of family-prefixed names this DDR's grammar table covers) — mirroring the same "regex over a known, closed vocabulary, not general CSS parsing" house style `design-system-keeper`'s token-usage audit and `handoff.ts`'s `filterTokensCss()` already use for **Maude's own trusted output files** (as opposed to Decision 1's parser choice for the untrusted *input* side). Everything else in the file — comments, structure, un-mapped declarations, the `@media (prefers-reduced-motion)` block — is left byte-for-byte untouched.
- **Realpath containment**, mirroring DDR-167 Decision 3: the resolved write path must resolve inside `<designRoot>/system/` before any write, independent of what `config.json` claims — defense in depth against a corrupted or malicious `config.json` pointing `tokensCssRel` somewhere unexpected.
- **Atomic write**: write to a temp file in the same directory, then `renameSync` over the target — never a partial/truncated file on a crash mid-write, same discipline as the concurrent `stage_bundled_cli_link()` symlink-swap fix elsewhere in this codebase.
- **Scaffold mode** (`--new-ds <name>`, no existing DS of that name): reuses the EXISTING `scaffold-design.ts` scaffolding path to create the minimal file skeleton first (same neutral, no-visual-defaults posture as `--no-discovery` mode, DDR-043), then applies the identical patch pass from above onto the freshly scaffolded file. Only this mode touches `config.json` — a read-merge-write that adds one entry to `designSystems[]` and never overwrites unrelated keys (no full-file replace).
- **Backup**: the pre-patch file content is preserved in the same `_history/_system/` report directory alongside the mapping report (not a `.bak` sibling next to the live file, keeping the working tree clean) — a manual revert path if a heuristic mapping produces an undesired result.

## Decision 8 — CLI-verb reachability: narrower residual than DDR-167 Decision 5, no proof-token gate

DDR-167 Decision 5 added an ACP-session-scoped proof-token gate for `import-asset` because that verb writes **arbitrary local file bytes** (an entire document/photo) into the peer-synced `assets/` tree — a high-bandwidth exfiltration channel a prompt-injected agent session could exploit indistinguishably from a legitimate import. `import-tokens` is a **different shape of risk**:

- The only data that can reach the output file is a value that (a) matched a recognized token-family **name pattern** and (b) passed that family's narrow **value grammar** (Decision 4). This is a low-bandwidth, structurally-typed channel (a handful of numbers, a color, a short font-family string) — categorically smaller than "an entire file's bytes/rendered pages," and specifically NOT capable of carrying arbitrary attacker-chosen text (font-family values are charset-restricted to `[A-Za-z0-9 _-]`, colors are numeric-argument-only).
- There is no HTTP route and no in-app panel for this verb (Decision, Instruments header) — the only entry point is the plain CLI, identical in shape to every other `maude design <verb>` today.
- **Named residual, not a silent omission**: a prompt-injected ACP agent session could still invoke `maude design import-tokens <path> --new-ds <name>`, and the resulting DS name/description string (free text, not value-grammar-constrained the way token values are) could carry attacker-chosen content into a visible, peer-synced file. This is accepted as a bounded residual for the same reason DDR-167 Decision 5 accepts its own human-in-the-loop residual: the output is user-visible (a new design system appearing in the canvas list) and the blast radius is a cosmetic string, not code execution or bulk file exfiltration. If a future revision of this feature adds an HTTP route or an in-app panel (mirroring T10's Brand-upload panel), THAT change must re-derive this decision — the "narrower than DDR-167" reasoning is specific to the CLI-only, value-grammar-bounded shape this DDR describes now.

## Threat model summary

| Threat | Closed by |
| --- | --- |
| CSS injection via token value (rule termination, `@import`, `url()`, `expression()`) reaching a live-rendered stylesheet | Per-family value-grammar allowlist, closed under composition (Decision 4) |
| Unbounded/cyclic alias resolution (`{a} → {b} → {a}`) causing a hang | Visited-set cycle detection + max depth 16 (Decision 2) |
| Token file referencing an external `$ref`/`extends`/file path, importer obligingly reads it | Resolver only ever reads the in-memory parsed object graph of the ONE input file — never dereferences a string as a path/URL (Decision 2) |
| Prototype pollution via recursive walk of untrusted JSON keys | `__proto__`/`constructor`/`prototype` key skip at every recursion level (Decision 3) |
| Malformed/adversarial raw-CSS input defeating a hand-rolled extractor | Real parser (`lightningcss`, already a dependency) instead of regex, for the untrusted input side only (Decision 1) |
| Oversized input file (memory/DoS) | 2 MB pre-parse cap (Decision 1) |
| Silent semantic mis-mapping (a foreign token silently becomes the wrong Maude variable) | Unmapped/rejected/skipped tokens are reported, never guessed (Decision 5) |
| Colorspace mismatch producing a value inconsistent with `config.json colorSpace` | Convert when a converter exists (hex/rgb→oklch); report `unsupported-colorspace-conversion` otherwise, never silently pass through (Decision 6) |
| Corrupted/malicious `config.json tokensCssRel` pointing the write outside the design root | Realpath containment assertion before write (Decision 7) |
| Partial/truncated file on a crash mid-write | Atomic temp-file + rename (Decision 7) |
| Destructive overwrite of a hand-authored token file | Targeted single-declaration regex replace over a closed vocabulary, not a full-file rewrite; pre-patch content backed up alongside the report (Decision 7) |
| Confused-deputy: ACP-agent-invoked import of an unintended local file | **Named, accepted residual** — narrower than DDR-167's because the reachable output is value-grammar-bounded (token values) or a cosmetic string (new-DS name/description), not arbitrary bytes; no technical gate added (Decision 8) |

## Consequences

- Net-new parsing/mapping/validation code (`_import-tokens.mjs`) needs test coverage across all three input formats plus the negative cases in the threat table above (a CSS-injection-shaped value, a cyclic alias, a `__proto__`-keyed object, an oversized file, a malformed JSON/CSS file).
- No new npm dependency — `lightningcss` (already present) covers the one format that needed a real parser; JSON formats use native `JSON.parse`.
- One small, low-risk addition to `apps/studio/draw/palette.ts` (`rgbToOklch`) — pure function, same file/style as its existing inverse.
- The value-grammar table (Decision 4) is the single control this DDR treats as load-bearing; any future change that adds a new target CSS-variable family (e.g. a new token kind) MUST add a corresponding grammar row here before the importer is allowed to write to it — an ungoverned family is a `skipped`, not a silent pass-through.
- Colorspace conversion coverage (hsl/lab → oklch) is an explicitly named gap, not silently absorbed — a reasonable, low-priority follow-up.
