# DDR-172: Token-file import — mapping contract and ingestion security posture

**Status:** Accepted — 2026-07-14 (design-stage, pre-code per plan `.ai/plans/feature-onboarding-and-design-system-migration.md` T11: this DDR gates all of T11's code, same discipline as T9/DDR-167 gated T10. `ethical-hacker` + `security-auditor` ran two full rounds — Round 1 against the initial draft (3 blockers, 6 warnings from security-auditor; 2 HIGH, 3 MEDIUM, 1 LOW from ethical-hacker, plus convergent findings from a third, accidental duplicate pass), Round 2 confirming every fix against the revised text and surfacing a handful of LOW/LOW-MED residuals, all closed. See § Security review below.)
**Extends:** [DDR-167](DDR-167-local-file-svg-pdf-ingestion-security-posture.md) (the sibling ingestion-security DDR for SVG/PDF — this DDR follows its "threat model → mitigation → named residual" structure, but covers a **structurally different** input class: structured JSON/CSS token data, not executable markup), [DDR-045](DDR-045-real-disk-path-resolution-for-compiled-dev-server.md) (real-disk-path resolution), [DDR-043](DDR-043-bias-free-design-plugin-templates.md) (no hardcoded visual defaults — the scaffold fallback path here reuses the same "neutral skeleton" posture).
**Instruments (planned, Phase 3 / T11):** `apps/studio/bin/import-tokens.sh` + `apps/studio/bin/_import-tokens.mjs` (shared pure functions) + tests; a small addition to `apps/studio/draw/palette.ts` (`rgbToOklch` — colorspace normalization, no new dependency); `cli/commands/design.mjs` verb registration. **CLI-only** — unlike T10, there is no HTTP route and no in-app upload panel for this verb (the plan's "Files to Create" list for T11 names only the CLI verb + tests). No canvas-origin route classification story applies.

## Context

Maude's only token-authoring path today is the interactive `/design:setup-ds` discovery flow, which writes `system/<ds>/colors_and_type.css` from `core/colors_and_type.css.tpl` using values chosen through the Stage 1–4 conversation. There is no way to bring in a design system a user **already has** as a file — a `tokens.json` (W3C design-tokens draft), a Style-Dictionary JSON export, or a raw CSS custom-properties file. Plan task T11 builds `maude design import-tokens` to close this gap: parse one of those three formats, map recognized token names onto Maude's documented CSS-variable contract (`--bg-*`, `--fg-*`, `--accent*`, `--border-*`, `--status-*`, `--space-*`, `--type-*`, `--lh-*`, `--radius-*`, `--shadow-*`, `--dur-*`, `--ease-*`, `--font-*` — the family-prefix contract documented in `core/colors_and_type.css.tpl` and enforced by the design-system-completeness-critic), and **scaffold or patch** the target DS accordingly, emitting a mapping report that never silently drops an unmapped token.

**Why this needs its own DDR rather than riding on DDR-167.** DDR-167 covers *byte-level* ingestion of SVG/PDF — content whose defining risk is **execution** (script, embedded actions, parser-CVE memory corruption). Token files are inert, structured data (JSON or a restricted CSS subset) with **no execution surface of their own** — the risk here is different in kind: (a) attacker-controlled *values* being written verbatim into a stylesheet that Maude's own studio-client and every canvas under the DS actually **renders live in a browser**, which is a CSS-injection question, not a script-execution one; (b) unbounded alias/reference resolution in the JSON formats (a DoS class DDR-167 doesn't have, because SVG/PDF have no analogous "resolve this name to another name in the same file" indirection); (c) the standard "parse untrusted JSON, walk keys recursively" prototype-pollution class, which is JSON-specific and absent from DDR-167's XML/binary formats. None of DDR-167's specific mechanisms (execution canary, sandboxed-render, worker-thread isolation for a parser hang) apply here in the same shape, so this DDR re-derives the threat model from scratch rather than inheriting DDR-167's mitigations by reference.

## Decision 1 — Input parsing: format-appropriate parsers, no hand-rolled CSS parser for untrusted input

**No new dependency.** JSON formats use the native `JSON.parse`, never `eval`/`Function`/a YAML-superset parser.

**Round-1 revision (security-auditor W5):** the initial draft proposed reusing `lightningcss` (`apps/studio/package.json`) for the raw-CSS-custom-properties input format. That dependency is a native napi addon exercised today only at **build time** (`apps/studio/build.ts:22`) — this verb is CLI-only and ships inside the `bun --compile` standalone binary end users install, and its runtime availability inside that compiled binary was never verified. This is exactly the native-addon/`bun --compile` risk class DDR-070/DDR-167 both deliberately avoid (DDR-167 rejected `pdfjs-dist` + `node-canvas` for the identical reason). Rather than take on an unverified runtime dependency, `_import-tokens.mjs` parses the raw-CSS input format with a **small, purpose-built, single-pass tokenizer** — not a regex, and not a full CSS parser (which the narrow "extract `--name: value;` declarations from a `:root`/theme-selector block" task doesn't need). The tokenizer walks the input character-by-character tracking three pieces of state — brace depth, whether it is inside a quoted string (honoring `\`-escapes), and whether it is inside a `/* … */` comment — and only emits a `{name, rawValue}` pair when it sees a `--name:` at depth 1 immediately inside a selector block, up to the next unescaped, non-string, non-comment `;` or `}`. This is provably safe against the adversarial shapes a regex extractor is vulnerable to (a `}` or `;` inside a quoted string or a comment can never be mistaken for a declaration terminator, because the tokenizer tracks those states explicitly) without depending on a parser whose runtime footprint in the shipped binary is unverified.
- **W3C design-tokens** (`$value`/`$type`, optional group-level `$type` inheritance, alias syntax `{group.token.path}` inside a `$value` string) and **Style-Dictionary** (`value`/`type`, alias syntax `{group.token.path}`) are both plain JSON.
- **Byte-size cap: 2 MB** on the input file, checked before parsing (mirrors DDR-167's pre-parse cap discipline). A design-token file this size is already generous — Style-Dictionary exports for large multi-brand systems commonly run tens of KB.
- **Input-file read mirrors DDR-167 Decision 2 step 1** (security-auditor W6): `realpath()`-then-open with a symlink-substitution reject, then a single capped read into memory — the same buffer is reused for the size check and the parse; no second, independent read of the operator-given path. **Implementation-time refinement (discovered writing the T11 test suite): the symlink check is LEAF-ONLY** (the file itself, checked via `lstatSync` against the pre-resolution path — never every ancestor directory component). A whole-ancestor-chain walk was tried first and rejects nearly every real macOS path outright, because `/tmp` and `/var` are themselves OS-level symlinks (`-> /private/tmp`/`-> /private/var`) — that check would have made the mechanism unusable, not more secure. The threat this actually closes — the file getting swapped out from under this read between validation and open (check-then-read substitution) — is fully covered by a leaf check; an attacker able to plant a symlink in a PARENT directory the operator already trusts and navigated into has an easier path to the same data than racing this read, which is the identical residual DDR-167 Decision 2 step 1 already names and accepts explicitly. Not a new gap — a narrower, correct implementation of the same accepted boundary.
- A JSON parse failure, or a tokenizer parse failure on the raw-CSS format, is a **hard reject** with a clear "could not parse as `<format>`" error — never a silent fallback to a different format guess. **Parse-error messages report only structural position (byte offset, expected-vs-found token class) — never a verbatim excerpt of the input file content** (security-auditor completeness note — an error path that echoes attacker-controlled input back to the caller is a namable, avoidable micro-exfil/reflection channel, closed here by construction).

## Decision 2 — Alias/reference resolution: cycle-safe, depth-capped, same-file only, WHOLE-VALUE aliases only

Both W3C and Style-Dictionary formats let a token's value reference another token by path (`"{color.brand.500}"`). This is genuinely useful (a `--accent-hover` alias to `--accent` should resolve), but it is also the one part of this format family with no execution-safety analogue in DDR-167 — an unbounded or cyclic resolver is a pure availability bug (stack overflow / infinite loop, or — Round-1 finding below — an amplification bomb) waiting in untrusted input.

**Round-1 finding (security-auditor W1 + ethical-hacker F5, same root cause found two ways): depth+cycle bounds alone don't bound total work.** A per-*chain* visited-set with a depth cap stops infinite loops and overlong chains, but neither stops (a) a composite token with multiple alias-able sub-fields creating branching fan-out with no memoization across sibling branches, or (b) a *partial-string, multi-reference* alias form (`"value": "{a} {a}"`, a real Style-Dictionary interpolation feature) that **doubles in size per resolution level** — a billion-laughs analogue with zero cycles and no chain exceeding the depth cap. Both are closed structurally, not by a size budget, by narrowing what this importer resolves at all:

- **Only WHOLE-VALUE single-alias substitution is resolved.** A token's raw value is treated as an alias reference ONLY when the entire trimmed value is exactly one `{group.token.path}` reference — nothing else on either side. A value that merely *contains* a `{…}` span alongside other text (`"{a} solid"`, `"{a} {b}"`) is **not** treated as alias syntax at all — it is passed through unresolved, as literal text, into Decision 4's grammar validation (which will reject it, since `{`/`}` appear in no grammar). This makes each token have **at most one outgoing alias edge**, which structurally caps total resolution work at O(tokens × max depth) regardless of how many tokens reference the same target — no branching-fanout term is possible, and partial-string interpolation (the doubling mechanism) is simply not a supported feature, not a bounded one.
- **Resolution happens over an in-memory flattened token map built from THIS FILE ONLY.** An alias that doesn't resolve to a token present in the same file is left **unresolved** and the token is reported `unmapped: unresolved-alias` — the resolver never reads, requests, or opens any other file, URL, or path. This closes a "malicious token file references `$ref`/`extends`/an alias path that happens to look like a filesystem path, and a naive resolver tries to open it" class outright: the resolver's only data source is the parsed-in-memory object graph, and any `$ref`/`extends`-shaped key with a string value that isn't a same-file whole-value alias is treated as inert data, never dereferenced as a file or network location.
- **Permanent test, not prose alone (ethical-hacker F4 — DDR-167's own lesson: "policy prose alone is exactly the failure mode this codebase has already hit once").** A standing test asserts the alias-resolver module imports none of `fs`/`net`/`http`/`https`/`dns`/`child_process` — checked **both with and without** the `node:` prefix (`fs` and `node:fs` both banned; a grep scoped to only the `node:`-prefixed form is trivially evaded) — and contains no reference to the global `fetch` or `XMLHttpRequest`. *(Round-2 tightening, ethical-hacker — the original ban list covered only the `node:`-prefixed fs/net/http(s) trio and missed the unprefixed-specifier evasion, `child_process` (exfil via spawning a subprocess), and `dns`.)* Mirrors `cli/lib/plugin-cli-reachability.test.mjs`'s existing "grep the tree for a banned call shape" pattern. This is what makes the "never dereferences a path/URL" claim above an enforced invariant instead of an intention a later refactor (e.g. someone "helpfully" adding real `$ref`-file support) could silently violate.
- **Cycle detection via a per-resolution visited-set**, retained as defense-in-depth even though the whole-value-only restriction already makes a cycle the only way to loop: resolving token A pushes A onto a `Set` for that resolution chain; encountering an already-visited path is a hard reject of that single token (`rejected: circular-alias`), not a crash — the rest of the file continues processing normally.
- **Max resolution depth: 16**, and a **global resolved-value memoization cache** (resolve each distinct token path at most once, reuse the result for every other token that references it) — belt-and-braces on top of the structural fix above, and it's free: with at-most-one-outgoing-edge per token, memoization turns "N tokens each independently walking up to a 16-deep chain" into "each distinct token resolved once."

## Decision 3 — Prototype-pollution-safe tree walk, structurally depth-capped

Flattening the parsed JSON into `{path, value, type}` leaves requires recursing over attacker-controlled object keys. The walk explicitly **skips** any key equal to `__proto__`, `constructor`, or `prototype` at every recursion level (both when reading and when the resulting flattened map is later looked up by path) — the standard, minimal-cost mitigation for this exact "recursively walk untrusted JSON keys" shape. This is a one-line guard per recursion step, not a new dependency (`Object.create(null)` for the flattened map's storage achieves the same thing structurally and is used for the map itself).

**Round-1 finding (security-auditor W4): this structural walk has no depth cap of its own, independent of Decision 2's alias-depth cap.** Decision 2 bounds how deep an *alias chain* can go; it says nothing about how deep the raw *JSON object/array nesting* can go before alias resolution ever runs. A 2 MB input consisting almost entirely of deeply nested arrays (`[[[[…]]]]`) fits easily under the byte cap while nesting millions of levels deep, stack-overflowing a naive recursive flattener before Decision 2's logic is reached at all. The flatten walk therefore carries its **own** explicit recursion-depth cap — **32** — independent of and checked before any alias-resolution logic; input nested deeper than that is a hard reject (`rejected: structure-too-deep`), not a crash.

## Decision 4 — Value-grammar allowlist: the CSS-injection closure (the load-bearing decision in this DDR)

**This is the single highest-value control in this DDR.** Unlike DDR-167's SVG/PDF (write-once artifacts referenced via `<img src>`/rasterized PNG, never inlined as live markup), a `colors_and_type.css` value written by this importer is **immediately and continuously rendered** — every canvas under the target DS, and the studio-client chrome itself if this is the active DS, loads this stylesheet live in a real browser. An attacker-controlled value is therefore a direct CSS-injection vector into a surface Maude actually renders, not a dormant file on disk.

Every value this importer is about to write is validated against an **explicit per-target-family grammar** before it touches the output file. A value that doesn't match its family's grammar is **rejected outright** (`rejected: invalid-value-shape`) — never written, never "cleaned up" or partially accepted:

| Target family | Allowed value grammar |
| --- | --- |
| `--bg-*`, `--fg-*`, `--border-*`, `--accent*`, `--status-*` (colors) | `^#[0-9a-fA-F]{3}$`, `^#[0-9a-fA-F]{4}$`, `^#[0-9a-fA-F]{6}$`, or `^#[0-9a-fA-F]{8}$` (exactly the 4 valid hex lengths — see Round-1 note below) OR `^oklch\([\d.]+%? [\d.]+ [\d.]+( ?/ ?[\d.]+%?)?\)$` OR `^rgba?\( ?[\d.]+[ ,][\d.]+[ ,][\d.]+( ?[,/] ?[\d.]+%?)? ?\)$` OR `^hsla?\( ?[\d.]+ [\d.]+% [\d.]+%( ?/ ?[\d.]+%?)?\)$` — numeric-argument color functions only, nothing else, matched against a literal space character (never `\s`) wherever whitespace is structurally required (Round-2 hardening, see below) |
| `--space-*`, `--radius-*`, `--type-*`, `--lh-*` (dimensions) | `^-?[\d.]{1,6}(px\|rem\|em\|%)$` or bare `0`, AND the numeric magnitude (unit stripped) must fall in **0–512** (`--type-*`/`--lh-*`/`--radius-*`) or **0–4096** (`--space-*`, generous for a max-width-adjacent spacing token) — see Round-1 note below |
| `--dur-*` (durations) | `^[\d.]{1,6}m?s$`, magnitude bounded to **0–60000** (ms-equivalent) |
| `--ease-*` (easing) | `^cubic-bezier\(\s?-?[\d.]+\s?,\s?-?[\d.]+\s?,\s?-?[\d.]+\s?,\s?-?[\d.]+\s?\)$` or one of the CSS easing keywords (`linear`, `ease`, `ease-in`, `ease-out`, `ease-in-out`) |
| `--font-*` (font stacks) | A comma-separated list where every entry is either a **quoted string matching `^"[A-Za-z0-9 _-]{1,64}"$`** (letters, digits, space, hyphen, underscore only — no `\`, no unescaped quote, no CSS-special characters) or one of a fixed generic-family keyword set (`serif`, `sans-serif`, `monospace`, `system-ui`, `ui-monospace`, `ui-sans-serif`, `ui-serif`, `cursive`, `fantasy`). **Deliberately rejects legitimate unquoted family names** (`Arial, Helvetica`) — a known, intentional conservative restriction, not an oversight; loosening it to admit bare identifiers is a real future request but must re-derive the charset safety argument from scratch, not be waved through as a usability fix. |
| `--shadow-*` | `^( ?-?[\d.]{1,5}px ){2,4}rgba?\( ?[\d.]+[ ,][\d.]+[ ,][\d.]+( ?[,/] ?[\d.]+%?)? ?\)( ?, ?( ?-?[\d.]{1,5}px ){2,4}rgba?\( ?[\d.]+[ ,][\d.]+[ ,][\d.]+( ?[,/] ?[\d.]+%?)? ?\))*$` — one or more `<offset-x> <offset-y> [<blur>] [<spread>] <rgba-color>` layers, comma-separated; **every layer, not just the first, uses the identical strict numeric-argument rgba grammar** — see Round-1 finding directly below, this is the fix for it |

**Round-1 finding, found independently by both reviewers with a concrete PoC (security-auditor B1, ethical-hacker F1) — the original `--shadow-*` grammar was NOT airtight.** The first draft spelled out the first shadow layer numerically but let every subsequent layer use `rgba?\([^)]+\)` — `[^)]+` matches anything except a literal `)`, including `;`, `{`, `}`, `@`, `url(`, quotes, and newlines, directly contradicting this section's own closure claim. Ethical-hacker constructed a concrete value — `0px 0px rgba(0,0,0), 0px 0px rgba(0(0)` — that passes the flawed grammar (the `[^)]+` layer captures `0(0`) and writes an **unbalanced open-paren** into the stylesheet, which per CSS custom-property parsing swallows subsequent tokens — including the declaration's own terminating `;` and the enclosing block's `}` — until the next `)` or EOF, corrupting or silently dropping later declarations in a stylesheet every canvas renders live. The table above now uses the strict first-layer grammar for every layer; there is no `[^)]+`/`[^;]+` anywhere in any grammar in this DDR.

**Round-1 finding (ethical-hacker F2): grammars must never be matched with the `m` (multiline) or `s` (dotall) regex flags, and every value is hard-rejected BEFORE grammar matching unless it consists ENTIRELY of printable ASCII (`0x20`–`0x7E`).** `^`/`$` anchors are only as strong as the flags they're evaluated under — under `/m`, `^#[0-9a-fA-F]{3,8}$` would match just the first line of a multi-line value, letting `#fff\n};@import url(//evil)` sail through as `#fff`. A printable-ASCII-only pre-filter (`^[\x20-\x7E]*$`, checked before any grammar regex runs) is simpler and more complete than enumerating specific forbidden characters: it closes not just C0 controls and the literal `\n`/`\r` but every JS `LineTerminator` code point (U+2028/U+2029, which `/m` treats as line boundaries despite not being C0 controls) and every other non-ASCII whitespace/control/formatting character (U+00A0, zero-width characters, bidi-override characters) in one universal rule, rather than an enumeration a future refactor could incompletely port. Every value this DDR's grammars actually need to admit — numbers, units, hex digits, named color-function syntax, a bounded charset of font-name characters — is already pure ASCII, so this costs nothing in expressiveness. *(Round-2 refinement, security-auditor N2/N3 + ethical-hacker Round-2 F2 — the original per-character enumeration was verified to miss U+2028/U+2029 specifically; the printable-ASCII-only rule supersedes the enumeration rather than patching it further.)* No part of this pipeline uses `/m` (Decision 7's redesigned patch is block-scoped, trimmed-line-start matching, not a whole-file `^…$/m` anchor — see Decision 7), so this is stated as an unconditional invariant, not contingent on avoiding some other component's flag choice; it is also an independent, redundant closure (defense-in-depth alongside the shadow-grammar fix above) for the newline-smuggling chain in Decision 7's Round-1 finding below. Decision 4's grammars use a literal space character, not `\s`, wherever whitespace is structurally required — closing the adjacent gap where a `\s`-permissive grammar could accept a "valid-shaped" value that isn't actually valid CSS and silently renders as nothing. **The same printable-ASCII-only + no-`m`/`s`-flags rule applies to the `--new-ds <name>` charset check in Decision 8** — stated there explicitly rather than left as an implicit "obviously the same rule applies," per ethical-hacker Round-2's finding that the two checks weren't visibly tied together in the prior revision.

**Round-1 finding (security-auditor W3): the original grammars bounded value *shape* but not *magnitude*.** `[\d.]+` is unbounded, so a grammar-valid `--space-9: 99999999px` or `--type-0: 99999rem` would reach a stylesheet rendered live in every canvas and the studio-client's own WKWebView (a context this codebase's own memory already documents as having a real filter/perf ceiling) — a pathological magnitude is a live-render hang/jank vector even though it's a "valid" value shape. Every numeric grammar above now pairs its shape check with an explicit magnitude range, checked after the regex match on the parsed numeric value.

Every grammar is **closed under composition with itself only** — no grammar admits `;`, `{`, `}`, `@`, `url(`, `expression(`, `javascript:`, `\`, or an unescaped quote, because none of the permitted constructs (numbers, units, named color functions with numeric arguments, a bounded charset for font names) can produce those characters, and no grammar contains an unbounded free-text capture group. This is what closes CSS injection: even a value that survives JSON/CSS parsing intact cannot smuggle a rule terminator, an `@import`, or a `url()` reference into the output file, because nothing that shape is in any grammar. `var(--other-token)` references **from the input file** are deliberately **not** in any grammar and are rejected — an imported token file may reference its OWN other tokens via the format's own alias syntax (Decision 2), resolved to a concrete value before this validation step ever runs; it may not reference an arbitrary Maude-side `--custom-property` name that could later be redefined out from under it.

## Decision 5 — Name-to-variable mapping: heuristic, never silent

There is no reliable way to know that a foreign token author's `"Surface/BG/0"` means the same thing as Maude's `--bg-0` without either (a) a rigid required input schema (defeats the point of importing an *existing* system) or (b) heuristic name matching that can be wrong. This DDR chooses (b), with the failure mode made **loud, not silent**:

- The importer normalizes each flattened token's path (lowercase, delimiter-collapse on `/`, `.`, `-`, `_`, camelCase-split) and matches it against a curated table of recognized naming patterns per target family (e.g. `bg|background|surface` + a ladder-position cue `0|base|default|page` → `--bg-0`; `accent|brand|primary` (when `$type`/`type` is `color`) → `--accent`; `space|spacing|gap` + a numeric scale index → the nearest `--space-N` slot; full table lives in the implementation, not duplicated here — it is data, not a security control).
- **A token whose path matches no recognized pattern is `unmapped`** — never guessed, never force-mapped to "the closest thing." It is written to the mapping report (`{path, detectedType, targetVariable: null, status: "unmapped"}`) and otherwise ignored.
- **A token that maps to a family, but whose value fails Decision 4's grammar, is `rejected`** — reported with the specific grammar violation, never partially applied.
- **A token that maps AND validates, but whose target variable has no existing declaration in the target `colors_and_type.css`** (e.g. the target DS never adopted the `status` family) is `skipped` by default — the importer does not force-insert new declarations into a hand-authored file structure unless the caller passes `--force-insert`.
- Only tokens that are `mapped` land in the output. The mapping report — printed to stdout and, matching this codebase's existing report-artifact convention, written to `<designRoot>/_history/_system/import-tokens-report-<ts>.json` — is a **complete accounting of every input token's disposition**, not just the successes. This is the concrete mechanism behind the plan's "unmapped tokens surfaced, never silently dropped" requirement — a report file, not a prose promise.

## Decision 6 — Colorspace normalization: convert when confident, report when not

The target DS's `config.json` declares `colorSpace` (`oklch | hsl | hex | lab`, default `oklch` per the completeness-critic's V2 check). A mapped color token whose input format doesn't match:

- **hex/rgb → oklch**: converted using a new `rgbToOklch()` added to `apps/studio/draw/palette.ts` (the exact inverse of the existing `oklchToRgb`, same Björn Ottosson constants, same file — no new module, no new dependency). `parseColor()` (already exported from `palette.ts`) handles the hex/rgb parse side.
- **oklch input, oklch target**: passed through via the existing `parseOklch`/re-serialize, value-grammar-validated as usual.
- **hsl or lab input, when the target `colorSpace` is NOT the same format**: conversion is **not attempted** — DDR-172 does not add an hsl↔oklch or lab↔oklch converter in this pass. The token is reported `skipped: unsupported-colorspace-conversion (hsl→oklch)` rather than silently passed through as a mismatched value or silently dropped. This is a real, named capability gap (matching this project's own "accepted residual, named explicitly" convention) — extending conversion coverage is a small, low-risk follow-up, not a blocker for T11.

## Decision 7 — Write-path: atomic, contained, non-destructive, THEME-BLOCK-SCOPED

**Round-1 finding, found independently by both reviewers against the real on-disk file shape (security-auditor B2, ethical-hacker F6) — the original draft's "replaces ONLY that declaration's value" model was under-specified against how a real Maude DS file is actually structured.** Every scaffolded DS ships a dark+light theme pair (verified against the real, committed `.design/system/maude/colors_and_type.css`: `--bg-0` is declared once inside `:root, .maude[data-theme="dark"] { … }` and again inside `.maude[data-theme="light"] { … }`) — most target variables are declared **twice**, not once. A single, whole-file `.replace()` patches only whichever block the regex engine finds first (silently leaves the other theme stale); a global `/g` replace writes the SAME single imported value into both the dark and light blocks (a single-valued imported token can't express "dark value" vs "light value" — this actively overwrites one theme with the wrong value). Neither behavior was an acceptable "replaces the declaration" outcome.

**Chained with a second, independent finding (security-auditor B3, ethical-hacker F2): a whole-file `m`-flagged regex scan is itself unsafe once Decision 4 allows any value to contain a newline (now closed at the grammar level above) — a value crafted with an embedded `\n--bg-0: red; x` could plant a fake declaration line that a later whole-file `/^--bg-0.../m` patch pass would match INSTEAD of the real declaration, corrupting the trusted stylesheet outside its intended theme block.** The redesign below closes this independently of the Decision 4 newline-reject fix (defense-in-depth, not reliance on a single control):

- **Patch mode is THEME-BLOCK-SCOPED, never a whole-file regex.** The importer first locates the text span of the target theme's selector block only. **Round-2 precision fix (ethical-hacker, checked against the real committed file):** the target is a **grouped selector prelude**, not two separate blocks — the real `maude` DS file's dark block is `:root,\n.maude[data-theme="dark"] { … }`, ONE rule whose selector list happens to include both `:root` and `.{rootClass}[data-theme="dark"]`, sharing a single `{`/`}` pair. The locator searches for the `.{rootClass}[data-theme="<theme>"]` selector text (tolerant of the whitespace/quote-style variants a hand-edited file might legitimately carry — `[ data-theme = "dark" ]`, `[data-theme='dark']`) — or, when `themeDefault` is the DS's only declared theme (`config.json themes` has length 1) and no `[data-theme]` selector exists at all, the bare `:root` selector, which for a single-theme DS legitimately IS the target — then brace-matches from THAT selector's own opening `{` to find the block's span; it does not treat `:root` and the `[data-theme]` selector as two separate blocks to reconcile.
- **Round-2 finding (ethical-hacker): the SAME selector strings recur inside the `@media (prefers-reduced-motion: reduce)` block** (the real file's motion-collapse rule re-lists `:root, .maude[data-theme="dark"], .maude[data-theme="light"]` verbatim). A locator that matches the first occurrence of the target selector text in raw document order is correct only by the accident that the real theme blocks currently precede the `@media` block — fragile against a hand-edited reorder. **The locator therefore explicitly scopes its search to top-level rules only, skipping any selector match found inside an `@media (...)` wrapper** (tracked via the same brace-depth state the tokenizer/locator already carries) — it locates the TOP-LEVEL theme rule specifically, never a `@media`-nested one that happens to share the same selector text.
- **The brace-matcher is comment/string-aware, reusing Decision 1's tokenizer state discipline** (track quoted-string and `/* … */` comment state while counting `{`/`}`) rather than naive character counting — a `}` inside a comment or inside a declaration's value (e.g. a `content: "}"`-shaped string, not that this file has one, but the matcher shouldn't assume) must not be allowed to mis-terminate the block span.
- All declaration lookup and patching happens **only within the located block's text span** — a value planted with an embedded fake `--name:` line elsewhere in the file (inside a different theme's block, inside a comment, inside another token's value) is structurally unreachable, because the patcher never scans outside the one located, top-level, comment-aware-matched block.
- **The failure mode when the target block can't be unambiguously located is a HARD REJECT with a clear "could not locate the `<theme>` block in `<path>` — this file's theme structure isn't recognized" error and NO write of any kind** (security-auditor N1, Round 2) — never a fallback to `:root`, to the first (possibly `@media`-nested) match, or to a whole-file scan, any of which would silently reopen a B2/B3-shaped variant of the exact bug this redesign closes. Triggers: a `themeDefault` naming a theme with no matching top-level selector, a theme expressed via `@media (prefers-color-scheme: dark)` instead of `[data-theme]` (a structurally different, out-of-scope-for-v1 mechanism), or a corrupted file whose brace-matching runs to EOF unresolved. This applies even in `--force-insert` mode: force-insert still requires a located block to insert before its closing `}` — it does not fall back to file-scope insertion when no block is found.
- **Explicit twin-declaration policy.** A flat, single-valued imported token patches ONLY the located target-theme block. Every OTHER theme block containing the same variable is left untouched and reported in the mapping report as `skipped: themed-token-not-patched (theme=<other>, value unchanged)`. A new `--theme <name>` CLI flag lets a caller target a specific theme explicitly (default: `config.json themeDefault`) — importing separate light/dark token exports means running the verb twice, once per `--theme`, each a fully independent, correctly-scoped patch pass.
- Within the located block, replaces ONLY the matched declaration's value via a targeted, closed-vocabulary line match (operating only on the fixed set of family-prefixed names this DDR's grammar table covers, matched against a **trimmed line start**, not a whole-file `^…$/m` anchor) — mirroring the same "regex over a known, closed vocabulary, not general CSS parsing" house style `design-system-keeper`'s token-usage audit and `handoff.ts`'s `filterTokensCss()` already use for **Maude's own trusted output files** (as opposed to Decision 1's tokenizer choice for the untrusted *input* side). Everything else in the file — comments, structure, un-mapped declarations, the other theme's block, the `@media (prefers-reduced-motion)` block — is left byte-for-byte untouched.
- **Force-insert anchor, specified precisely**: `--force-insert` (a token whose target variable has no existing declaration in the located block) inserts the new declaration line immediately before the CLOSING `}` of the SAME located theme-block span used for patching — never at file scope, never "before the last `}` in the file" (which could land in the wrong rule entirely, e.g. the `@media` block).
- **Realpath containment**, mirroring DDR-167 Decision 3: the resolved write path must resolve inside `<designRoot>/system/` before any write, independent of what `config.json` claims — defense in depth against a corrupted or malicious `config.json` pointing `tokensCssRel` somewhere unexpected.
- **Atomic write**: write to a temp file in the same directory, then `renameSync` over the target — never a partial/truncated file on a crash mid-write, same discipline as the concurrent `stage_bundled_cli_link()` symlink-swap fix elsewhere in this codebase.
- **Scaffold mode** (`--new-ds <name>`, no existing DS of that name): reuses the EXISTING `scaffold-design.ts` scaffolding path to create the minimal file skeleton first (same neutral, no-visual-defaults posture as `--no-discovery` mode, DDR-043), then applies the identical theme-block-scoped patch pass from above onto the freshly scaffolded file (both theme blocks exist from the template; only the `--theme`-targeted one is patched, per the policy above). Only this mode touches `config.json` — see Decision 8 for exactly what is and isn't written there.
- **Backup**: the pre-patch file content is preserved in the same `_history/_system/` report directory alongside the mapping report (not a `.bak` sibling next to the live file, keeping the working tree clean) — a manual revert path if a heuristic mapping produces an undesired result.

## Decision 8 — CLI-verb reachability: narrower residual than DDR-167 Decision 5, no proof-token gate — but the new-DS metadata sink is ELIMINATED, not merely bounded

DDR-167 Decision 5 added an ACP-session-scoped proof-token gate for `import-asset` because that verb writes **arbitrary local file bytes** (an entire document/photo) into the peer-synced `assets/` tree — a high-bandwidth exfiltration channel a prompt-injected agent session could exploit indistinguishably from a legitimate import. `import-tokens` is a **different shape of risk** for the token VALUES themselves:

- The only data that can reach the output stylesheet is a value that (a) matched a recognized token-family **name pattern** and (b) passed that family's narrow **value grammar** (Decision 4). This is a low-bandwidth, structurally-typed channel (a handful of numbers, a color, a short font-family string) — categorically smaller than "an entire file's bytes/rendered pages," and specifically NOT capable of carrying arbitrary attacker-chosen text (font-family values are charset-restricted to `[A-Za-z0-9 _-]`, colors are numeric-argument-only, and — after this revision — no grammar contains an unbounded free-text capture).
- There is no HTTP route and no in-app panel for this verb (Decision, Instruments header) — the only entry point is the plain CLI, identical in shape to every other `maude design <verb>` today.

**Round-1 finding (ethical-hacker F3, HIGH — this revises the original draft's reasoning, not just its wording).** The first draft called the `--new-ds <name>`/description sink "a cosmetic string, low-blast-radius" without tracing where it actually goes. Traced properly: `config.json designSystems[]` is **VERSIONED and peer-synced** (DDR-054's untrusted-peer model, the same runtime-state taxonomy CLAUDE.md documents) AND is **read into context by multiple Maude LLM agents** — `design-system-completeness-critic`, `design-system-keeper`, and the `/design:setup-ds`/`/design:new` flows all read `config.json`. Free text landing there from an unvalidated source is not "cosmetic" — it is a **prompt-injection surface** reaching those agents, cross-peer, which is exactly the class of risk DDR-167 itself quarantined behind an explicit DDR gate (the plan's T12a) rather than accepting inline. Calling it cosmetic without tracing the sinks was the error, not the underlying architecture.

**Fix: eliminate the sink rather than bound it.**
- **The imported token file's content NEVER supplies the DS description.** No `$description`/metadata/comment field read from the input token file is written into `config.json` under any circumstance — there is no code path from "text found in the parsed token file" to "text written into `designSystems[].description`." The importer always writes a **fixed, importer-authored template string** for a scaffolded DS's description (e.g. `"Imported via maude design import-tokens — <N> tokens mapped on <date>. Refine via /design:setup-ds."`, with only the token COUNT and a server-generated date as the two non-literal parts, both numeric/date values, not free text). A user who wants a real, considered description sets one afterward via the existing `/design:setup-ds` flow, which already has its own, separate, human-typed-CLI-arg trust model.
- **`--new-ds <name>` is charset-constrained to `^[a-z0-9-]{1,64}$`, asserted before it touches the filesystem path, the `system/<ds>/` directory name, or `config.json`.** This closes the separate concern (ethical-hacker F3's second half) that the name string also flows into path-adjacent and name-keyed lookups elsewhere in the codebase (the server's `canvasDesignSystems` map, `meta.designSystem` references) beyond just `config.json` — a name outside this charset is a hard reject (`rejected: invalid-ds-name`), not sanitized-and-accepted. The SAME charset-validated name (never a second, unvalidated copy) is what's forwarded to `scaffold-design.ts` and into any generated file — closing the adjacent question (raised independently by a second ethical-hacker pass against the pre-revision draft) of whether an unescaped name could break out of a CSS comment or a JSON string somewhere downstream: the kebab-case-only charset contains no `*/`, `"`, `` ` ``, `{`, or `}`, so there is no character available to attempt a breakout with, regardless of how downstream code interpolates it.
- **`import-tokens.sh` (the bash wrapper) quotes every argument it forwards** (`"$@"`/individually-quoted positional args, never an unquoted or `eval`-expanded interpolation) — mirroring every other `maude design <verb>` wrapper in this codebase. This is a wrapper-hygiene requirement stated explicitly here (rather than left to be "obviously" done right) because `--new-ds <name>` is exactly the kind of caller-supplied argv value a careless wrapper could mishandle; the charset validation above happens in `_import-tokens.mjs`, not the shell wrapper, so the wrapper's OWN job is limited to safe argv passthrough, not validation.
- **`config.json`'s write (scaffold mode only) is realpath-contained to the single, exact expected path `<designRoot>/config.json`** — a narrower assertion than the CSS write's "resolves inside `<designRoot>/system/`" (there is exactly one legitimate config.json location, not a subtree), stated explicitly rather than left implicit under the `system/`-scoped bullet above, which does not cover this second write target.
- With both of those closed, the ONLY new-DS-mode data reaching `config.json` from this verb is: the charset-validated name, a fixed description template with a numeric count, and the `tokensCssRel`/`rootClass`/`themes` structural fields the scaffold path already derives from `scaffold-design.ts` (not from the input file). There is no remaining free-text sink to name as a residual — the fix is structural elimination, not a bound.
- **Read-side note (security-auditor completeness note), stated explicitly rather than left implicit**: this verb still reads an arbitrary local path in an ACP-reachable CLI and emits a mapping report enumerating parsed token paths/values. This grants no NEW capability beyond what a file-reading agent already has (the same DDR-164 §F3 structural-residual logic DDR-167 itself relies on for reads) — but the report is written under `<designRoot>/_history/_system/` (gitignored runtime state per the taxonomy) and Decision 1's parse-error messages never echo raw input content, so no new echo-back exfil channel is added either.
- If a future revision of this feature adds an HTTP route or an in-app panel (mirroring T10's Brand-upload panel), THAT change must re-derive this decision — the "narrower than DDR-167" reasoning is specific to the CLI-only, value-grammar-bounded, metadata-sink-eliminated shape this DDR describes now.

## Threat model summary

| Threat | Closed by |
| --- | --- |
| CSS injection via token value (rule termination, `@import`, `url()`, `expression()`) reaching a live-rendered stylesheet | Per-family value-grammar allowlist, closed under composition, no unbounded free-text captures, shadow-layer grammar fixed to strict-numeric-only (Decision 4) |
| Grammar bypass via multiline value + `/m`-anchored matching (`#fff\n};@import url(…)`) | Newline/control-char hard-reject before grammar matching; grammars never matched with `m`/`s` flags (Decision 4) |
| Unbalanced-paren stylesheet corruption via the `--shadow-*` grammar's original `[^)]+` layer | Every shadow layer uses the identical strict numeric-argument rgba grammar — no free-text capture in any grammar (Decision 4) |
| Live-render DoS via a grammar-valid but pathological numeric magnitude (`99999999px`) | Magnitude range bound paired with every numeric grammar, checked on the parsed value (Decision 4) |
| Unbounded/cyclic alias resolution (`{a} → {b} → {a}`) causing a hang | Visited-set cycle detection + max depth 16 (Decision 2) |
| Alias amplification / billion-laughs analogue via composite-token branching or multi-reference string interpolation (`"{a} {a}"`) | Only WHOLE-VALUE single-alias substitution is resolved at all — structurally caps total work at O(tokens × depth), no branching/doubling term possible; memoization cache as additional hardening (Decision 2) |
| Token file referencing an external `$ref`/`extends`/file path, importer obligingly reads it | Resolver only ever reads the in-memory parsed object graph of the ONE input file — never dereferences a string as a path/URL; enforced by a permanent test banning fs/net/http imports in the resolver module, not prose alone (Decision 2) |
| Prototype pollution via recursive walk of untrusted JSON keys | `__proto__`/`constructor`/`prototype` key skip at every recursion level (Decision 3) |
| Deeply-nested JSON structure (independent of alias depth) stack-overflowing the flatten walk | Explicit structural recursion-depth cap (32), checked before any alias logic (Decision 3) |
| Malformed/adversarial raw-CSS input defeating a naive extractor, or an unverified native-addon runtime dependency in the compiled binary | A small purpose-built, state-tracking tokenizer (brace/string/comment-aware) — not `lightningcss` (native addon, build-time-only usage, unverified in the `bun --compile` runtime) and not a regex (Decision 1) |
| Oversized input file (memory/DoS) | 2 MB pre-parse cap (Decision 1) |
| Symlink/TOCTOU on the input file read | `realpath()`-then-open with symlink-component rejection + single capped read (Decision 1) |
| Parse-error text becoming a reflection/micro-exfil channel | Error messages report structural position only, never a verbatim input excerpt (Decision 1) |
| Silent semantic mis-mapping (a foreign token silently becomes the wrong Maude variable) | Unmapped/rejected/skipped tokens are reported, never guessed (Decision 5) |
| Colorspace mismatch producing a value inconsistent with `config.json colorSpace` | Convert when a converter exists (hex/rgb→oklch); report `unsupported-colorspace-conversion` otherwise, never silently pass through (Decision 6) |
| Same token variable declared in multiple theme blocks (dark+light) silently left stale, or overwritten with the wrong theme's value | Theme-block-scoped patch (locate the target theme's block span first) + explicit `--theme` flag + `skipped: themed-token-not-patched` report for untouched themes (Decision 7) |
| Cross-token patch hijack via a newline-smuggled fake declaration planted inside another token's value | Theme-block-scoped patching (never a whole-file `/m` scan) + the Decision 4 newline-reject, two independent closures (Decision 7) |
| Corrupted/malicious `config.json tokensCssRel` pointing the write outside the design root | Realpath containment assertion before write (Decision 7) |
| Partial/truncated file on a crash mid-write | Atomic temp-file + rename (Decision 7) |
| Destructive overwrite of a hand-authored token file | Targeted single-declaration match scoped to the located theme block, not a full-file rewrite; pre-patch content backed up alongside the report; precise force-insert anchor (Decision 7) |
| New-DS `config.json` name/description as a prompt-injection surface into `design-system-completeness-critic`/`design-system-keeper`/setup flows, cross-peer via DDR-054 | **Eliminated, not bounded** — no token-file-derived free text ever reaches `config.json`; description is a fixed importer-authored template with only a numeric count; `--new-ds` name is charset-constrained (`^[a-z0-9-]{1,64}$`) before touching any path/config (Decision 8) |
| Confused-deputy: ACP-agent-invoked import of an unintended local file | **Named, accepted residual** — narrower than DDR-167's because the reachable output is value-grammar-bounded (token values); the one free-text sink DDR-167's own review pattern would flag (new-DS metadata) is eliminated above rather than merely bounded; no technical gate added (Decision 8) |

## Consequences

- Net-new parsing/mapping/validation code (`_import-tokens.mjs`) needs test coverage across all three input formats plus the negative cases in the threat table above (a CSS-injection-shaped value incl. the multiline/`/m` bypass and the shadow-grammar unbalanced-paren case, a cyclic alias, a multi-reference-interpolation value, a `__proto__`-keyed object, a deeply-nested-array object, an oversized file, a malformed JSON/CSS file, a dual-theme patch run, a pathological numeric magnitude, and a theme-block-not-found rejection). The Decision 1 tokenizer specifically needs fixtures for both quote styles, a quote of one style nested inside the other (must stay a literal, not a string-start), and escaped terminators (`\;`, `\}`) inside a value — the exact shapes a state-tracking-but-untested tokenizer is most likely to get subtly wrong (security-auditor N4).
- No new npm dependency. JSON formats use native `JSON.parse`; the raw-CSS input format uses a small hand-written tokenizer instead of `lightningcss` (deliberately NOT reused here — see Decision 1's Round-1 revision) or a regex.
- One small, low-risk addition to `apps/studio/draw/palette.ts` (`rgbToOklch`) — pure function, same file/style as its existing inverse.
- The value-grammar table (Decision 4) is the single control this DDR treats as load-bearing; any future change that adds a new target CSS-variable family (e.g. a new token kind) MUST add a corresponding grammar row here — with both a shape AND a magnitude bound, and no unbounded free-text capture — before the importer is allowed to write to it. An ungoverned family is a `skipped`, not a silent pass-through.
- Colorspace conversion coverage (hsl/lab → oklch) is an explicitly named gap, not silently absorbed — a reasonable, low-priority follow-up.
- Two permanent regression-test requirements, not optional hardening: (1) the resolver-module import-ban test (Decision 2), (2) the theme-block-scoped patch tested against a real dual-theme fixture (dark+light both present, only the targeted one changes).

## Security review

**Round 1 (2026-07-14) — design-stage, against the initial draft.** `security-auditor` (defender) + `ethical-hacker` (adversarial) both reviewed the DDR text (no code existed yet).

**security-auditor — 3 blockers, 6 warnings:**
1. (Blocker) `--shadow-*` grammar's `[^)]+` layer falsified the DDR's own closure invariant → every layer now uses the strict numeric-only rgba grammar (Decision 4).
2. (Blocker) Patch model didn't account for real dual-theme (dark+light) declarations, confirmed against the actual committed `maude` DS file → theme-block-scoped patch + explicit twin-declaration policy (Decision 7).
3. (Blocker) Newline-bearing grammar-valid values + `/m`-anchored whole-file patch regex chain into a cross-token patch hijack → theme-block scoping + independent newline-reject at the grammar layer, two closures (Decision 4 + 7).

5. (Warning) New-DS name/description residual under-argued, sinks not enumerated → sink eliminated (fixed template, charset-constrained name), not just re-argued (Decision 8).
6. (Warning) No numeric magnitude bound on grammar-valid values → magnitude ranges added to every numeric grammar (Decision 4).
7. (Warning) No structural depth cap on the JSON tree-walk, separate from alias depth → explicit 32-level cap (Decision 3).
8. (Warning) `lightningcss` runtime availability in the compiled `bun --compile` binary unverified → dropped in favor of a small dependency-free tokenizer (Decision 1).
9. (Warning) Input read lacked DDR-167's realpath/symlink/single-read discipline → added, mirrored from DDR-167 Decision 2 step 1 (Decision 1).

**ethical-hacker — 2 HIGH, 3 MEDIUM, 1 LOW, all with concrete PoCs or precise mechanisms where applicable:**
