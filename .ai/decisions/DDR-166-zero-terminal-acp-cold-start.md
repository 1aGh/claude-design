**Status:** Implemented (T0a–T0f all landed) — revised after the T0a-mandated `ethical-hacker` + `security-auditor` pass found the first draft **not sound enough to proceed** (3 High findings from security-auditor, 1 Critical exploit chain + 3 High findings from ethical-hacker). This revision addresses every finding below. A second, code-level defender+attacker pass then ran against the actual T0b–T0f diff (three total review rounds, including a follow-up that caught the first "fix" as itself incomplete — see Security posture), and T0f's own `desktop-e2e` scenario (`acp-cold-start`) is built and green against the real compiled app. Windows/Linux provisioning and `switch_project()`'s grandchild-reaping remain named, accepted residuals (see Consequences).
**Supersedes in part:** [DDR-123](DDR-123-acp-chat-runs-on-users-claude-cli-subscription.md) guardrail #2 ("do NOT implement a sign-in flow") and [DDR-128](DDR-128-first-open-readiness-check-detect-and-guide.md) Decision 1's "`claude` login stay[s] guide-only" conclusion — both were reached assuming the *only* login surface was the interactive `/login` slash command inside a running session. That assumption is now known false (see Context). Every other guardrail in both DDRs is unchanged and reaffirmed below.
**Extends:** [DDR-128](DDR-128-first-open-readiness-check-detect-and-guide.md) Decision 4 (the one sanctioned auto-action — bundling `maude` — deferred out of v1, exercised here in a narrower form) and [DDR-143](DDR-143-acp-session-scoped-plugin-auto-bootstrap.md) (the plugin-injection mechanism this DDR verifies actually fires in the shipped bundle).

## Context

A designer's live-machine cold start hit three terminal detours before their first AI edit: install `claude`, run it + `/login`, restart Maude; get told to `npm i -g @1agh/maude`; get told to add the marketplace even though DDR-143 should have auto-injected the plugin. Fixing all three from inside a GUI app is a real trust decision, not a UI polish task — two of the three fixes (provisioning a CLI, triggering a login) sit directly on top of explicit prior postures:

- DDR-126: **"the app does not run `npm install` / `brew install` / package managers."**
- DDR-128 Decision 1: plugin/`claude`-login automation is **"structurally out of reach"** — "neither can be safely automated from outside a Claude Code session."
- DDR-123 guardrail #2: **"do NOT implement a sign-in flow (that is the restricted path)."**

DDR-128 already has a precedent for revisiting a "structurally out of reach" conclusion when a new lever is found (its own note superseding itself in part for DDR-143's plugin injection: "It missed a third [lever]"). This DDR does the same thing for `claude`'s auth surface, based on **live verification performed this session** (2026-07-13, `claude` 2.1.204, this machine), not assumption:

- `claude auth login`, `claude auth status [--json|--text]`, `claude auth logout` are **real, documented, non-interactive Commander subcommands** — confirmed via `claude --help` (lists `auth` under `Commands:`) and `claude auth --help`/`claude auth login --help`/`claude auth status --help` (full flag surfaces: `login` takes `--claudeai` (default, subscription) / `--console` (API billing) / `--email` / `--sso`; `status` takes `--json` (default) / `--text`).
- `claude auth status --json` **while genuinely logged in on this machine** returned a real, structured payload: `{ loggedIn: true, authMethod: "claude.ai", apiProvider: "firstParty", email, orgId, orgName, subscriptionType: "max" }`, exit code 0. This is materially better than a presence probe — `apiProvider`/`subscriptionType` let readiness **positively confirm subscription billing**, not just "logged in."
- Credential custody was independently confirmed: on macOS, `claude auth login` writes to the OS Keychain under service `"Claude Code-credentials"` (`security find-generic-password -s "Claude Code-credentials"` resolves) — the same custody class Maude's own GitHub sign-in already uses (`keychain.rs`), never a Maude-readable plaintext file.
- `claude install [target]` / `claude update|upgrade` also exist, but operate on an *already-installed* native build — relevant to keeping a provisioned `claude` current, not to the zero-to-one bootstrap problem T0c solves.

**What was NOT independently verified this session** (a research pass, and later the review agents, also surfaced claims about browser-auto-open behavior, `claude`'s actual public distribution channel(s), and exit-code semantics when logged **out** — none of that was live-tested by me, since doing so would have logged this machine's real Claude session out, or required fetching/executing an installer I hadn't yet vetted). **T0c implementation MUST live-verify the actual current official distribution channel** (see Decision 2) **before writing a single line of fetch code** — this DDR fixes the required posture, not a specific URL, precisely because the two review passes disagreed with my first draft's assumption (that it looks like `_ensure-browser.mjs`'s CfT-manifest case) and I have not personally confirmed which channel is current. Treat any specific URL mentioned below as a **candidate to verify**, not a fact.

### What the T0a review found (both passes read in full; findings folded into the decisions below)

The first draft of this DDR claimed to "mirror `_ensure-browser.mjs`'s already-shipped, already-reviewed pattern exactly" and to reuse `scrubAgentEnv` as "the enforcement mechanism," while separately describing the new work as two `#[tauri::command]`s. Both reviewers independently flagged that combination as internally inconsistent and under-defended for the actual stakes involved:

- **security-auditor** (gate: NOT MET, 3 High + 3 Medium): the DDR named two different runtimes (a `.mjs` dev-server script vs. two Tauri commands) for the same work, each with a *different* mechanism for the "never reachable from the untrusted canvas iframe" guarantee; the PATH-append in Decision 1 reintroduces a shadowing class `sidecar.rs`'s own comments already reject for `agent-browser`; "mirrors X" / "reuses `scrubAgentEnv`" are not literally true across a TS↔Rust boundary; plus three Medium findings (raw-stdout PII-to-syslog risk, understated blast-radius vs. a headless screenshot renderer, unaddressed npm-lifecycle-script risk if the tarball route is chosen).
- **ethical-hacker** (verdict: not sound enough to proceed as written; one finding **promoted to Critical**): `claude`'s actual documented public install path today is a live, executable shell script (`curl | bash`) — categorically incompatible with "validate before touching a path/shell, never execute untrusted content"; a same-UID attacker (this repo's own accepted local-compromise baseline elsewhere) who plants a substitute binary in the provisioning cache gets a **durable, silent proxy over every future AI chat session** once the user clicks "Sign in," because nothing re-verifies the cached binary's integrity after write time and the ACP bridge auto-approves tool calls for whatever `claude` resolves to; plus High findings on the same PATH-append issue, the same env-scrub-doesn't-obviously-extend issue, and a self-referential gap (the opt-out env vars for locked-down machines are themselves invisible to a Finder-launched, zero-terminal app).

The decisions below are the direct fix for each of these, not a restatement of the original draft.

## Decision 0 — T0c and T0d are new main-origin-only dev-server routes, not Tauri commands (resolves the architecture ambiguity)

Both `security-auditor` and `ethical-hacker` independently hit the same wall: the first draft couldn't decide whether the new work lived in Rust or TypeScript, and that ambiguity is exactly what let the "reuses `scrubAgentEnv`" / "mirrors `_ensure-browser.mjs`" claims go unverified (those are TypeScript; a Tauri command can't import them).

**Resolution: T0c (provision `claude`) and T0d (sign in + poll) are implemented entirely as new privileged dev-server HTTP routes** (`POST /_api/claude/provision`, `POST /_api/claude/signin`, `GET /_api/claude/signin-status` — final names at implementation time), following the exact precedent already established for `/_api/asset` and `/_api/preflight`: **main-origin-only, absent from both `CANVAS_SAFE_API` (`http.ts`) and the `startCanvasServer` routes map (`server.ts`)** — the DDR-088 privileged-route pattern, not Tauri capability scoping. This is a **deliberate simplification**, not just a bugfix:

- **Zero new `#[tauri::command]`s are needed.** T0b (below) is the only Rust change this DDR requires. This sidesteps an entire class of risk the reviews flagged around Rust reimplementing TS-side invariants, and avoids the `build.rs`/capabilities-wiring surface (memory `reference_tauri_command_needs_build_rs`) for two commands that don't need to exist.
- **The reuse claims become literally true.** `claude-provision.ts` and `login-state.ts` run in the same Bun process as `bridge.ts` and can `import { scrubAgentEnv } from './env.ts'` directly — the *same* function, the *same* file, not a re-derived Rust twin that can silently drift from it. The login/status spawn scrubs `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` exactly the way the ACP bridge spawn already does, because it calls the identical code.
- **`claude-provision.ts` reuses `_ensure-browser.mjs`'s actual reviewed primitives**, not a re-copy: the host-allowlist checker, the strict version-string regex gate, the "no redirect-follow" fetch, the `0700`-cache-dir + atomic-staging-then-rename sequence are extracted into a shared `apps/studio/bin/_fetch-cache-lib.mjs` that both `_ensure-browser.mjs` and the new `claude-provision.ts` import. A future fix to the allowlist/regex logic propagates to both call sites instead of silently diverging.
- **`login-state.ts` resolves `claude` through the same `resolveClaudePath()`** (`probe.ts`) the ACP bridge itself uses to decide which binary to spawn for chat — closing the "readiness could report against a different binary than chat actually uses" gap the security-auditor named.

Rust's role shrinks to exactly what only Rust can do here: T0b's PATH staging (below). Opening the system browser is `claude auth login`'s own responsibility once spawned — it needs no Rust involvement, since the dev-server sidecar already runs inside the user's real logged-in GUI session (the same reason a headless-shell-launching child from this same sidecar already works today). **T0c/T0d implementation must still live-verify this on a real packaged `.app`**, not just `tauri dev` (memory `feedback_native_app_verification_ceiling`).

## Decision 1 — Bundle `maude`, exposed as a narrow single-binary PATH entry, not the shared bundle directory (T0b)

`sidecar.rs`'s own existing comment (next to where `MAUDE_AGENT_BROWSER` is set) already names the exact risk both reviews flagged for the first draft's PATH-append: *"prepending `current_exe().parent()` ... would let a same-user attacker who can write there shadow `node`/`google-chrome`/etc. for every dev-server child."* The reviewers' suggested fix — mirror `agent-browser`'s single env-var pointer — **does not actually transfer to `maude`**, and it's worth stating why explicitly rather than adopting it wholesale: `agent-browser` is invoked by Maude's *own* TypeScript (`resolveBrowser()`), which can check an env var. `maude` is invoked two different ways that are **outside Maude's own code**: (a) `readiness.ts`'s own `resolveOnPath('maude')` does a bare PATH lookup already (verified at `readiness.ts:169`), and (b) — the actual reason it must be on PATH at all — the ACP-spawned `claude` agent's **Bash tool** runs the literal shell command `maude design <verb>` per DDR-062's own convention ("plugin markdown calls `maude design <verb>`, never a raw bin path"). Neither consumer can be redirected to an env var without either rewriting `resolveOnPath` (fine, in-scope) or rewriting every plugin script's dispatch convention (out of scope, a much larger and separately-reviewable change).

**Resolution:** stage the bundled `maude` binary as the *only* entry in a dedicated, Maude-managed directory — e.g. `<app-data-dir>/bin-link/` containing nothing but a `maude` symlink (or copy) to the real `externalBin` binary — and append **that narrow directory**, not `externalBin`'s / `Contents/MacOS`'s shared directory (where `maude-server` and `agent-browser` also live), to the sidecar child's PATH. This keeps the fix inside `sidecar.rs` (where PATH is already being constructed via `resolve_login_path()`) and satisfies the actual constraint (bare-word `maude` must resolve) while exposing exactly one name for unqualified lookup instead of an entire bundle directory's worth. Appended, not prepended (the user's own newer global `maude` — e.g. `npm i -g @1agh/maude` — still wins on precedence); the narrow-directory fix is what closes the *shadow-surface* half of the original finding, which append-vs-prepend alone does not.

## Decision 2 — Provision `claude`: verified-artifact fetch, never a live script, never a package manager (T0c)

**DDR-126's line is reaffirmed, not relaxed** — no `npm install -g`, no `brew install`, no package manager of any kind. But the first draft's assumption that this looks like `_ensure-browser.mjs`'s Chrome-for-Testing case (a static, unsigned JSON manifest, download-only) is now known to be the **wrong model for the stakes involved**, per the ethical-hacker's Critical finding: a compromised `claude` binary doesn't just render a bad screenshot — once wired in as the binary the ACP bridge spawns for chat, it silently intermediates every future coding-agent turn (the bridge auto-approves tool calls for whatever `claude` resolves to). That asymmetry means the CfT-style "host-pin is enough" trust model is **not** sufficient here, and it means the single most important fix is closing the exploit chain the ethical-hacker walked end to end: *plant a substitute binary in the idle cache → user clicks Sign in later → Maude trusts it forever, silently, across restarts.*

Binding requirements for T0c, none of them optional:

1. **Never fetch, and never execute, a live installer script** (`curl | bash`-class). If that turns out to be `claude`'s only current official distribution mechanism, T0c is **blocked** until a verified, declarative artifact channel is confirmed — do not ship a version of this feature that pipes a network response into a shell.
2. **Require an integrity proof from an official Anthropic channel before the binary is ever staged** — a published checksum and/or signature, verified against the fetched bytes, not merely "the host matched an allowlist." The exact channel (a release manifest + signature, an npm registry integrity hash, or whatever Anthropic currently publishes) is an implementation-time question T0c must verify live against Anthropic's current docs — **this DDR requires that *some* such proof exists and is checked; it does not bless a specific URL**, because neither the earlier research pass nor this DDR's author independently confirmed one, and the review agents' web citations were third-party blogs, not Anthropic's own docs.
3. **Re-verify the cached binary's integrity before it is ever trusted, not only at write time.** Persist the verified hash alongside the cache entry; re-hash and compare before `login-state.ts`/readiness wires the cached path in as `MAUDE_CLAUDE_BIN` — at minimum on every cold app start and immediately before every "Sign in" click. This is the direct, concrete close of the ethical-hacker's Critical exploit chain: a `0700` cache directory stops *other users*, not other processes running as the same user (this repo's own accepted local-compromise baseline elsewhere), so write-time validation alone is not durable — an idle-period substitution must be caught before it's ever used, not just prevented from RCE-ing "correctly" the first time.
4. If the eventual channel is an npm-published tarball: **raw archive extraction of the target binary only** — never `npm install`/`pnpm add` against the downloaded artifact, and never execute any script the package embeds (`postinstall`/`preinstall` or otherwise). This is the concrete form DDR-126's "no package managers" line takes if that channel is chosen.
5. **Extraction must assert path-containment** (reject any archive entry whose resolved path would land outside the staging directory) — folded into the shared `_fetch-cache-lib.mjs` so both `_ensure-browser.mjs` and `claude-provision.ts` get the fix, not just the new code.
6. Same non-negotiables as the original draft: HTTPS + pinned/allowlisted host, `redirect: 'error'`, strict version-string validation before any path/shell use, `0700` cache dir, atomic staging + rename.

The download is **user-consented**: only triggered by an explicit "Set up AI editing" button click, never silently in the background, with an honest size/one-time label.

**Addendum 1 (2026-07-13, live-verified against `code.claude.com/docs/en/quickstart.md`):** the *recommended* official install method is `curl -fsSL https://claude.ai/install.sh | bash` (macOS/Linux native install) — a live shell script, no checksum or signature published anywhere on that page. Homebrew (`brew install --cask claude-code`) is the only alternative with independent provenance (Homebrew's own cask signing), but shelling out to `brew install` is exactly what DDR-126 forbids. Per point 1/2 above, a design that **caches and permanently trusts** a fetched artifact is blocked for v1 — there is no verified, declarative artifact channel to build that against today. First shipped as: an accurate, verbatim copy-paste command (Copy action + Recheck), no in-app fetcher.

**Addendum 2 (2026-07-13, superseding Addendum 1's conclusion after further owner review + empirical testing) — T0c ships as a real one-click install after all, via a narrower, different design than the one the T0a review blocked.** The T0a review's Critical finding was specifically about a **persistent, Maude-managed cache** of a fetched binary (`~/.maude/claude/`) that the app would trust forever afterward — that's what created the "plant a bad file while idle, get a silent standing MITM" exploit chain. That finding does not apply to a design with **no persistent artifact at all**: spawn the exact official one-liner (`bash -c "curl -fsSL https://claude.ai/install.sh | bash"`), once, on an explicit button click, exactly as if the user had typed it themselves — and let Anthropic's own installer decide where the binary lands and how it's trusted, same as it does for every Claude Code user today. There is nothing left for a later, idle-time attacker to poison, because Maude never re-uses a cached copy — every future spawn re-resolves through the normal, already-reviewed `resolveClaudePath()`/PATH mechanism.

**What this design does and doesn't change:**
- **Still true:** never a package manager (`brew`/`npm install`), never a modified/mirrored copy of the script, HTTPS + the fixed official host only, no argument/path built from user input (the spawned command is a fixed literal string, zero injection surface).
- **New, explicit trade-off the user made deliberately, not a default:** Maude executes a live, unsigned script fetched over the network, once, per install click. The trust anchor is "Anthropic's own domain + TLS," identical to what the official docs already ask every Claude Code user to accept by hand — automating it doesn't create a new target, it removes the copy-paste step from a decision the user was already implicitly making. If `claude.ai` were ever compromised, every Claude Code install everywhere is compromised, not something specific to Maude having automated it. This is **not free** — it is a deliberate, informed acceptance of the ambient curl-\|-bash trust model (the same one `rustup.rs`'s own installer uses), made explicitly here rather than inherited silently.
- **Blast-radius asymmetry (the original Decision 2 concern) is addressed differently now:** it no longer matters that a compromised `claude` would be a higher-value target than a compromised screenshot engine, because there's no window between install and use where a *substitute* artifact could get planted — the binary that runs is whatever `install.sh` just placed, checked once, immediately, not a long-lived cache trusted blindly on every later launch.

**Empirical verification (2026-07-13, this session, tested directly — not just documentation):**
- `curl -fsSL https://claude.ai/install.sh | bash` run with `stdin` closed (`< /dev/null`) and `HOME` redirected to an empty throwaway directory: **exits 0, fully non-interactive, completes in seconds**, no prompt ever blocks it. Installs to the fixed path **`~/.local/bin/claude`**.
- **Correctness finding, not just a security one: the installer explicitly does NOT add `~/.local/bin` to PATH** — it prints a one-line suggestion for the user to add it to their shell config themselves. This means neither the existing readiness probe (`resolveOnPath`) nor the ACP bridge's own `resolveClaudePath()` would find a freshly Maude-installed `claude` without an explicit fix — **`resolveClaudePath()` needs a new fallback check for the well-known `~/.local/bin/claude` location**, independent of PATH, or the "install" button would appear to succeed while the chat panel stays stuck on not-connected.
- `claude auth login --claudeai` spawned the same way (`stdin` closed, not attached to any TTY, output piped not interactively read — the exact shape `Bun.spawn` produces): **works correctly with zero stdin interaction on the happy path.** It prints "Opening browser to sign in…" plus a fallback URL immediately, then polls silently in the background. The docs' "paste code here if prompted" text is a defensive fallback for when the browser can't complete the round-trip at all (e.g., no browser reachable) — it does **not** block or require stdin on the normal path where the browser opens and the user completes OAuth there. Confirmed cleanly killable (`SIGTERM`) mid-poll for the cancel button.
- Net effect: **T0c and T0d can be auto-chained into one user action** — click "Set up AI editing" → install (silent, ~seconds) → sign-in spawns automatically → browser opens → user completes OAuth → polling detects completion → panel connects. The only input the user ever provides is completing sign-in in their own browser tab, matching the actual product goal.

**Revised Decision 2, concretely:**
1. New privileged dev-server route `POST /_api/claude/install` (same main-origin-only + CSRF + loopback double gate as every other privileged route) spawns `bash -c "curl -fsSL https://claude.ai/install.sh | bash"` with `stdin: 'ignore'`, `scrubAgentEnv()`'d env, single-flight guarded (mirrors `startSignin()`'s guard).
2. On success (exit 0), the caller (client-side orchestration, not the route itself) immediately calls the existing `startSignin()` — one user click drives both steps.
3. `resolveClaudePath()` gains a `~/.local/bin/claude` fallback check (after the `MAUDE_CLAUDE_BIN` override, before the plain `Bun.which` call) — cheap, deterministic, no shell spawn, and correct regardless of whether Maude or the user ran the installer.
4. The copy-paste command stays as a **visible fallback**, not the primary path — covers non-macOS/Linux targets (out of scope for automation this pass, Mac-first per the plan) and gives a power-user escape hatch if the automated install ever fails.
5. Install output is not raw-echoed to any persistent log (mirrors the no-raw-payload-logging invariant from Decision 3) — only a success/failure boolean and a short human message are surfaced to the UI.

## Decision 3 — Sign in to Claude from Maude: drive `claude auth login` + poll `claude auth status --json`, on the same scrubbed-env code path as chat (T0d)

This is the guardrail this DDR moves, deliberately and narrowly. **What changes:** Maude spawns `claude auth login` (the user's own CLI's own documented, non-interactive auth subcommand) as a subprocess when the user clicks "Sign in to Claude," then polls `claude auth status --json` on a capped, cancelable interval for `loggedIn: true`, then hot-reconnects the ACP bridge in place (mirroring `switch_project`'s in-process re-navigate pattern in `sidecar.rs` — never `app.restart()`).

**Why this does not cross into "Maude implements a sign-in flow" (the thing DDR-123 forbids):** the distinction that guardrail draws is *whose* login experience it is. Building our own OAuth UI, or embedding the Agent SDK with a token, is Maude offering its own claude.ai login — the restricted path. Spawning `claude auth login` and waiting on `claude auth status` is structurally identical in kind to the ACP bridge already spawning `claude -p` to run prompts (DDR-123's core sanctioned pattern): we drive the user's own already-trusted binary through its own documented interface. The actual OAuth exchange, the browser tab, and the credential write are 100% `claude`'s — Maude never renders a login form, never requests a scope, never sees a token. The credential lands exactly where it always does when a user runs the command themselves (OS keychain, verified above) — Maude reads only `claude auth status`'s stdout, a channel Anthropic ships specifically for scripting.

**What must NOT move (reaffirmed and, per the review, made concrete):**
- **The spawn uses `scrubAgentEnv(process.env)` — literally the same function `bridge.ts` calls for the chat spawn** (per Decision 0, both now live in the same Bun process). This closes the ethical-hacker's High finding that a Rust-side reimplementation could silently miss the scrub; there is no second code path to keep in sync.
- Maude never reads the keychain entry or any credential file itself — only `claude auth status`'s JSON.
- **Show the user which `claude` binary is about to be invoked before the button spawns anything** — the resolved absolute path, or at minimum "via Maude's bundled Claude Code" vs. "via your own installed Claude Code." This is the concrete fix for the ethical-hacker's finding that a pre-existing PATH-hijacked `claude` (not the provisioned one) gets no protection from Decision 2's integrity checks, and that a GUI "Sign in" button aimed at non-technical users raises the cost of a convincing fake login page popping up unexpectedly.
- `apiProvider`/`subscriptionType` from the status JSON let readiness *confirm* subscription billing rather than merely hope the scrub worked; surface a warning if `apiProvider !== 'firstParty'`.
- **Single-flight guard**: concurrent sign-in attempts are rejected, not queued or raced. The spawned child (and any local OAuth-callback listener it opens) is killed on cancel, on app quit, and before a retry — no orphaned listener survives past the UI's own lifecycle. (New requirement — the first draft didn't specify subprocess lifecycle at all.)
- The poll loop is capped in duration and cancelable; its state copy respects `prefers-reduced-motion`.
- **Never format the raw `claude auth status` JSON into any log/console/panic sink** — parse it, extract only `{loggedIn, apiProvider, subscriptionType}` for any diagnostic output, and never let `email`/`orgId`/`orgName` reach `console.error`/`eprintln!`/a crash log. This is an explicit, testable invariant (worth a grep-style test alongside the existing CSP/canvas-origin invariant tests), not just a stated intention — both reviews independently flagged that this repo's own adjacent code habitually pipes subprocess stdout straight to a log sink, and unified logging on macOS persists whatever lands there.

`apps/studio/acp/login-state.ts` (new) shells `claude auth status --json` — resolving the binary via the *same* `resolveClaudePath()` the ACP bridge uses — and feeds `readiness.ts`'s `claude` row an honest 3-state: **not installed** / **installed, signed out** / **signed in on subscription**.

## Decision 4 — Guarantee plugin auto-inject fires in the shipped bundle (T0e)

Unchanged from the first draft — not a new trust surface. DDR-143 already built the correct design (session-scoped `_meta.claudeCode.options.plugins` injection, no `~/.claude` write, no network). The designer's report of a marketplace remediation despite DDR-143 shipping is a **packaged-bundle resolution regression** in an already-correct design (the historically fragile part per DDR-045: `resource_dir()` mapping inside a real `.app`). T0e verifies + fixes `isNativePluginContext()`/`DESIGN_PLUGIN_DIR` resolution in an actual built `.app` and adds a desktop-e2e assertion.

## Decision 5 — The readiness UI is wiring; opt-outs must not require a terminal (T0f)

T0f replaces `ChatPanel.jsx`'s terminal-instruction copy with `ReadinessList` rows carrying inline actions that call the new dev-server routes from Decisions 2–3. **The reviewable new surface is the three new privileged dev-server routes (fetch-and-provision, spawn-login, poll-status)** — not Tauri commands (Decision 0), and not new React logic beyond wiring.

**Opt-out fix (ethical-hacker High finding, self-referential gap in the first draft):** `MAUDE_NO_CLAUDE_PROVISION`/`MAUDE_NO_AUTO_SIGNIN` as bare env vars are invisible to a Finder/Dock-launched `.app` — exactly the launch path this "zero-terminal" feature targets, meaning the escape hatch for locked-down/enterprise machines would itself require a terminal to reach. The env vars remain as a secondary override for CI/test contexts specifically, where a terminal is already in use by definition.

**Implemented + verified live, 2026-07-13.** `prefs_get_claude_auto_setup`/`prefs_set_claude_auto_setup` Tauri commands (mirroring crash-reporting's exact shape, registered in `generate_handler!` + `build.rs` + capabilities); `sidecar.rs::spawn_server` reads the current value fresh on every spawn (covers respawn/`switch_project`, not just app launch) and passes it as `MAUDE_CLAUDE_AUTOSETUP_ENABLED`; `readiness.ts` gates the `action` field on it (disabled → falls back to guide-only, copy-paste command still shown); `login-state.ts`'s `startInstall()`/`startSignin()` also check it server-side as defense-in-depth, so a direct route call is rejected too, not just the button hidden. Verified end-to-end against the real compiled debug build: default-on shows `action:"install"`; flipping the pref to `false` and respawning removes `action` entirely from the readiness response AND makes `POST /_api/claude/install` return `409 {"ok":false,"reason":"Automatic setup is turned off in Settings."}`.

## Security posture

**T0a design-stage review: both `ethical-hacker` and `security-auditor` findings addressed** — every High/Critical finding from the design-stage pass has a concrete resolution in Decisions 0–5.

**Closing code-level review, 2026-07-13 — both `ethical-hacker` and `security-auditor` re-ran against the actual T0b–T0f diff.** Findings and disposition:

- **CRITICAL (ethical-hacker) — the mtime-freshness check only proved freshness at verification time, then trusted the path forever afterward.** `MAUDE_CLAUDE_BIN`, once set, was checked only via `existsSync()` on every subsequent `resolveClaudePath()` call — a same-UID attacker who swapped the *content* at that path at any later point in the long-lived dev-server process's life got the exact "durable, silent MITM over every future chat spawn" blast radius the original cached-artifact design was rejected for, just reached through a different door (path existence is not authenticity). **Fixed, in two rounds** (the first round's fix was itself found insufficient on re-verification — recorded honestly rather than smoothed over):
  1. *First fix:* content-pinning. `installClaudeCli()` hashes the verified-fresh binary (SHA-256) and calls `probe.ts`'s `setTrustedClaudeBin`; `resolveClaudePath()` re-verifies the pinned hash on every resolution — but cached the hash result keyed on mtime, only re-hashing when the file's mtime had changed since the last verified read.
  2. *Re-verification caught that the cache itself reopened the same hole:* mtime is neither secret nor tamper-evident — an attacker with the same-UID write access already required to swap the file's content can trivially restore its original mtime afterward (`touch -d`/`utimensat`, nanosecond-precision, no race), defeating the cache and going undetected for the rest of the process's life. This is a *different, easier* bypass than the honestly-disclosed Scenario B below (no real-time click-watching needed, works at any point after install) and the mtime-cache version of the fix did not disclose it as a residual — a real gap between the DDR's prose and the shipped code, caught by re-running the same reviewer against the revised diff rather than accepting the first "fixed" claim at face value.
  3. *Final fix:* the mtime-caching shortcut is removed entirely — `contentStillTrusted()` now re-hashes UNCONDITIONALLY on every call, no caching. This is safe performance-wise: a live measurement against the real ~241 MB installed `claude` binary took ~116ms, and the "avoid re-hashing on every poll tick" concern that motivated the cache doesn't actually hold — `useReadiness`'s polling only runs while the panel is disconnected (i.e., only during the bounded, actively-supervised install/sign-in flow), not for a long session's entire lifetime; the other real caller (a fresh chat-session spawn) pays the cost once per session, which has no meaningful latency budget concern.
  - **Honest residual, not fully closable client-side:** the ethical-hacker's Scenario B (an attacker who *pre-plants* a malicious binary and runs a tight `touch`-loop keeping its mtime just ahead of every install click) can still defeat the *initial* freshness gate itself — content-pinning protects the binary *after* it's been trusted, not the trust decision at the moment of pinning. This is a fundamental limit of verifying an unsigned installer with no published checksum (confirmed live against `code.claude.com`'s docs — see Decision 2's addendum): no purely client-side heuristic can fully close it without Anthropic publishing a real signed-artifact channel. It requires an attacker *already actively running a process that is watching for install-button clicks in real time* — a meaningfully narrower, more targeted capability than a dormant planted file (which IS rejected, since the mtime check already requires postdating the click), and roughly the same class of already-accepted same-UID-attacker baseline this codebase holds elsewhere (e.g. `~/.config/maude/keys.json`).
- **HIGH (both reviewers) — Decision 3's binding "show which binary is about to be invoked" requirement was never implemented in the UI.** **Fixed:** `ReadinessItem` gained `resolvedPath`/`resolvedViaMaude` fields (`readiness.ts`); `ReadinessList.jsx` renders the resolved absolute path ("Installed by Maude: …" / "Found on your PATH: …") immediately before the Sign-in button, for every `action:'signin'` state — the human-visible signal the DDR designed specifically to bound a PATH-hijacked-`claude` scenario.
- **MEDIUM (security-auditor) — the two new `-status` GET routes used `sameOriginWrite` (the CSRF guard for mutating routes) instead of `sameOriginRead`.** `sameOriginWrite` allows any request with no `Origin` header through, which browsers don't reliably stamp on a simple cross-origin GET — this file's own `sameOriginRead` exists specifically for this class (built for a prior ethical-hacker finding on a different route). **Fixed:** `/_api/claude/install-status` and `/_api/claude/signin-status` now use `sameOriginRead`. **Also fixed, adjacent:** `/_api/acp/status` (pre-existing, unmodified by the original diff) had *zero* CSRF/loopback gating at all — not this DDR's bug originally, but this DDR changes what its `claudePath` field can reveal (a Maude-auto-installed path), so it now carries the same `sameOriginRead` + `isLoopbackHost` gate as its siblings.
- **MEDIUM (both reviewers) — no shutdown-hook reaped in-flight install/sign-in grandchild processes.** The DDR's own threat-model table had named this as an open question ("an explicit answer for how a Tauri app-quit event reaches and kills the login-subprocess's grandchild") without an implementation. **Fixed:** `startInstall()`'s spawned child is now tracked at module level (`installChild`, mirroring the existing `signinChild` pattern) with a new `cancelInstall()`; `server.ts`'s `shutdown()` (SIGINT/SIGTERM handler) calls both `cancelSignin()`/`cancelInstall()` before its other cleanup. **Root-caused further:** `sidecar.rs`'s `kill_server()` (the Tauri app-quit path) called `CommandChild::kill()` alone, which sends **SIGKILL** (confirmed against `tauri-plugin-shell`'s actual behavior, not assumed) — SIGKILL bypasses `server.ts`'s SIGTERM handler entirely, so the new shutdown cleanup never ran for the actual app-quit case, only for a standalone dev-server Ctrl+C. **Fixed:** `kill_server()` now sends `SIGTERM` first (via the system `kill` binary — no new crate dependency, mirrors this file's existing `resolve_login_path()` shell-out pattern), waits a bounded 400ms grace period, then falls through to the existing guaranteed-termination `child.kill()` regardless.
  - **Residual, scoped down deliberately:** `switch_project()` (the in-process project-switch path) still uses bare `child.kill()` (SIGKILL, no grace period) — left unchanged rather than risk a regression in an already-delicate respawn/re-navigate code path this late, given the practical impact (an orphaned local process during the narrow window of "switching projects while an install/signin happens to be mid-flight") is bounded and self-expiring. Tracked as a follow-up, not a blocker.

**T0b (bundling `maude`) also landed in this pass**, verified live: `cli/lib/pkg-root.mjs` (new) gives the CLI the same DDR-045-class real-disk-path resolution the dev-server already has — with its own regression caught by live testing, not static review: a naive single-anchor check (`apps/studio/bin/screenshot.sh` alone) false-positived inside the actual Tauri build, because `stage-resources.mjs` stages a full working copy of `apps/studio` into `target/debug/apps/studio/` for the sidecar's own resolution, and a compiled `maude` binary placed at `target/debug/maude` matched that staged copy first, one level too early. Fixed by requiring a second anchor (`cli/commands/design.mjs`) only present at a genuine package root; locked down with `cli/lib/pkg-root.test.mjs`. `apps/desktop/scripts/build-cli-binary.mjs` (new) compiles it via `bun build --compile` (no NAPI workaround needed — unlike the dev-server, the CLI never imports `oxc-parser` at bundle time), wired into `beforeDevCommand`/`beforeBuildCommand`. `sidecar.rs` stages the bundled binary into a narrow, single-purpose symlink directory (never the shared `externalBin` directory, per Decision 1's own reasoning) and appends only that directory to the sidecar's PATH — also fixing a second real bug caught live: `process.execPath` returns the *symlink's* path when invoked through one, not the real target, so the walk-up resolver needed an explicit `realpathSync` first. `MAUDE_DEV_SERVER_BIN` is also now pre-set by the sidecar (mirroring `MAUDE_AGENT_BROWSER`), so the CLI's `BOOT_VERBS` dispatch never needs its own (compiled-binary-unsafe) npm-resolution fallback inside the Tauri context. `update-check.mjs`'s self-respawn (which also re-invokes `import.meta.url` as a script path, the same DDR-045 trap) is now skipped entirely for a compiled binary — a Tauri-bundled `maude` updates via the app's own auto-updater, not `npm i -g`, so the check was actively wrong advice there anyway.

**T0f desktop-e2e coverage (`acp-cold-start`), built and green, 2026-07-13.** `apps/desktop/e2e/scenarios/acp-cold-start.e2e.ts` + `wdio.acp-cold-start.conf.ts` drive the real compiled `.app`, DOM-only, through the full install → sign-in → connected chain. Deterministic via three new debug-only stubs (never in the release build): `MAUDE_E2E_FORCE_CLAUDE_STATUS=missing` (already existed) starts the run on a simulated clean machine; `MAUDE_E2E_FAKE_CLAUDE_INSTALL=1` makes `startInstall()` skip the real `curl | bash` and instead write a tiny offline stand-in script through the SAME freshness+content-hash verification path a real install goes through (the security-critical code stays exercised, not bypassed); `MAUDE_E2E_CLAUDE_INSTALL_PATH` redirects the well-known install path to a disposable temp file so the stub can never touch a real developer's actual `~/.local/bin/claude`. A precedence fix was needed for the stub to even be usable end-to-end: `resolveClaudePath()`/`probeReadiness()` originally let `MAUDE_E2E_FORCE_CLAUDE_STATUS=missing` clobber an explicit, just-verified `MAUDE_CLAUDE_BIN` override — meaning the scenario could start on "missing" but could never observe its own install succeeding. Fixed by making an explicit, content-pinned override always win over the coarse force-missing stub.

**Real bug found and fixed while building this scenario, not by review — T0d's own stated bar wasn't actually met.** `probeAcpAvailability()` (backing `GET /_api/acp/status`, the one signal `ChatPanel.jsx`'s connected/not-connected gate watches) only checked whether `claude` was *installed*, never whether the user was *signed in* — exactly the "logged-out-but-installed reads as available" failure mode T0d's own validation line calls out by name. A user could click install and land on a "connected" composer before sign-in even finished. Fixed with a new `probeAcpAvailabilityAuthed()` (`probe.ts`) that layers a real `getClaudeAuthStatus()` check on top — deliberately a separate function, not a change to `probeAcpAvailability()` itself, since that one also backs the cheap, no-subprocess WS `onOpen` ready frame and has its own pre-existing test contract (`acp-bridge.test.ts`) that a bare resolvable binary is sufficient. `getClaudeAuthStatus()` itself moved from `login-state.ts` into `probe.ts` (re-exported for backward compatibility) to avoid a circular import between the two. New tests: `probeAcpAvailabilityAuthed — DDR-166 T0d, logged-out must not read as available` in `acp-bridge.test.ts`, using a new `test/fixtures/fake-claude-auth.mjs` fixture. Also fixed in the same pass: `readiness.ts` carried a stale doc comment flatly asserting "T0c's fully-automated fetch-install is deliberately NOT built" — directly contradicting the `action:'install'` code three lines below it (a leftover from the pre-Addendum-2 draft, never updated when the automation was actually built) — corrected to describe what the code now actually does.

**Two non-code gotchas surfaced while getting the scenario to a genuine pass, worth recording since they'll recur:** (1) editing `client/app.jsx`/`ReadinessList.jsx`/`ChatPanel.jsx` source has NO effect on a packaged `.app` until `apps/studio/dist/client.bundle.js` is rebuilt (`MAUDE_SKIP_RUNTIME_BUILD=1 bun run build.ts --release`) AND the desktop build restaged (`pnpm test:e2e:desktop:build`) — the first two scenario runs against a stale bundle failed for a reason that looked like a wiring bug but was actually a stale-artifact problem (memory-worthy: MD5-verify `dist/client.bundle.js` against the staged `.app` resource copy before trusting a UI-testid-driven e2e failure). (2) the e2e bundle id (`com.maude.app.e2e`) persists its own `prefs.json` ACROSS runs — an earlier interactive session's manual toggle of the Settings "auto setup" checkbox had left `claude_auto_setup: false` on disk, which silently suppressed the install button on every subsequent run with no error, until traced back to the config file directly. `wdio.acp-cold-start.conf.ts` now resets this file at config load, mirroring `wdio.onboarding.conf.ts`'s existing reset of its own app-state files.
