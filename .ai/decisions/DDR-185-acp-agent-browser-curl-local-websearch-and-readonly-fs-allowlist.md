# DDR-185 — ACP default-allow: `agent-browser` + `curl-local` verb + read-only fs + WebSearch/WebFetch

**Status:** accepted · **Date:** 2026-07-18 · **Phase:** feature-acp-safe-defaults-and-attention-notifications
**Relates:** [DDR-184](DDR-184-acp-default-tool-allowlist-and-no-edit-mode-banner.md) (the default tool allow-list this extends — this DDR is a COMPLEMENT, using different mechanisms per capability class, not a reversal), [DDR-179](DDR-179-acp-permission-gate-retires-ddr125-f2.md) (mode-driven permission gate, unchanged), [DDR-180](DDR-180-acp-elicitation-form-support-askuserquestion-plus-mcp.md) (elicitation channel, unchanged), [DDR-054](DDR-054-linked-mode-trust-model-and-task-4-hardening.md) (untrusted-project-content trust model), [DDR-144](DDR-144-bundled-screenshot-engine-agent-browser-headless-shell.md) (`settingSources` narrowing, via its security addendum), [DDR-062](DDR-062-plugins-reach-executable-logic-via-maude.md) (`maude design <verb>` dispatch — the single-Bash-rule enabler)

## Context

A user reported that real `/design:setup-ds`/`/design:edit`/`/design:new` sessions in the ACP chat panel kept stalling on permission prompts, well beyond what DDR-184 already covers. Two concrete asks: (1) `curl` to the user's own localhost, and general read-only terminal commands, should not require approval every time; (2) later clarified — the actual dominant friction is that these design workflows call `agent-browser` and `WebSearch`/`WebFetch` directly and repeatedly, not just `curl`/`ls`.

DDR-184's own "Alternatives rejected" section explicitly killed "`acceptEdits` + a broad Bash allow-list of common commands" as unmaintainable — the literal shape of the initial ask. Extending the allow-list needed a mechanism that didn't reopen that risk.

**A `PreToolUse` hook was investigated as the "real enforcement" alternative to string-prefix matching, and ruled out.** Claude Code's `Bash(prefix:*)` allow-list syntax is a plain string-prefix match with no semantic understanding of "this argument is a URL to localhost" — `Bash(curl http://localhost:*)` does not match `curl -s http://localhost:3000` (the flag breaks the prefix). A `PreToolUse` hook could do a real host/path check instead, and the installed adapter (`@agentclientprotocol/claude-agent-acp@0.57.0/dist/acp-agent.js:2857`) does merge `...userProvidedOptions?.hooks` — but this path is a dead end: `apps/studio/acp/bridge.ts:719` spawns the adapter as a genuinely separate OS process (`Bun.spawn`), and `newSession(params)` (`bridge.ts:623`) sends `params` to that process over the ACP JSON-RPC wire. A `HookCallback` is a live JS function; it cannot survive JSON serialization across that process boundary. `userProvidedOptions.hooks` can only ever be populated by code running *inside* the adapter process — never by `bridge.ts`.

### Debate record

A 3-seat `reduce`-tier debate (BUILDER/SHIPPER/BREAKER, blind parallel openings, per `flow:debate-protocol`) ran on how to widen the allow-list for curl + fs without reopening DDR-184. Verdicts: BUILDER → `pretooluse-hook` (confidence 7), SHIPPER → `minimal-unscoped` (confidence 6 — a bare unscoped `Bash(curl:*)`, cutting the fs half entirely), BREAKER → `pretooluse-hook` reluctantly (confidence 8, with a "steelman against consensus" leaning toward shipping neither). No short-circuit — genuine disagreement, consolidated by the planning lead.

**The 2-of-3 `pretooluse-hook` verdict was overturned by a fact none of the three seats had**: the wire-boundary finding above. Preserved here rather than silently discarded: BUILDER/BREAKER's *reasoning* (real semantic enforcement beats string-prefix matching) is right, and is what the `curl-local` verb achieves via a different, wire-compatible mechanism; SHIPPER's caution about not reopening DDR-184's rejected shape is preserved in the fs list's "equivalent-power, closed-list, no-mutation" framing, and its "cut what isn't load-bearing" instinct is preserved by NOT giving `curl` a broad unscoped rule.

## Decision

Four independently-justified tracks — deliberately not collapsed into one "widen Bash" rule:

| Track | Mechanism | Why this one's safe to auto-approve |
| --- | --- | --- |
| `agent-browser` | Direct `Bash(agent-browser:*)` entry | Named, vetted, first-party-adjacent tool — same trust tier as `Bash(maude:*)`, not "any command" |
| `curl` | Dedicated `maude design curl-local` verb | Generic system utility reaching the network — Maude doesn't "own" curl the way it owns `agent-browser`/itself, so it earns real host enforcement instead of a blanket grant |
| `ls`/`cat`/`find`/`pwd`/`head`/`tail`/`wc`/`tree`/`file`/`stat` | Direct allowlist entries | Add no capability beyond what `Read`/`Grep`/`Glob` already grant unconditionally today — friction reduction, not a new grant |
| `WebSearch`/`WebFetch` | Direct allowlist entries (bare tool names, native) | Already-available native tools under the session's `claude_code` preset; risk is prompt-injection-via-fetched-content, orthogonal to the approve/deny decision itself |

**1. `Bash(agent-browser:*)`.** Confirmed by grep that `plugins/design/agents/motion-critic.md` and `plugins/design/commands/edit.md` (among others) document RAW `agent-browser eval`/`agent-browser screenshot` calls as current, expected behavior — not routed through any `maude design <verb>` wrapper, so DDR-184's `Bash(maude:*)` rule doesn't cover them. `agent-browser` is a declared dependency of the design plugin (`plugins/design/dependencies.json` — `"soft"`/auto-install for the general CLI/web install path, but **bundled unconditionally in the Maude desktop app**, which is the only place this allow-list applies since `design:chat` is native-only — so it is always present where this rule fires). Same trust argument DDR-184 already used for `Bash(maude:*)`: a named, vetted, purpose-built tool, not a generic shell escape hatch. **Residual, accepted explicitly:** nothing stops `agent-browser navigate https://not-localhost` — the tool has no built-in host restriction, and prefix-matching can't add one. This doesn't open a new risk category; it extends the one DDR-184 already accepted to a second tool. `npx playwright` (the documented fallback when `agent-browser` itself is missing) is deliberately excluded — `npx` executes arbitrary, non-pinned npm packages, a categorically bigger escape hatch than a fixed installed binary.

**2. `maude design curl-local <url> [curl-args...]`** (`apps/studio/bin/_curl-local.mjs` + `curl-local.sh`, dispatched via `cli/commands/design.mjs`'s `BIN_VERBS`). Resolves every http(s) target argument's host via `dns.lookup(host, {all:true, verbatim:true})` and requires **every** returned address to classify as strictly loopback (IPv4 `127.0.0.0/8`, IPv6 `::1` or its IPv4-mapped form) — closing the multi-record DNS-rebinding gap. Deliberately **stricter** than `_fetch-asset.mjs`'s `classifyAddress` (which blocks loopback/private/link-local/CGNAT/etc. and allows public IPs — built for fetching attacker-controlled external URLs): `curl-local` requires loopback specifically and rejects ordinary private-LAN addresses too (192.168.x.x is a different, real host — not "my own machine"). Reuses `_fetch-asset.mjs`'s reviewed `parseIPv4`/`parseIPv6` literal parsers rather than reinventing address parsing. Covered automatically by the **existing** `Bash(maude:*)` rule — zero additional Bash-surface widening. Unlike `fetch-asset`, does NOT DNS-pin the connection or disable redirects — the target is the user's own local dev server (not an attacker-controlled external URL), and that server issuing its own internal redirects is ordinary, expected behavior. A static line in `buildStudioBrief` (`apps/studio/acp/bootstrap-brief.ts`) nudges the model to prefer the verb; raw `curl` still falls through to today's normal permission prompt.

**3. Read-only filesystem verbs** (`Bash(ls:*)`, `Bash(cat:*)`, `Bash(pwd:*)`, `Bash(find:*)`, `Bash(head:*)`, `Bash(tail:*)`, `Bash(wc:*)`, `Bash(tree:*)`, `Bash(file:*)`, `Bash(stat:*)`). `Read`/`Grep`/`Glob` are already auto-approved with **no path scoping at all** (a pre-existing DDR-184 fact, not something this DDR changes) — Claude can already read any file it can name via those tools. So this list adds no incremental read capability; it's a more convenient interface to power already granted, not the "these commands are safe in isolation" argument DDR-184 already rejected. Mutating verbs (`mkdir`/`touch`/`rm`/`mv`/`cp`/`chmod`) are excluded — mutation stays behind `Write`/`Edit` (with `_history/` rollback) or the prompt. **Accepted residual, named not hidden:** `find`'s own flags can mutate (`-delete`/`-exec`), and prefix-matching can't distinguish `find . -name '*.tmp'` from `find . -delete` — drop `find` from the list first if this is ever judged unacceptable.

**4. `WebSearch`, `WebFetch`.** Bare native tool names — no `Bash(...)` prefix matching involved, so none of the flag-order brittleness above applies. Already part of the session's available toolset (the adapter defaults to the full `claude_code` tool preset), so this is purely a permission change, not a capability-availability change the way DDR-180's `AskUserQuestion` gate was. Removes friction from `/design:setup-ds` Stage-2 research (`ux-research-agent` runs 6-8 `WebSearch` queries) and `draw-agent`/`reconstruct-agent` reference lookups. **Residual, accepted explicitly:** fetched web content is exactly the kind of untrusted external data a prompt-injection attack rides in on — but this risk is orthogonal to the approve/deny decision (a user manually approving a WebFetch doesn't vet its content either) and exists in every Claude Code session regardless of Maude.

## Addendum — security fan-out findings, fixed before commit

The mandatory security-auditor + ethical-hacker fan-out (§Consequences below) ran against the Decision section above **before** it was ever released to users (same-session, before the closing commit) and found real, severe bypasses in two of the four tracks. Fixed, not waved through — this addendum is the current, accurate state; the Decision section above is left unedited as the historical record of what was first proposed.

**CRITICAL — `Bash(agent-browser:*)` was a zero-confirmation, zero-click session-hijack primitive (ethical-hacker Finding D).** The Decision section's residual note ("nothing stops `agent-browser navigate https://not-localhost`... extends the [DDR-184] risk to a second tool") materially understated the actual severity: `agent-browser`'s OWN bundled onboarding skill (`plugins/flow/skills/agent-browser/SKILL.md`, hidden, auto-loaded) recommends a **persistent** Chrome profile as its *default* auth strategy for exactly the high-value origins that make this dangerous — "your app (dev + prod), any service the user has personal SSO with… GitHub web… ClickUp / Linear / Notion." A DDR-054 prompt injection could steer the auto-approving session into `agent-browser navigate <authenticated-origin>` + `agent-browser eval "fetch(...)"`, reading or exfiltrating a real, live session with **no human anywhere in the chain** — worse than this repo's own prior worst-case bar (DDR-179's "wrong default silently grants a standing exemption," which at least required a misclick). The security-auditor's independent pass separately found the bare `Bash(agent-browser:*)` grant reached far more than "browser automation against the canvas" — `cookies get`, `clipboard read`, `--cdp`/`--auto-connect` (attach to any already-running debuggable Chrome), and the `chat` sub-agent were all reachable through the same one prefix rule.

**Fixed:** `Bash(agent-browser:*)` is REMOVED from `MAUDE_DEFAULT_ALLOWED_TOOLS`. The two real, documented raw call sites (`motion-critic.md`, `edit.md`) now go through a new hardened wrapper verb, `maude design agent-browser-safe` (`apps/studio/bin/_agent-browser-safe.mjs`), covered for free by the existing `Bash(maude:*)` rule:
- A closed subcommand allow-list (`open`/`eval`/`screenshot`/`snapshot`/`get`/`wait`/`close`) — nothing that reads cookies/clipboard/storage, attaches to an external Chrome, uploads/downloads files, or spawns `chat` is reachable at all.
- A closed reject-list for any argument that could override this wrapper's own constraints (`--profile`/`--session-name`/`--allowed-domains`/`--action-policy`/`--confirm-actions`/`--confirm-interactive`/`--cdp`/`--auto-connect`/`--proxy`/`--engine`) — fails closed on any of these, anywhere in argv.
- Forces `--allowed-domains localhost,127.0.0.1` — agent-browser's own NATIVE domain-scope enforcement, verified live (`agent-browser open https://example.com` through the wrapper is refused by agent-browser itself: `✗ Domain 'example.com' is not in the allowed domains list`).
- Explicitly **deletes** (not empty-strings — agent-browser validates an empty session name as invalid, not unset) any ambient `AGENT_BROWSER_PROFILE`/`AGENT_BROWSER_SESSION_NAME`/`AGENT_BROWSER_ACTION_POLICY`/`AGENT_BROWSER_CONFIRM_ACTIONS` before spawning, so a persistent profile configured in the user's own `~/.claude/settings.json` (which DDR-144's `settingSources:['user']` legitimately still reads for the user's own manual terminal use) cannot leak into this wrapper's calls.

**CRITICAL — `curl-local`'s "real host enforcement" claim had two independent, live-confirmed bypasses (security-auditor findings 1–2, ethical-hacker findings B–C).** The original implementation validated the hostname, then forwarded the caller's full argv verbatim to a real `curl` process:
1. **`-K`/`--config <file>`** — curl reads additional directives, including a different `url = "..."` target, from a config file; the argv scanner only recognized tokens that parse as URLs, so a validated loopback target plus `-K some.conf` let curl ALSO fetch whatever `some.conf` said (a file that could simply be checked into the served, DDR-054-untrusted project).
2. **`--resolve`/`--connect-to`** — force curl's actual TCP destination independent of the validated hostname, AND, even without an explicit override, Node's validation lookup and curl's own independent DNS resolution are two separate lookups with no pinning between them — the same TOCTOU bug class as CVE-2026-27826 (an MCP-server SSRF guard bypassed identically via DNS rebinding).

**Fixed:** `_curl-local.mjs` no longer forwards argv verbatim. It now allowlist-rejects (`validateArgv`) `-K`/`--config`/`--resolve`/`--connect-to`/`--next`/`-L`/`--location`/`--location-trusted`/`--max-redirs`/`-x`/`--proxy`/`--proxy-user`/`--socks4`/`--socks4a`/`--socks5`/`--socks5-hostname`/`-T`/`--upload-file` outright (a blocklist of KNOWN bypasses is exactly how the first cut missed these — the point is these are now REJECTED, not silently allowed-by-omission of a check), and PINS the connection itself via curl's own `--resolve host:port:IP`, set to the address `resolveLoopbackIp` already validated (mirrors `_fetch-asset.mjs`'s `curlDownload` pinning, opposite trust direction) — closing the TOCTOU regardless of DNS TTL. Also forces `-q` (no `.curlrc` auto-load — closes a related persistence angle the security-auditor flagged), `--proto '=http,https'`/`--proto-redir '=http,https'`, `--max-redirs 0`, and `--noproxy '*'`.

**MEDIUM — `Bash(find:*)`'s residual was mischaracterized (both reviewers, independently).** The Decision section named `find`'s risk as "own flags can mutate (`-delete`/`-exec`)" — comparable in the text's own framing to `mkdir`/`rm`. Both reviewers found this understated the actual severity: `find … -exec <any command> {} \;`/`-execdir`/`-ok` is **unrestricted arbitrary command execution with attacker-chosen argv**, not "mutation" — reopening exactly the blanket-Bash risk DDR-184 was built to prevent, through one closed-looking prefix rule. The ethical-hacker pass separately found `find`'s metadata predicates (`-perm`, `-newer`, `-user`) enable full-filesystem reconnaissance (SUID/SGID enumeration, recent-activity fingerprinting) that `Read`/`Grep`/`Glob` cannot replicate — a capability gap the "equivalent power" argument for the rest of the fs list doesn't cover.

**Fixed:** `find` is REMOVED from the fs verb list — not patched, because neither residual is fixable via prefix-matching (it can't inspect `find`'s own flags). The Decision section's own text ("drop `find` from the list first if this residual is ever judged unacceptable") is exactly what happened.

**MEDIUM — `WebFetch`/`WebSearch`'s residual named only the response side, not the request side (ethical-hacker Finding E).** The original residual note covered "fetched content is untrusted." It didn't name that the OUTBOUND request itself is a pure exfiltration channel independent of any response — a URL with attacker-chosen query-string content leaks the instant the request fires, no jailbreak or response-parsing needed. **Not fixed as a mechanism change** (no tractable server-side way to distinguish a legitimate WebFetch from a beaconing one without breaking the feature) — named explicitly here instead, per the reviewer's own recommendation, so it's an acknowledged residual rather than an omission that reads as "not considered."

**LOW — attention-notification burst (ethical-hacker Finding G).** DDR-179/180 cap pending requests at 10 permissions + 5 elicitations, so a single adversarial turn can legitimately queue up to 15 distinct approval decisions — this feature's own notification fires on every new one. **Fixed:** `app.jsx`'s `handleAssistantAttention` now rate-limits the OS `Notification` itself to at most one per 30s (`ATTENTION_NOTIFY_COOLDOWN_MS`); the in-app badge is unaffected (still reflects every new request instantly) — a burst now reads as one attention-getting ping, not fifteen.

**Verified clean (no finding):** the notification body is a static, generic string with no tool-call content, file path, or request payload interpolated — no information-disclosure path from the attention-notification feature itself. The `2d124965`-landed `handleAssistantAttention`/prop-wiring slice (see the commit-history note below) was reviewed and found clean independent of the rate-limit fix.

**Named, deliberately NOT changed:** `curl-local`'s scope is "any loopback address," not "only Maude's own dev-server port" (ethical-hacker Finding A) — the user's explicit ask was checking arbitrary local dev servers, not just Maude's own, so narrowing the scope would defeat the feature. Accepted and now named explicitly in `_curl-local.mjs`'s own header comment and in the Decision section context above, rather than left implicit.

New test coverage: `apps/studio/bin/_curl-local.test.mjs` (argv-allowlist rejection tests for every entry in `REJECTED_FLAGS`, including the exact `-K`/`--resolve` PoCs from both reports) and `apps/studio/bin/_agent-browser-safe.test.mjs` (subcommand-allowlist + flag-reject tests, including the exact `--profile`/`--cdp` PoCs). `apps/studio/test/acp-session-allowed-tools.test.ts` now also asserts NO raw `agent-browser` invocation remains in `motion-critic.md`/`edit.md`.

## Addendum, round 2 — the round-1 fixes were themselves bypassed; both wrappers redesigned

A mandatory re-verification pass (requested at `/flow:done`, since this DDR's status can't be treated as final without it) found that round 1's fixes for `curl-local` and `agent-browser-safe` were **live-reproducibly bypassable** — not theoretical gaps, actual working exploits against the shipped code. This is the second time this DDR's own security posture was found materially weaker than its text claimed; both findings and the root-cause pattern are recorded here in full rather than quietly patched, because the pattern itself is the lesson.

**CRITICAL — `curl-local`'s round-1 argv allowlist (`validateArgv`, `a.split('=')[0]`) never recognized curl's own CONCATENATED short-flag syntax.** curl accepts `-K<path>` (no space, no `=`) as equivalent to `-K <path>` — a real, common, fully-supported curl idiom. `validateArgv`'s check only stripped a `=`-joined suffix, so `-Kevil.conf`, `-xhttp://evil.example` (short form of the rejected `--proxy`), and `-T/etc/passwd` (short form of the rejected `--upload-file`) all sailed through unrejected. **Live-reproduced**: `node _curl-local.mjs "http://127.0.0.1:PORT/" "-K$PWD/evil2.conf"` fetched both the validated loopback target AND the config-smuggled second target — the EXACT original bypass this DDR's first addendum claimed was closed, reproduced verbatim against the "fixed" code.

**CRITICAL — a separate, independent gap in the same round-1 pass: `--noproxy` (the flag `curl-local` forces to `*`) was never itself added to `REJECTED_FLAGS`.** curl is last-flag-wins for repeated options, so a caller-supplied `--noproxy ""` placed after the wrapper's own forced `--noproxy '*'` silently re-enabled an ambient proxy. **Live-reproduced**: with `HTTP_PROXY` pointed at a fake local proxy, `node _curl-local.mjs http://127.0.0.1:PORT/ --noproxy ""` routed the "loopback-only" request through the fake proxy instead of connecting directly.

**HIGH — the round-1 `_agent-browser-safe.mjs` env-clearing list was a strict subset of what agent-browser's own `--help` documents.** `AGENT_BROWSER_AUTO_CONNECT` (env equivalent of the already-rejected `--auto-connect`), `AGENT_BROWSER_PROXY`/`HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` (env equivalents of the already-rejected `--proxy`), and `AGENT_BROWSER_ENGINE` (env equivalent of the already-rejected `--engine`) were never cleared. **Live-reproduced**: a stub `agent-browser` confirmed all three leaked through unmodified from the ambient environment while `AGENT_BROWSER_PROFILE` was correctly cleared — an ordinary corporate/VPN `HTTP_PROXY`, or any prior terminal use that set `AGENT_BROWSER_AUTO_CONNECT`, defeated the wrapper with zero attacker action needed.

**Separately found (same review pass, before round-2 fixes were designed): `-p`/`--provider <name>`** — undocumented in the round-1 flag reject-list at all — routes an ENTIRE agent-browser session through a remote cloud browser provider (`browserbase`/`kernel`/`browserless`/`agentcore`) instead of local Chrome, a capability class round 1 never considered.

### Root cause, named plainly

Both round-1 wrappers used the same shape: allowlist the entry point (subcommand / target host), then REJECTLIST specific known-dangerous arguments in the remainder, forwarding everything else verbatim to the real binary. A rejectlist against a THIRD-PARTY CLI's own evolving argument grammar — short flags, concatenation, bundling, `=`-forms, env-var equivalents, provider/plugin flags — is an unbounded surface. Each fix closed the specific bypass found and left the next binary quirk for the next review pass to discover. This is not a "try harder to enumerate" problem; it is a wrong-shape-of-fix problem.

### Fixed: both wrappers redesigned to eliminate the bypass CLASS, not enumerate instances

- **`_curl-local.mjs`** no longer accepts raw curl arguments at all. It now defines and parses its OWN small, Maude-owned flag vocabulary (`parseRequestArgv`: `<url> [--method M] [--header "K: V"]... [--data D] [--user-agent UA] [--max-time N] [--output PATH] [--insecure] [--include] [--verbose]`) — plain, unambiguous `--flag value` pairs with no short forms, no concatenation, no bundling, nothing left to mis-parse — then constructs the real curl invocation (`buildCurlArgs`) from FIXED, hardcoded flag names, with every caller-supplied value riding as its own `spawnSync` argv array element (never string-interpolated, so a value containing e.g. `-K` or shell metacharacters is inert data to curl, not a new flag token). The caller can no longer NAME a curl flag at all, so there is no longer an enumeration to keep pace with. Uses `--data-raw` (never `-d`/`--data`, which treats a leading `@` as a local-file-read instruction) — live-verified: a `--data "@/etc/passwd"` value round-trips as the literal 13-character string, not file contents.
- **`_agent-browser-safe.mjs`** replaces its flag reject-list with a fixed positional-argument ARITY per subcommand (`open`=1, `eval`=1, `screenshot`=0-1, `snapshot`=0, `get`=1-2, `wait`=1, `close`=0) and rejects ANY argv beyond that count — flag-shaped or not. `-p browserbase`, `--provider browserbase`, `--profile Default`, `--cdp 9222` are all rejected the same way now: as unexpected extra arguments, not as individually-named forbidden flags. A legitimate `eval` expression starting with `-` (e.g. `"-1 + 2"`) still works — arity is a COUNT check, never a prefix check, so it can't confuse a positional value's own content with a flag. `CLEARED_ENV_KEYS` grew from 5 to 14 entries (adds the 3 newly-found equivalents plus both cases of all 4 standard proxy vars).

Both fixes live-verified end to end against the real `curl`/`agent-browser` binaries on this machine (not just unit tests): the exact `-K`/`--noproxy`/`-p` PoCs from this addendum now fail with a clear "not recognized" error before either real binary is ever invoked; the legitimate documented workflows (a loopback GET/POST, `eval`/`screenshot`/`open` with no extra arguments) still function identically to before.

**Revisit-when addition:** if either wrapper's flag-free/arity-only model is ever felt too restrictive for a genuine new need (e.g. `agent-browser-safe snapshot -i` for the interactive-elements-only filter), add it as an explicit, narrowly-scoped, reviewed extension to that subcommand's arity/shape — never by reopening a "reject known-bad, allow everything else" flag model on either file again.

## Consequences

- The dominant real-world friction in `/design:setup-ds`/`/design:edit`/`/design:new` ACP sessions — `agent-browser` calls (now via the hardened wrapper), `WebSearch`/`WebFetch` research, basic fs inspection, and localhost `curl` (now via the hardened wrapper) — runs without a prompt, while arbitrary Bash, non-loopback targets, and unlisted commands still route through the real approve/deny gate (DDR-179).
- `apps/studio/test/acp-session-allowed-tools.test.ts`'s source-of-truth guard now asserts the Bash rules are EXACTLY `Bash(maude:*)` + the closed fs list (no `agent-browser`, no `find`) — nothing else — and that `WebSearch`/`WebFetch` are present. A future widening beyond this fixed set fails loudly.
- **Mandatory security-auditor + ethical-hacker fan-out**, matching every prior ACP-permission DDR (179, 180, 184) — ran this session, found the findings documented in the addendum above, all fixed before this DDR's status was finalized.

## Alternatives rejected

- **Curated `curl` prefix-list** (`Bash(curl http://localhost:*)` etc.) — the literal DDR-184-rejected shape; flag-order and `127.0.0.1`-vs-`localhost` text variants defeat it outright.
- **`PreToolUse` hook via `_meta.claudeCode.options.hooks`** — structurally infeasible; see the wire-boundary finding above. Do not attempt this without first re-verifying the adapter's process topology hasn't changed (spawn vs. in-process import) on any future `@agentclientprotocol/*` version bump.
- **Bare unscoped `Bash(curl:*)`** (SHIPPER's literal ask) — rejected because the `curl-local` verb achieves the same friction removal with real enforcement at roughly the same implementation cost; kept as the documented fallback if the verb approach ever proves materially harder to maintain than expected.
- **Provisioning a hook into the user's own `~/.claude/settings.json`** — rejected: would leak Maude's gate into the user's unrelated plain-terminal `claude` sessions (global, not session-scoped), and conflicts with the spirit of `settingSources:['user']` narrowing being about *reading* user config, not Maude *writing* into it.
- **Routing `agent-browser` through new `maude design <verb>` wrappers instead of a direct Bash rule** — INITIALLY rejected for this pass on the reasoning that some call sites (`edit.md`'s `agent-browser eval "matchMedia(...)"`) are ad-hoc, dynamic expressions that don't fit a fixed verb. **Reversed by the security addendum above**: the dynamic-expression concern is real but doesn't require a FIXED verb per expression — `agent-browser-safe eval "<any expression>"` still accepts an arbitrary `eval` argument, it's the SUBCOMMAND set and the override-capable flags that are closed, not the expression content. The original rejection conflated "the eval argument varies" with "the wrapper can't work," which doesn't follow.

## Revisit when

- The adapter/SDK changes how `hooks`/`allowedTools` are forwarded, or `Bash(prefix:*)` matcher semantics change (mirrors DDR-184's own revisit clause).
- `agent-browser` ships its own equivalent of `--allowed-domains`/profile controls that make `_agent-browser-safe.mjs`'s reject-list redundant, or changes its CLI surface in a way that adds a NEW subcommand/flag capable of reading credentials/attaching to another process — re-audit `ALLOWED_SUBCOMMANDS`/`REJECTED_FLAGS` against the new `--help` output on any agent-browser version bump.
- `curl-local`'s "any loopback address" scope (accepted, named explicitly above) is judged too broad for a future multi-user/hub-reachable ACP surface (mirrors DDR-125's "untrusted to peers" line) — at that point, scoping to an explicit port allowlist (config-driven, not hardcoded to Maude's own port) is the likely next step.
- The `curl-local`/`agent-browser-safe` reject-lists are blocklists of KNOWN bypasses, not a formal proof of completeness — if either tool's CLI gains a new flag with similar override power to what's already rejected, it needs adding here too. Re-read this DDR's addendum before assuming either wrapper's reject-list is exhaustive.
