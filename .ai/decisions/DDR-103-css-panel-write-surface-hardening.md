## Context

The Phase-12.2 `/flow:validate` security fan-out (defender `security-auditor` scoped to the diff + adversarial `ethical-hacker`) returned four findings against the in-canvas source-write surface. Two are genuine and addressed here; two are pre-existing, cross-cutting properties of the dev-server architecture scoped as follow-ups so a pre-existing concern doesn't block a feature that didn't introduce it.

The write surface in question is the three main-origin-only routes `POST /_api/edit-css`, `/_api/edit-text` (both Phase 12 / DDR-101) and `/_api/edit-attr` (new in Phase 12.2 / DDR-102). All three rewrite a single JSX attribute (or text node) in the user's source `.tsx` via `canvas-edit.ts`. They are absent from `CANVAS_SAFE_API` + `startCanvasServer`'s route map (DDR-054), so the untrusted canvas *iframe* cannot reach them.

## Findings

- **F3 (correctness + injection, both reviewers — FIXED here).** `editStringAttr`'s two *replace* branches (`Literal`/`StringLiteral` and `JSXExpressionContainer`) emitted `JSON.stringify(value)`, while its two *insert* branches used `escapeAttr`. `JSON.stringify` is JS-string escaping (`\"`), which is **invalid inside a JSX attribute** — a `value` containing a `"` (or `<`/`>`) corrupted the source on write (the attribute string terminated early / produced malformed JSX). The four branches disagreed on the escaping contract for the same target context.
- **F2 (CSRF / no Origin guard on POST write routes — MITIGATED here for the edit-* surface).** `readJson` parses any POST body via `req.text()` → `JSON.parse` with **no `Content-Type` check**. A malicious top-level page in another browser tab could therefore forge a `text/plain` CORS *simple-request* POST to `http://localhost:<port>/_api/edit-*` (no preflight) and drive a source write. Mitigating factor: the write needs a valid 8-hex `data-cd-id`, which is not readable cross-origin (the GET routes carry no permissive CORS headers), so blind exploitation is a 2³² guess. Real class nonetheless, shared by every write route — pre-existing, not a Phase-12.2 regression.
- **F1 (edit-text relay confused-deputy — DEFERRED, Phase-12 surface).** The shell's `onMessage` handler (`app.jsx`) accepts `postMessage`s from `cfg.canvasOrigin` and relays `{dgn:'edit-text'}` to `/_api/edit-text`. Under DDR-054 the canvas origin is *untrusted*, so untrusted canvas code can make the shell a confused deputy that persists escaped-text edits to the active canvas's source. Bounded (escaped text, single active canvas, text nodes only) and **specific to `edit-text` (Phase 12)** — Phase 12.2's `edit-css`/`edit-attr` are shell-direct (called from the `CssKnobs` component, never relayed), so 12.2 added no new confused-deputy.

## Decision

1. **Escaper consistency (F3) — all four `editStringAttr` branches use `escapeAttr`.** The two replace branches now write `` `"${escapeAttr(value)}"` `` (entity-escaping `"`→`&quot;`, `<`/`>`→`&lt;`/`&gt;`), matching the insert branches. The JSX-attribute context has exactly one correct escaping contract and the function now states it once. `JSON.stringify` is removed from this path. Regression-tested in `test/canvas-edit.test.ts`: a `"`-bearing value round-trips as `&quot;` through the literal-replace, expression-container-replace, and insert branches, and never emits `\"`.

2. **CSRF Origin guard (F2) — `sameOriginWrite(req)` on the three edit-* routes (DDR-054 defense-in-depth, layer 2).** A request whose `Origin` header is **present and ≠ the server's own origin** is rejected `403`. A request with **no** `Origin` (curl / programmatic / `bun:test` — none of which are the CSRF threat, which requires a browser, and a browser always sends `Origin` on a cross-origin POST) passes. This blocks the browser-driven cross-site forgery while leaving the legit same-origin shell `fetch` and all non-browser clients working. It is the OWASP-recommended control for exactly this "no-CSRF-token localhost dev-server" shape and is layered *on top of* the DDR-054 origin-split: the split closes the untrusted **iframe**, this closes the untrusted **top-level page**. Unit-tested in `test/csrf-write-guard.test.ts` (forged / look-alike-host / wrong-port / wrong-scheme → reject; same-origin / absent → allow).

   **Deliberately NOT applied to `/_api/asset`** — that route is canvas-origin-reachable by design (drag-drop/paste/picker upload runs inside the iframe), so an Origin guard there would break the legit upload. Its trust mitigation stays the `api.saveAsset` cap stack (magic-byte sniff, 10 MB ceiling, content-addressed name, traversal guard, no-SVG) per DDR-088. The guard is intentionally scoped to the three source-write edit routes whose only legit caller is the same-origin shell.

3. **F1 + residual-F2 scoped as pre-existing follow-ups, not blockers.** Blanket CSRF/Origin hardening across the *other* ~9 write routes (`export`, `canvas`, comment writes, annotation-svg, …) and a proper fix for the `edit-text` relay confused-deputy (drop the relay → make text-edit shell-direct like CSS, or gate the relay on a user-gesture token) are **cross-cutting dev-server changes** touching surfaces Phase-12-or-earlier introduced. Per the project's "no-break exhaustive verify" rule for risky dev-server refactors (inventory + per-feature plan first), they are not bolted onto this feature's validate. The defender pass scoped to the Phase-12.2 diff returned **0 blockers**; the two adversarial findings are architectural and pre-existing. Tracked in the security-review log and the plan's follow-up list. This is the `/flow:validate` Step-5 "requires a DDR explaining the disposition" path, taken here consciously rather than by force-passing the gate.

## Consequences

- `sameOriginWrite` is exported from `http.ts` and unit-tested as a pure function of the `Request` (no subprocess boot). This was also the right call against a **pre-existing test-harness flake**: `test/_helpers.ts` `nextPort()` (seed `4500`, module-scoped) collides across bun's test-worker processes, so adding *any* 124th server-booting test file perturbs scheduling and surfaces a cross-worker port collision in `canvas-meta-api.test.ts` (`GET returns the meta document` → 200 with a title-less body because the fetch hits a different worker's server on the same port). A booted-server integration test for the guard would have re-exposed it. The unit test sidesteps it; the harness race is logged as its own follow-up (fix = bind `--port 0` + read the assigned port back from `_server.json`, a `bootServer` signature change across ~50 callers — its own scoped change, not a drive-by).
- New trust-boundary invariant: **the three source-write edit routes are same-origin-write-only.** Future write-route additions reachable only from the shell should call `sameOriginWrite`; routes that must be canvas-origin-reachable (like `/_api/asset`) must NOT, and rely on payload caps instead.

## Alternatives considered

- **Enforce `Content-Type: application/json` at `readJson` instead of an Origin check.** Rejected as the primary control: it's a choke point shared by *every* JSON route (including GET-shaped reads and canvas-origin-reachable routes), so tightening it risks breaking legit clients far outside this surface, and a same-origin attacker on the shell origin could still send JSON. The Origin check is targeted to the exact threat (cross-site forgery) and the exact routes.
- **Fix F1/F2 fully now.** Rejected for this feature: cross-cutting, higher regression risk against the 1300+-test dev-server suite, and not a Phase-12.2 regression. Deferred with a DDR rather than silently passed.
