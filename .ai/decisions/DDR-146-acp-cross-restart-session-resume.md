# DDR-146 — ACP chat: persist + resume the claude session across app restarts

**Status:** accepted
**Date:** 2026-07-03
**Relates:** DDR-123 (ACP chat runs on the user's own `claude` CLI subscription), DDR-125 (multichat + security posture — this closes its "Cross-restart claude memory is NOT yet wired" tracked follow-up), DDR-142 (context pipeline / session bootstrap brief), DDR-115 (runtime-state taxonomy), rca/issue-acp-chat-cross-restart-session-resume

## Context

Reported bug: killing and reopening Maude Desktop (e.g. to pick up an update), then continuing a chat, produced a reply with no memory of the visible prior conversation — the agent re-derived context from `git status` instead of recalling anything. RCA (`.ai/logs/rca/issue-acp-chat-cross-restart-session-resume.md`) traced the cause: `AcpBridge.sessions` (chatId → ACP sessionId) was purely in-memory, scoped to one bridge instance (one per WebSocket connection, i.e. one per app lifetime). Every fresh connection called the adapter's `newSession()` unconditionally. The on-disk transcript (`_chat/<id>.jsonl`) made the panel LOOK unchanged, but the underlying `claude` process backing a "continue" was genuinely new. This gap was already known and explicitly deferred at DDR-125 (2026-06-23): *"The adapter supports `loadSession`; persisting + resuming the session id is the tracked follow-up."*

## Decision

**Persist the ACP sessionId per chat, resume via the adapter's `loadSession`, fall back to `newSession` on any failure.**

- A new sidecar, `<designRoot>/_chat/<chatId>.session.json` (`{ sessionId, updatedAt }`), written after every successful `newSession()` (`AcpBridge.writePersistedSessionId`, `apps/studio/acp/bridge.ts`). Per-machine runtime state — no new gitignore/DDR-115 entry needed, it already falls under the existing `_chat/` directory-level ignore in all three lists (`.gitignore`, `cli/lib/gitignore-block.mjs`, `apps/studio/git/service.ts` `isMaudeRuntimeState`).
- `AcpBridge.sessionFor(chatId)` now: (1) reuse the in-memory session if this bridge already created one this lifetime (unchanged); (2) else read the sidecar — if present, call `conn.loadSession({...newSessionParams(...), sessionId: persisted})`; (3) on success, resume that id; on any thrown error (adapter/CLI can't find the session — pruned, `claude` reinstalled, etc.), append a `resume-failed` audit line to the transcript and fall through to `newSession()` exactly as before.
- `index.ts` wires the sidecar path through both the `prompt` and `warm` (composer-typing warm-up) message handlers, mirroring the existing `transcriptPathFor`/`setTranscriptPath` wiring — a resume can be triggered by either.

**Replay suppression.** Verified against the installed `@agentclientprotocol/claude-agent-acp@0.49.0` sources: its `loadSession` handler calls `getOrCreateSession` (which itself calls `createSession(..., {resume: sessionId})` — this is the actual mechanism that gets the underlying SDK to `resume:` the real `claude` conversation) and THEN `replaySessionHistory(sessionId)`, which re-emits the ENTIRE prior conversation back through the same `client.sessionUpdate` callback our bridge already uses for live streaming (`acp-agent.js`, functions `loadSession`/`replaySessionHistory`, confirmed live in `node_modules`). Left unguarded, this would double-render every historical message in the panel and double-append it to the transcript jsonl. `AcpBridge` gates this with a `replaying` boolean, set for the duration of the `loadSession()` call, checked inside the `sessionUpdate` callback (skip both `onUpdate` forwarding and `appendTranscript` while true) — since the on-disk transcript and the already-rendered panel already have that history, the replay only needs to prime the adapter's own in-process state, never resurface client-side.

**What's NOT changed.** The studio bootstrap brief (`_meta.systemPrompt.append`) is still passed on every `loadSession` call, same as `newSession` — on inspection this doesn't concatenate/duplicate across resumes (it's a per-request `_meta` option, not literal transcript content), so there's no correctness reason to special-case it for resume vs. new.

## Consequences

- ✅ Closes the DDR-125 follow-up: an app kill/restart (or a browser hard-reload) now resumes the actual `claude` conversation, not just the transcript display.
- ✅ Graceful degradation: any resume failure (pruned session, reinstalled/upgraded `claude`, adapter without `loadSession`) silently falls back to today's exact `newSession()` behavior — no new failure mode, only a fixed one.
- ⚠️ Session-fingerprint dependency on adapter internals: the resume path relies on the installed adapter's `getOrCreateSession`/`replaySessionHistory` behavior, which is adapter-internal and undocumented (same caveat DDR-142 already flagged for the `_meta` contract). An adapter bump that changes this contract degrades to "always falls back to newSession" (safe) rather than a silent break, since every call is wrapped in try/catch.
- ➡️ Not addressed here (unchanged from before): resuming across a DIFFERENT machine, or after `<designRoot>/_chat/` is deleted/not synced (by design — DDR-115 keeps it per-machine).

## Testing

`apps/studio/test/acp-bridge.test.ts` — 3 new cases against the shared mock ACP agent (extended with a `session/load` handler): persisted-id resume succeeds and is used verbatim; a resume failure (`not-found` sentinel) falls back to `newSession` and re-persists the new id; a brand-new chat with no sidecar behaves exactly as before. Also fixed `acp-commands.test.ts`, which was leaking a stray file into a real (non-tmp) `designRoot` because of the new `warm`-path write once wired.

## Security fan-out (`/flow:done`, 2026-07-03)

Defender: **PASS** (0 blockers; 2 low-severity notes — unbounded `sessionId` string forwarded to the wire, and a local-only `resume-failed` error string in the transcript, confirmed never rendered client-side since `readChatMessages` only consumes `user`/`stop`/`agent` roles). Adversarial: **NEEDS-FIXES → fixed before close-out**:

- **HIGH — `replaying` could wedge permanently `true`.** If the adapter's `loadSession` RPC never settles (dead transport, adapter crash mid-call), the `finally` that resets `replaying` never ran, silently black-holing every future `sessionUpdate` for that bridge (the `if (this.replaying) return;` guard in the `sessionUpdate` callback). **Fixed:** `loadSession` is now wrapped in a 15 s `withTimeout` (mirrors the existing `withTimeout`/`TIMED_OUT` pattern in `apps/studio/git/service.ts`) — a hang now surfaces as an ordinary resume failure and falls back to `newSession`, so `replaying` is bounded to reset within 15 s regardless of adapter/transport behavior.
- **MEDIUM-HIGH — no mutual exclusion around `sessionFor`.** A `warm` frame (composer autocomplete) and a `prompt` frame racing for the same chat on one bridge could both call `establishSession`, each toggling the single shared `replaying` flag independently — one call finishing (flipping `replaying → false`) while the other's resume replay was still arriving would let stale-session history leak through `onUpdate`/`appendTranscript`. **Fixed:** `sessionFor(chatId)` now caches the in-flight promise per chatId (mirrors `ensureStarted`'s existing `this.starting` pattern) — a concurrent call for the same chat awaits the FIRST call's attempt instead of re-entering it. Verified with a new test that fires `warmUp()` and `prompt()` concurrently for the same chat and asserts only one resume happens and the turn still completes normally.
- **MEDIUM — `_chat/<chatId>.session.json` is a new control-plane input `readPersistedSessionId` didn't validate the shape of** (same underlying concern as the defender's low-severity A12). Bounded exploitability even unmitigated: `cwd` is always the server's own `repoRoot`, never sourced from the file, so a planted value can only ever attempt to resume a REAL pre-existing local `claude` session by (impossible-to-guess) UUID collision, or fail harmlessly into `newSession` — but the input was unvalidated at a privileged boundary regardless. **Fixed:** `readPersistedSessionId` now rejects any value that doesn't match `^[A-Za-z0-9_-]{1,128}$` (the shape of an adapter-generated `randomUUID()`), tested with an injection-shaped string (embedded newline + shell metacharacters) that must fall back to `newSession`.
- Cross-cwd/cross-project session-fingerprint scoping (an even more speculative angle the attacker flagged as "unverified, flag for a dedicated test") is accepted as residual, untested risk — it would require access to a real (non-mock) `claude-agent-acp` install to exercise the adapter's own `getOrCreateSession` fingerprinting, which is out of scope for this repo's CI (same boundary DDR-142 already draws around adapter-internal, undocumented behavior).

Reports: read-only agent output, not persisted as standalone files (folded directly into this DDR per the size of the change — no `.ai/logs/security-reviews/` entry was warranted for a fix this scoped).
