## Context

Editing an element in Maude Studio was functional but incomplete versus what users already know from Figma / Webflow / Pencil.dev, and in two cases actively broken (a pan-reset on absolute-element move; an overflow-select layout shift). The everyday designer edits — `position`, inset, `transform`, `object-fit`, drag-resize, swap-the-photo, delete-this, add-a-frame — were either unreachable (raw "Advanced" escape hatch only), missing (no resize handles, no delete/insert), or unpredictable (editing an element inside a reused component silently changed every instance with no signal). The user's brief was explicit: make editing "předvidatelné" (predictable) and familiar — "resize elementu dragem", swap imagery, start a clean artboard and add elements, and always know whether an edit is local or shared.

The whole feature was achievable by **extending already-hardened lanes** rather than inventing plumbing — which is what made a large plan low-risk. This DDR records the load-bearing decisions (and the rejected alternatives) so a future reader understands *why* each new surface took the shape it did. It is one DDR for one cohesive plan; the sections are independent decisions.

## Decision

### 1. Curated-knob tier expansion — reverse DDR-104 §3's OUT-list

DDR-104 §3 deliberately deferred `position`, `top/right/bottom/left`, `transform`, `text-transform`, `text-decoration`, `font-style`, `object-fit`, `aspect-ratio`, `object-position` to the raw "Advanced" custom-property hatch, on the theory they were power-user escapes. **User feedback reversed that premise:** box, framing, and positioning are *core* designer edits, not escapes — the exact recurring changes the brief names. These are now first-class curated knobs.

Mechanically this is client-only over DDR-103's already-generic write path: extend `KNOB_PROPS` (`dom-selection.ts`) so `styleMapsFor` captures the promoted props into `authored`/`computed` (which also moves them *out* of the Advanced bucket), add `CSS_*` option lists, and render new rows/sections in `CssKnobs`. A **Position** section carries a `top/right/bottom/left` inset widget built by mirroring the existing margin/padding box-model `side()` primitive (a new bare-longhand `inset()` variant, negative-allowed, `auto`-default), plus `position` (`csel`) and `z-index` (`num`). A conditional **Media** section (`<img>`/`<video>`/`<picture>`/bg-image only) carries `object-fit`/`aspect-ratio`/`object-position`. *Rejected:* a layout-mutating "convert to absolute on drag" (Webflow-style) — a raw `position` knob makes that intent explicit instead of implicit, which is less surprising in a TSX-authored mock.

### 2. On-canvas resize — reuse the annotation-resize geometry, write via the existing reposition lane

Element resize (genuinely missing — there were zero element resize handles) models on `use-annotation-resize.tsx`: 8 screen-space handles (4 corner + 4 edge) that stay a constant 8 px at any zoom, with FigJam modifier grammar (Shift = aspect-lock, Alt = from-center). The pure math (`computeElementResize`) is unit-tested DOM-free; the overlay (`ElementResizeOverlay`) is **camera-agnostic** (reads `getBoundingClientRect` + the selection set, no viewport-controller dependency) so the same component mounts in both `CanvasShell` and the lite specimen mount (§3). In-flow elements resize by writing explicit `width`/`height` only (never convert-to-absolute); an out-of-flow element additionally moves `left`/`top` on a top/left-edge drag. Commit rides the **existing** `reposition-request → /_api/edit-css` lane extended to chain up to four props on the serialized `editApplyChainRef` — so resize inherits DDR-105 no-flicker and DDR-050 undo for free.

Artboard resize (D4) writes the `width`/`height` **JSX props** on `<DCArtboard>` (per DDR-027 artboard size is JSX-authoritative, not a `layout` field), addressed by the artboard's `id` prop — because the rendered `<article data-dc-screen>` carries **no `data-cd-id`**. This forced a new `writeNumericAttr` engine primitive (`width={430}`, not the string `"430"` that `editStringAttr` would have written) and a dedicated main-origin `/_api/resize-artboard` route, which is why D4 was batched with the structural routes (§5), not shipped as a quick `edit-css` follow-up.

### 3. Specimen selection — a mount/router gap fix, `select-set` as the trust boundary

DS preview specimens (`system/<ds>/preview/*.tsx`) render bare markup, not `<DesignCanvas>`, so they have no `CanvasShell` selection router and `resolveHoverTarget`'s artboard-ancestry hard-requirement returns null. Rather than loosen that requirement (load-bearing for UI canvases), the lite comment-mount got its **own** specimen-select resolver (`pickSpecimenSelectEl`, generalizing `pickSpecimenEl` to anchor on the hit's own pipeline-stamped `data-cd-id` without artboard ancestry) behind a **capture-phase listener self-gated on `isBareSpecimen()`** — so it is the *only* select handler on a specimen and a pure no-op on a UI canvas. It is deliberately **not** added to the shared `COMMENT_CLAIMS` (which would `preventDefault`+`stopImmediatePropagation` a UI canvas's own select in capture phase). Everything downstream (`select-set` message, Inspector, `edit-css`/`edit-attr`) was already kind-agnostic. The security surface added is *producing a selection* on a specimen, which flows through the already-parent-source-gated `select-set` handler (DDR-054) — no new canvas-origin-reachable write.

### 4. Media swap — `edit-attr` src-replace / annotation-model href-swap, orthogonal to the photo-editor

Replacing an authored `<img>`/`<video>` re-points its `src` via the existing `editAttribute` src-replace path through `/_api/edit-attr`; a background image writes `background-image: url(assets/…)` via `edit-css`. Annotation `ImageStroke`/`MediaRefStroke` images have no `data-cd-id`, so they swap through the **annotation model** (`href` swap), never the source-write routes — the fault line between the three media representations is kept explicit. An `AssetPicker` dialog (browse the content-addressed `assets/` via a new read-only `GET /_api/assets`, plus upload via the existing `POST /_api/asset`) resolves every pick to a *local* `assets/<name>` path — never a remote hotlink (the CSP split origin blocks it). This is **orthogonal to `feature-photo-editor.md`**: that plan owns an image's *pixels/look* via its own `/_api/photo-edit`; this plan owns its *box/framing/source* via `edit-css`/`edit-attr`. The two Inspector additions (its "Photo" tab vs this plan's "Media" section) are coordinated to not fight over the same DOM slot.

### 5. General element delete / insert / new-artboard — structural ops with **whole-file-snapshot undo**, reusing the reorder command

Only video-comp `<Sequence>` clips had delete/insert before. General `applyDeleteElement` / `applyInsertElement` / `applyInsertArtboard` (+ the D4 `applyResizeArtboard`) are new engine ops in `canvas-edit.ts`, each reparse-gated, modeled on `applyRemoveClip`/`applyInsertClip`/`moveElement`. Two decisions matter:

- **Undo reuses the existing reorder command, not a new command file.** A structural edit renumbers positional `data-cd-id`s (DDR-019), so an inverse *descriptor* goes stale — exactly why reorder already logs a whole-file `{before, after}` under a server seq and reverts via `/_api/reorder-revert`. The reorder command (`op:'reorder'` record-edit) is already the generic "whole-file seq revert" command (the DDR-150 clip ops reuse it too). So all four new ops reuse it via `logUndo`; **no** new `delete-element-command.ts`/`insert-element-command.ts` files were needed — this supersedes the plan's Task-I2 five-part-wiring assumption. Reuse here is *correct*, not a shortcut.
- **Inserted elements carry no `data-cd-id`.** The synthesized JSX (`<div>`, `<p>Text</p>`, `<img src="assets/…"/>`) is written without an id; the pipeline stamps it on next transpile (DDR-019), and the op recomputes the new id by insert-offset match. A new empty artboard is a `<DCArtboard id label width height></DCArtboard>` in the `scaffold-design.ts` shape (**empty** — the user's explicit "začít s čistým" intent), with a screen-size preset table + a `patchCanvasMeta` grid slot.

All four routes are main-origin-only (DDR-054): absent from `CANVAS_SAFE_API` + `startCanvasServer`'s route map, `sameOriginWrite`+`isLoopbackHost` gated, `activePath`-pinned (never the iframe-supplied `m.canvas`), and asserted 403-from-canvas-origin in `canvas-origin-gate.test.ts`.

### 6. Reusable-component predictability (INV-3) — surface the scope + keep instance move/resize local; **no** override/detach

The user chose **Option A**: predictability comes from *showing* whether an edit is local or shared, and from routing instance move/resize per-occurrence — **not** from a new per-instance style-override or detach primitive (both explicitly out of scope). Two parts:

- **Edit-scope resolver + badge (H1/H2, shipped).** `resolveEditScope` composes the *same* primitives `resolveUsageId` ships — the element's enclosing `componentName` + that component's source usage count — to return `local` / `shared`('component', affects = usages) / `shared`('mapped', a single source element rendered N× via `.map()`, driven by a client-supplied `rendered` count, the DDR-139 §1 caveat). A parse failure degrades to `local` (a badge must never crash selection). It is exposed as a **read-only** `GET /_api/edit-scope` (no write, no undo, no rate-cap — a mere parse the shell runs on selection; main-origin-only like `/_api/assets`). The Inspector shows a strip across all tabs: "Local · this element only" vs "Shared · `<Comp>` · edits N places". *Rejected:* extending the `Selection` payload with the scope — the in-iframe selection builder has no parsed program; a small main-origin GET is the clean seam.
- **Instance move/resize stays local (H3, in progress).** Moving/resizing a component *instance* (a `<Card/>` usage, a frame-root) routes through the occurrence `idIndex`→`resolveUsageId` so the write targets that specific usage's own `left/top`/`width/height`, not the shared definition. Styling an *inner* element of a shared component is inherently global (no override primitive) — the badge is the answer there. This is deliberately paired with the resize/reposition drag lanes, since its live effect is only verifiable through them.

### 7. Structural-write budget — a rate-cap + source-size ceiling + `_history` prune (security, this session)

The G3 adversarial review flagged that the new structural verbs are the first that let an **untrusted active canvas** both *remove* and *grow* its own source: the shell relays a canvas's `dgn:*` request after gating only on `e.source === activeWin`, so a hostile on-load script can drive delete/insert in a loop with no user gesture (a silent design-shredder) and spam inserts to fill disk (each op snapshots a whole file to `_history/`, uncapped, + a whole-file RAM undo entry). The `/_api/asset` byte-upload lane already had `ASSET_SESSION_BUDGET` (DDR-088); the structural-edit lane — the *other* untrusted-origin disk-write surface — had none. **Decision:** mirror that posture on the structural ops:

- A **per-`createApi` token bucket** (`takeStructuralToken`, burst 40 / refill 8·s⁻¹, env `MAUDE_STRUCTURAL_BURST`) rate-caps all four structural ops → `429` when spent. A human does a few structural edits/sec; a scripted loop can't beat the refill.
- A **source-size ceiling** (`MAX_CANVAS_SOURCE`, 512 KB, env-tunable) refuses a *growth* op once the source exceeds it → `413`; delete/shrink always pass.
- **`_history` pruning** (`maxSnapshotsPerSlug`, 300 pairs, env `MAUDE_MAX_SNAPSHOTS`) bounds disk regardless of edit rate.

Enforcement is server-side (the durable point regardless of how the request arrives), not a client user-activation check — activation doesn't cross frames, so a client gate would be fragile. Two below-floor Lows were hardened while in-area: `assertContainedAssetSrc` denylist → strict allowlist `^assets/[A-Za-z0-9._-]+$`; `listAssets` `stat`→`lstat` (skip symlinks); the AssetPicker stamps the requesting canvas and aborts on active-canvas drift mid-modal. Two residual below-floor items (the `/assets/<file>` serve route's symlink follow; the `escapeAttr` `&`-non-escape spoof nit) are documented follow-ups — they need a pre-existing local-filesystem-write attacker outside the DDR-054 threat model.

## Consequences

- **Positive:** editing is now familiar and predictable — curated box/framing/position knobs, direct-manipulation resize, select+edit on specimens, one-click media swap, delete/insert, a clean new artboard, and an always-visible local-vs-shared signal — all riding hardened lanes with DDR-105 no-flicker and DDR-050/reorder-seq undo. The security posture of the untrusted-canvas disk-write surface is now on par with the asset-upload lane.
- **Negative / follow-ups:** `resolveEditScope` is fetched with `rendered=1` for v1 (the `.map()` mapped refinement needs the client to report the DOM occurrence count). H3 (instance-local move/resize) lands with the resize-overlay work. The two residual security Lows remain documented, not code-closed. Live drag/select verification is deferred to the Stage-G scenarios (cross-origin selection is not agent-browser-drivable).
- **Supersedes:** DDR-104 §3's OUT-list (the promoted props are now curated). Extends DDR-138/139's move/reorder + occurrence model from clips/nodes to general delete/insert and edit-scope.
