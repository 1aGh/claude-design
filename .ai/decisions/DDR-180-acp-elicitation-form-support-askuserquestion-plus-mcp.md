# DDR-180 — ACP elicitation-form support: AskUserQuestion + generic MCP form input, fail-closed

**Status:** accepted · **Date:** 2026-07-15 · **Phase:** feature-acp-ask-user-question
**Relates:** DDR-179 (permission gate — the fail-closed posture + Promise/pending-map/timeout shape this replays), DDR-125 (multi-chat + security posture, native-only/loopback-only), DDR-123 (connection model + guardrails, unchanged), DDR-054 (untrusted-canvas / loopback trust model)

## Context

Claude Code's built-in `AskUserQuestion` tool — the interactive multi-choice picker the CLI itself uses to ask the user something mid-task — did nothing inside Maude's ACP chat panel. A user asking Claude to "use the ask user tool" got a plain-text question instead, and Claude's own reply said it had no such tool available.

This was not a client-side rendering gap. `claude-agent-acp` strips `AskUserQuestion` from the model's tool list entirely (`disallowedTools = elicitationSupport.form ? [] : ["AskUserQuestion"]`) whenever the connected client hasn't declared `elicitation.form` support during `initialize()`. Maude's bridge declared no `elicitation` capability at all, so the tool was never offered to the model in this session — not silently ignored, structurally absent.

The full request/response contract (`unstable_createElicitation`, `CreateElicitationRequest`/`CreateElicitationResponse`, the `ElicitationCapabilities` gate, and the exact `AskUserQuestion` → form-elicitation mapping) is already implemented and shipping in the exact SDK/adapter versions Maude pins (`@agentclientprotocol/sdk@0.28.1`, `@agentclientprotocol/claude-agent-acp@0.57.0`) — confirmed by reading the installed packages directly, not the public docs (which may describe a different unstable-surface snapshot). No version bump was needed.

## Decision

**Declare `elicitation: { form: {} }` in `clientCapabilities` at `conn.initialize()` — `form` only, never `url`.** A schema-driven form rendered entirely client-side is a materially smaller trust surface than `url`-mode elicitation, where the agent picks a URL and directs the user to open it. If a future need for url-mode elicitation shows up, it should be its own follow-up with its own security review, not folded into this one.

**`AcpBridge` implements `unstable_createElicitation` on the `client` literal, replaying DDR-179's Promise + pending-map + timeout shape exactly** (`acp/bridge.ts`):
- A new `pendingElicitations` Map, parallel to `pendingPermissions` rather than sharing it — the two response shapes (`RequestPermissionResponse`'s `{outcome:{outcome,optionId?}}` vs `CreateElicitationResponse`'s `{action,content?}`) don't unify cleanly under one generic "pending client answer" type without a discriminated wrapper that would make both call sites harder to read for no real gain. This was a deliberate, judgment-call choice (the plan's own Open Decisions flagged it as acceptable either way) — noted here rather than left implicit.
- Forwards the request via a new `onElicitationRequest(id, req)` callback (fresh `crypto.randomUUID()` nonce), resolves via `resolveElicitation(id, response)`.
- **Fails closed, but with an asymmetry from the permission gate that matters**: timeout, turn-cancel, and teardown (`cancel()`/`stop()`) all resolve `{action:'decline'}` — **never** `{action:'cancel'}` and never a fabricated `accept`. This is intentional, not an oversight: per `applyAskElicitationResponse`'s documented contract (read directly off the installed adapter source), `decline` tells the model the user skipped — the tool call completes and the turn continues — while `cancel` **aborts the tool call**. A bridge-initiated abandonment (the user walked away, the connection dropped) should degrade to "the user didn't answer," not silently kill whatever the agent was doing. A user's own explicit Cancel click IS forwarded as `'cancel'` — that distinction is preserved end to end, from `ElicitationPrompt.jsx`'s Cancel button through the `elicitation-response` frame to `resolveElicitation`.
- `resolveElicitation` is the last line of defense against a malformed response: only a literal `action:'accept'` carrying a real, non-array `object` `content` resolves as accept; a literal `action:'cancel'` resolves as cancel; **everything else — including an accept with missing/malformed content — collapses to decline.** The bridge never fabricates `content` to satisfy a well-formed-looking accept.

**Wire protocol** (`acp/index.ts`): a new `elicitation-request` server→browser frame (`{id, message, mode, requestedSchema}`) and `elicitation-response` browser→server frame (`{id, action, content?}`) → `bridge.resolveElicitation(id, {action, content})`. Both ride the existing main-origin, loopback-guarded `/_ws/acp` socket — no new route, so the DDR-054/123 canvas-origin exclusion holds by construction (the socket-level origin gate covers every frame type on it, elicitation included, without needing its own enumerated test case).

**Client** (`acp-runtime.js` + `ElicitationPrompt.jsx`): pending requests surface OUTSIDE the assistant-ui message stream via a panel-level `onElicitation(fn)` subscription, mirroring `onPermission` — a form request is "pause here for a human," not renderable turn content. `acp-elicitation.js`'s `parseElicitationSchema`/`buildElicitationContent` are pure and written **generically against the field-pairing pattern** (`<key>` + sibling `<key>_custom`), not hardcoded to the `question_N` prefix — confirmed against `askUserQuestionsToCreateRequest`'s actual wire output by reading the installed adapter source, so a non-AskUserQuestion form following the same convention renders correctly too. `ElicitationPrompt.jsx` renders single-select (radio), multi-select (checkbox), and plain-text questions, plus each question's own collapsed free-text override where the schema offers one; Submit is disabled only when a `schema.required` field is unanswered (AskUserQuestion never marks anything required — Skip always works — but a generic MCP form theoretically could).

## The accepted residual: this channel is not AskUserQuestion-exclusive

**The SAME `unstable_createElicitation` handler carries elicitation requests from ANY MCP server connected to the session, not just the built-in tool** — confirmed directly in `elicitation.d.ts`'s own header comment: "`onElicitation` — fired when an MCP server requests user input... maps directly onto ACP `session/create_elicitation`". There is no capability sub-flag to accept AskUserQuestion-shaped forms only; declaring `elicitation.form` opens the same UI to both sources uniformly. `AcpBridge.resolveElicitation` does not and cannot distinguish which source a given request came from — the doc comment on `onElicitationRequest` says so explicitly.

This is accepted as a residual, not gated behind a separate opt-in, for two reasons:
1. **Adapter-side, this isn't separable.** `claude-agent-acp` doesn't expose a "form, but only for the built-in tool" sub-flag. A Maude-side heuristic to detect and reject non-AskUserQuestion-shaped forms would be fragile — pattern-matching on field-naming conventions the adapter could change at any point — and would be a materially worse implementation than accepting the residual honestly.
2. **It's the same trust class as an existing tool-call permission prompt, not a new category of risk.** A compromised or malicious MCP server could theoretically use a deceptive form `message` to solicit sensitive input (e.g. "paste your API key") from the user. But the user is always the one typing the answer into a form rendered by Maude's own trusted UI — nothing auto-fills, nothing is read from disk or the environment and silently forwarded. The form card looks the same regardless of which source triggered it; a user who wouldn't type a secret into an unexpected form from an unfamiliar MCP server is protected the same way they'd be protected against a suspicious permission-prompt tool call.

This is worth naming explicitly so a future reader doesn't have to rediscover it from the adapter source.

## Consequences

**Positive:**
- `AskUserQuestion` now works end-to-end: the exact reported failure ("ask me something, use the ask user tool" producing a plain-text fallback) is fixed.
- The fail-closed defaults (timeout → decline, turn-cancel → decline, malformed response → decline, teardown → decline) mean there is no code path where an abandoned or malformed elicitation resolves to a fabricated `accept` — matching DDR-179's security property for the sibling permission gate.
- The decline-vs-cancel distinction is preserved precisely, matching the adapter's own documented semantics — a timed-out question doesn't unnecessarily abort whatever tool call triggered it.

**Negative / trade-offs:**
- This whole feature rides an **UNSTABLE** upstream protocol surface — the SDK's own type comments mark every elicitation type `@experimental`. A future SDK bump could change the wire shape (field names, response union) without any Maude-side signal beyond a broken form. Re-verify against the installed adapter source on any `@agentclientprotocol/*` version bump, the same discipline DDR-179 already established for the permission gate's mode semantics.
- The MCP-elicitation residual above: any connected MCP server can now render an arbitrary form to the user through the same channel as the built-in tool. Accepted, not silently — see above.
- `pendingElicitations` is a second, parallel Map to `pendingPermissions` rather than a shared generic structure — slightly more bridge-side bookkeeping in exchange for two independently-readable call sites (open decision #2 in the plan; recorded as a conscious choice, not a default).

## Addendum — security fan-out findings, fixed before commit

`security-auditor` + `ethical-hacker` ran in parallel over the implementation. Fail-closed correctness, no-dangling-Promise, origin/reachability, and WS input handling all came back clean. Three real, concrete findings did NOT — fixed, not waved through:

- **Hardcoded "Question from Claude" attribution** (`ElicitationPrompt.jsx`) — both reviewers independently flagged this as an *affirmative* misattribution, not neutral non-disclosure: the same card renders any connected MCP server's form (see the residual above), and branding every one of them as first-party Claude chrome is a materially better phishing primitive than what it looks like at a glance. **Fixed**: the card no longer claims a source it can't verify. `toolCallId` — present on `ElicitationSessionScope` and already populated in this feature's own mock test fixture — is now forwarded through the `elicitation-request` frame (it was being read off `req` and silently dropped two lines into `acp/index.ts`) and used to show "Requested by the tool call above" (verifiable against the transcript) vs. "Requested by a connected tool (not tied to a visible step)" when absent. This corrects a factual error in this DDR's own original "Revisit when" note, which claimed the source data "doesn't cleanly carry" — it does; it just wasn't wired up.
- **`mode:'url'` was never rejected, only never rendered** — `AcpBridge` declared `elicitation.form` only, but capability negotiation is advisory: nothing stopped a non-compliant adapter or a malicious/buggy MCP server from sending `mode:'url'` anyway, which would have produced a bare "message + Submit" card with the URL never shown anywhere — a confused-consent primitive (chained by `ethical-hacker` with the attribution finding into a "high" combined severity: a Claude-branded card confirming an out-of-band flow the user never saw). **Fixed**: `AcpBridge.unstable_createElicitation` now rejects (auto-declines, never surfaces to `onElicitationRequest`) any request whose `mode !== 'form'`, structurally, in the one place that already knows the declared capability set — not by trusting the other side to honor it. Covered by a dedicated test (`mock-acp-agent-elicit-url.mjs` + the bridge test asserting zero `onElicitationRequest` calls).
- **`__proto__`-keyed schema property silently dropped its answer** (`acp-elicitation.js`, low severity, not exploitable across the wire — `JSON.parse` never triggers the accessor) — **fixed anyway** as cheap defense-in-depth: `buildElicitationContent`'s `content` accumulator is now `Object.create(null)`.

Not fixed, accepted as-is: `security-auditor`'s two "low" findings on unsupported-mode handling were superseded by the `mode:'url'` structural rejection above (the "hollow accept" it described can no longer occur — there's nothing left to accept).

## Addendum — live dogfooding fixes (pre-commit)

The user tested the first implementation live in the native app and found four real bugs, fixed before commit:

- **Every keystroke in a free-text field lost focus.** Root cause: the keydown-listener `useEffect` in `ElicitationPrompt.jsx` had `answers` in its dependency array AND called `cardRef.current?.focus()` at the top of its body — so every character typed re-ran the effect, which re-stole focus from the input back to the outer card div. **Fixed**: split into two effects — a mount-only `[request.id]` effect that focuses the card once, and the keydown-listener effect (still depending on `answers`/`canSubmit` for fresh closures) with the `.focus()` call removed.
- **Submitting a custom answer appeared to do nothing.** Downstream of the focus bug (retyping each character made the interaction slow enough to plausibly hit the 120s pending-request timeout) compounded by a real, separate gap: when the bridge settled a pending elicitation on its OWN initiative (timeout, turn-cancel, teardown), nothing told the client — the card kept showing a Submit button that was already provably dead server-side, and clicking it was a silent no-op (`resolveElicitation`'s `if (!pending) return`). **Fixed**: a new `elicitation-resolved` frame (`onElicitationSettled` on the bridge, fired unconditionally at the end of `resolveElicitation` regardless of which path settled it) tells the client to drop a request from its pending list even when it didn't initiate the settlement itself.
- **Multiple questions stacked vertically instead of one-at-a-time.** Matches neither the CLI's own AskUserQuestion picker (one question at a time) nor a comfortable scan when a call asks 3-4 questions. **Fixed**: `ElicitationPrompt.jsx` now renders a Back/Next wizard when `questions.length > 1` (Submit only on the last step); a single-question call renders exactly as before (no stepper chrome).
- **Only the header chip showed, not the actual question text.** The AskUserQuestion → form mapping puts a required, ≤12-char `header` chip in the field's `title` and the FULL question text in `description` — but ONLY for multi-question calls (a single-question call's full text lives in the card's own top-level `message` instead, confirmed against the SDK's `AskUserQuestionInput` schema directly, `@anthropic-ai/claude-agent-sdk/sdk-tools.d.ts`). The original render picked `title || description`, so whenever a header existed (essentially always) the real question text was silently dropped — legends showed bare chips like "Barva"/"Projekty"/"Styl" with nothing underneath. **Fixed**: both render together (chip + full text), confirmed against the authoritative SDK type as the complete set of fields (`question`, `header`, `options[].{label,description,preview}`, `multiSelect`, plus the adapter's own auto-appended "Other" field) — there is no other AskUserQuestion question shape to support.
- Also added while addressing the doc-verification ask: per-option `preview` rendering (the SDK's documented "mockup/code-snippet/comparison" field, forwarded through `_meta` — was parsed nowhere before), and `title`/`aria-label` tooltips distinguishing Skip ("let Claude continue without an answer") from Cancel ("aborts the tool call") — visibly identical actions otherwise, per a direct user question ("isn't skip the same as cancel?").

## Addendum — a second, independent security fan-out found three more real findings

A second `security-auditor`/`ethical-hacker` pass ran over the full diff (both this feature and the sibling capability/permission-gate close-out it shipped alongside) before commit. The defender pass came back clean (0 blockers). The attacker pass, reasoning from the MCP spec's own elicitation guidance rather than just this codebase, found three findings the first pass's attribution/url-mode/proto-pollution fixes above didn't cover:

- **Unbounded elicitation queue + unbounded schema size — a connected MCP server can flood the panel, not just show one misleading form.** Nothing capped how many concurrent `pendingElicitations` a bridge would register, or how large/how many properties a `requestedSchema` could carry, before forwarding it to the client. A hostile/compromised MCP server firing requests without waiting for answers could grow server-side memory unboundedly and force the user into an endless Submit/Skip/Cancel loop just to get their composer back; an oversized `oneOf`/`enum` list on the one visible question had no rendering clamp either. **Fixed**: `unstable_createElicitation` now checks two caps BEFORE registering a pending entry or forwarding anything to the client — `MAX_PENDING_ELICITATIONS` (5 concurrent per bridge) and `elicitationSchemaWithinBounds` (`MAX_ELICITATION_SCHEMA_PROPERTIES` = 20 top-level properties, `MAX_ELICITATION_SCHEMA_BYTES` = 16 KiB serialized) — a request that trips either cap is declined immediately, same fail-closed outcome as a timeout. Covered by `test/acp-elicitation-bridge.test.ts`'s pure bound-check tests plus a dedicated flood fixture (`mock-acp-agent-elicit-flood.mjs`) firing 8 concurrent requests and asserting only the cap's worth ever reach `onElicitationRequest`.
- **The server-side `resolveElicitation`'s `content` builder didn't get the same `Object.create(null)` fix the client-side `buildElicitationContent` did.** The first pass's proto-pollution fix (addendum above) only touched the client-side helper the real UI happens to use — but `resolveElicitation` in `bridge.ts` is the ACTUAL last line of defense reachable by a hand-crafted `elicitation-response` WS frame (`acp/index.ts` only shallow-validates before forwarding), not just the trusted browser UI. No live escalation was demonstrated (a `__proto__`-keyed assignment on a plain object is a spec no-op for a non-object value, and every wire-legal `ElicitationContentValue` is non-object), but the asymmetry meant one function claimed a guarantee its sibling didn't actually share. **Fixed**: `resolveElicitation`'s `content` accumulator is now `Object.create(null)` too, for genuine parity rather than relying on the accessor's no-op side effect.
- **Declaring `form`-only (never `url`) makes the free-text box the ONLY channel any MCP server — benign or hostile — can ever use to ask for a real credential.** Sharpens the accepted residual above with a mechanism it didn't name: per the MCP spec's own guidance, url-mode elicitation exists specifically so a genuine secret request never has to pass through the LLM/client at all. By not supporting it (a deliberate, reviewed, still-correct choice — see the Decision section), Maude pushes every legitimate-or-hostile credential ask onto the one channel that does work, rendered with no visual distinction from "which color do you like?". **Fixed** with a cheap, adapter-independent mitigation that changes nothing about accept/decline routing: a new `looksLikeSecretRequest` pure helper (`acp-elicitation.js`) pattern-matches a question's own title/description (or the card's top-level `message`) against credential-shaped language (password/passphrase/secret/API key/access key/private key/auth token/credential/OAuth token); when it matches, `ElicitationPrompt.jsx` renders that field's input as `type="password"` and shows an inline warning ("Maude never needs your real ones here") — the same pause a real password field gives a user, instead of identical chrome to a benign question. A false positive just masks an unrelated field (harmless); a false negative leaves today's behavior unchanged. This is a mitigation, not a fix for the underlying residual — a determined attacker can still phrase a request to dodge the pattern match, and this doesn't change the Decision section's `form`-only choice, which remains correct on its own terms.

Note corrected in this addendum, not the original text above: this session's own testing confirmed the property-count-plus-byte-size check runs on the FULL schema object (not per-property), so a single property with an oversized `description` trips the byte cap even under the property-count limit — both caps are independent gates, not layered fallbacks.

## Revisit when

- The adapter/SDK version bumps in a way that changes `unstable_createElicitation`'s request/response shape, the `question_<n>`/`question_<n>_custom` field-pairing convention, or `applyAskElicitationResponse`'s decline-vs-cancel folding rule.
- A real need for `url`-mode elicitation surfaces — treat as a new feature with its own security review, not an extension of this one.
- Dogfooding surfaces the MCP-elicitation-as-phishing-vector residual as a further real problem in practice beyond the attribution fix above (e.g. a user reports confusion about *which* tool/server is asking even with the toolCallId-based label) — the next mitigation would likely be resolving `toolCallId` to the actual tool/server NAME client-side (the transcript already tracks tool-call titles; this feature only forwards the id, not a resolved label) rather than the generic "the tool call above" phrasing.
