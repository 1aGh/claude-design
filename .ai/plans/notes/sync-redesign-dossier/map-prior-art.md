# Prior art: folder mirroring between N peers with a server in the middle

Research basis: Syncthing BEP v1 spec, CouchDB Replication Protocol spec, Dropbox Nucleus engineering posts + API docs, git-annex design docs, Mutagen/Unison/rclone-bisync docs, automerge-repo/y-sweet docs, Firebase/Supabase storage-event docs, RFC 6578. All URLs inline. Mapped throughout onto Maude's shape: desktop Bun process ↔ CF Worker + container (checkout) + R2, one canonical hub, ~hundreds of files, files up to tens of MB, DDR-054/102/115 as hard constraints.

---

## 1. The recurring structural patterns (4)

### Pattern 1 — One append-only journal per authority, monotonic cursor per consumer, checkpointed resume

Every centralized system converges on this, and the decentralized one (Syncthing) converges on the per-device equivalent:

- **Dropbox**: the server keeps a journal of namespace mutations; clients hold an opaque **cursor** and call `list_folder/continue` to get "only what changed since then" ([detecting-changes guide](https://developers.dropbox.com/detecting-changes-guide), [/delta design post](https://dropbox.tech/developers/efficiently-enumerating-dropbox-with-delta)).
- **CouchDB**: the `_changes` feed with incremental sequence IDs is the entire replication driver; replicators persist their position as **checkpoints** in `_local/{replication-id}` docs (`source_last_seq`, `session_id`) and resume from the last common session ([replication protocol](https://docs.couchdb.org/en/stable/replication/protocol.html)).
- **Syncthing**: every FileInfo carries a device-local monotonic `sequence`; on reconnect, peers exchange `{index_id, max_sequence}` in Cluster Config and transmit only items with higher sequence ([BEP v1](https://docs.syncthing.net/specs/bep-v1.html)).
- Even **WebDAV had to retrofit exactly this** — RFC 6578 `sync-collection` adds a server-issued opaque `sync-token` because ETag-walking a tree doesn't scale ([RFC 6578](https://datatracker.ietf.org/doc/html/rfc6578)).

**Maps onto Maude:** the cell is already the single canonical server — it should own ONE ordered journal of designRoot mutations: `{seq, path, contentHash, size, tombstone?, source}`. Desktop keeps one cursor per hub (a few bytes in `_sync.json`); "catch up" is `GET /journal?since=<seq>`. This single primitive replaces: boot sweep, the 20 s poll, `requestFastPull`, and the file-plane manifest diff — they are all ad-hoc reconstructions of "what changed since my last look". It also directly yields the **doručenka** (§6 of the ground truth): the hub knows its head seq; each peer reports its cursor + per-file hash — "is X delivered everywhere" becomes a table lookup, like Syncthing's `FolderCompletion` per device. At ~hundreds of files, the journal is a trivial DO-SQLite table; compaction = collapse to latest-entry-per-path (which is exactly a manifest — the manifest is the compacted journal, so `GET /api/files` survives as the seq-0 case). Fail-closed cold start (DDR-102/223) is preserved structurally: "no cursor" is distinct from "nothing changed", so an empty diff can never be conflated with an empty project; a cursorless peer must run the Pattern-3 three-way, never a blind apply.

### Pattern 2 — Content-addressed blobs, separated from the namespace/metadata index; names are pointers

- **git/git-annex** is the purest form: git tracks "filenames and metadata"; annexed content lives under a content-addressed key (`SHA256E`), the working tree holds a pointer/symlink, the `git-annex` branch tracks **which repo has which content** (location tracking), and content moves independently via special remotes incl. S3 ([how it works](https://git-annex.branchable.com/how_it_works/)).
- **Dropbox**: files are block-lists of 4 MB SHA-256 blocks; the published `content_hash` is the hash of concatenated block hashes ([content-hash reference](https://www.dropbox.com/developers/reference/content-hash)); blocks are deduplicated and transferred independently of namespace ops.
- **Syncthing**: FileInfo = a list of `BlockInfo{offset, size, hash}`; a device "MAY reuse a block from a different file and offset having the same size and hash" ([BEP v1](https://docs.syncthing.net/specs/bep-v1.html)).
- **CouchDB** attachments are referenced by digest from revisions and streamed out-of-band via multipart, precisely because inlining blobs in the doc plane was unworkable ([protocol §attachments](https://docs.couchdb.org/en/stable/replication/protocol.html)).

**Maps onto Maude:** journal entries carry `path → hash`; the blob plane is keyed by hash only. R2 becomes a pure CAS + the checkout a materialization of the manifest — which dissolves ground-truth critique #4 (two stores with independent consistency): the bucket stops having serving/probe semantics at all (the §6 "bucket = durability snapshot" direction, but stronger: a CAS never has a "stale name" problem). `POST /_asset-probe` generalizes into exact hash-presence negotiation (CouchDB's `_revs_diff`: "tell me which of these you're missing"). Idempotent push/pull (invariant §7) becomes structural: PUT of an existing hash is a no-op; the fast-push echo-guard disappears because pulling your own upload is detectably identical. DDR-054 is *easier* under CAS, not harder: the path is untrusted data in a journal entry — the receiver validates the path against the DDR-115 classifier exactly as today, and independently re-hashes fetched bytes, so a compromised hub can neither invent paths that pass validation nor substitute content for a hash it doesn't have. At Maude's sizes, whole-file hashing suffices — chunking/rolling-delta (the [rsync algorithm](https://rsync.samba.org/tech_report/)) is an optimization the big systems layer on the same hash-compare skeleton for multi-GB files, not a prerequisite.

### Pattern 3 — Three-way decision against a persisted "last synced" ancestor; conflict = rename aside, never silent overwrite

- **Dropbox Nucleus** maintains exactly three trees — Remote, Local, and **Synced** ("the last known fully synced state... each node can be thought of as a merge base") — and the Synced Tree is what lets it "unambiguously derive the direction of a change": did the user edit locally, or did it change on the server? Sync is complete when all three trees converge ([testing sync at Dropbox](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine), [rewrite post](https://dropbox.tech/infrastructure/rewriting-the-heart-of-our-sync-engine)).
- **Mutagen** keeps "the most-recently agreed-upon content" as ancestor; its default `two-way-safe` mode auto-resolves **only conflicts that don't lose data** ([sync docs](https://mutagen.io/documentation/synchronization/)).
- **Unison** archives "the contents at the last moment when they were the same in the two replicas"; true conflicts are flagged for manual resolution, never auto-merged ([manual](https://github.com/bcpierce00/unison/blob/master/doc/unison-manual.tex)).
- **rclone bisync** stores prior listings and classifies each side's delta (new/newer/older/deleted); on both-changed it renames **both** copies (`.conflict1`/`.conflict2`) and propagates them ([bisync docs](https://rclone.org/bisync/)).
- **Syncthing** encodes the ancestor implicitly in version vectors; the conflict loser is renamed `<name>.sync-conflict-<date>-<time>-<modifiedBy>.<ext>` and — crucially — conflict copies "are treated as normal files... so they are propagated between devices" ([syncing docs](https://docs.syncthing.net/users/syncing.html)).
- **CouchDB** keeps *all* leaf revisions; a deterministic winner is picked for display but nothing is discarded ([protocol](https://docs.couchdb.org/en/stable/replication/protocol.html)).

**Maps onto Maude:** this is `decideColdStart`/`decideAnnotationsColdStart` generalized to every non-CRDT file and made total. Desktop persists per-file `{path, syncedHash, remoteSeq}` (the ancestor — Maude's Synced Tree; today's `syncMeta` stamps are a partial, per-lane approximation of it). Every decision — boot, reconnect, mid-flight — is then one pure function `(localHash, remoteHash, ancestorHash) → push | pull | conflict-aside | noop`, in ONE table both architectures call (kills critique #2, the double cold-start). The DDR-223 invariant "unstamped emptiness never beats content" falls out for free: overwriting a side requires `ancestor == that side's current hash`; a stale empty wrapper whose hash ≠ ancestor can never win — it goes aside as a conflict file instead. Conflict copies flowing back through the same journal (Syncthing's move) means both endpoints SEE the conflict instead of one silently losing.

### Pattern 4 — Notify-then-fetch: events carry no payload and are only hints; a scan/diff is the truth

- **Dropbox** `longpoll`: the client parks an HTTP long poll with its cursor; the response says only "something changed" — deliberately **no data in the notification** (it let them run an auth-free notification tier, and it means a lost/duplicate notification is harmless); the client then fetches real deltas via the cursor ([low-latency notification](https://dropbox.tech/developers/low-latency-notification-of-dropbox-file-changes)).
- **Syncthing**: `Index`/`IndexUpdate` announce metadata; bytes move only through hash-verified `Request`/`Response`. Its FS watcher merely *triggers rescans* (10 s accumulation), and hourly full scans stay on "as it is possible that some changes aren't picked up by it" ([syncing docs](https://docs.syncthing.net/users/syncing.html)).
- **CouchDB**: the continuous `_changes` feed IS the notification bus, and the same feed drives both replication and application UIs.
- Even "storage with events" products implement events on the **metadata index, never the blob store**: Firebase Storage events (`onObjectFinalized` etc.) fire server-side Cloud Functions only — no client realtime listener ([docs](https://firebase.google.com/docs/functions/gcp-storage-events)); Supabase realtime on storage means subscribing to the `storage.objects` *database table* ([discussion](https://github.com/orgs/supabase/discussions/2794)).

**Maps onto Maude:** the hub, after committing any write (every write door), appends to the journal and broadcasts `{seq}` — or literally just a poke — over the **already-existing** WS (sync socket / canvas-hmr socket). Peers respond by pulling the journal from their cursor. This one mechanism kills the 20 s poll, the fast-lane special-casing, and the debounce heuristics *at once* (the §6 "event-driven notifikace" direction — prior art says it's not just an option, it's the universal endgame), while a low-frequency journal-diff reconcile remains as the Syncthing-style safety net. Because the event is payload-free and the journal is the truth, a dropped WS frame costs latency, never correctness — the property today's lanes lack.

## 2. Embed/adopt options — honest evaluation

Short version: **there is no credible off-the-shelf engine for the file plane** that fits Bun-desktop + CF Worker/container + R2 + DDR-054 (receiver validates every path, no presigned URLs, hub untrusted to author arbitrary content). What IS adoptable is the *protocol shape* (Pattern 1+2+3 above ≈ the CouchDB/Dropbox skeleton), implemented over Maude's existing HTTP/WS surface. Per candidate:

| Candidate | Maturity | Fit | What we'd still own | Verdict |
|---|---|---|---|---|
| **automerge-repo** ([blog](https://automerge.org/blog/automerge-repo/), [docs](https://automerge.org/docs/reference/repositories/)) | Active, 2.x, parts still alpha-tagged | Doc-oriented sync (per-doc heads negotiation); Storage/Network adapters store *doc chunks*, not user files. **No folder-mirror or blob/asset story at all.** Adopting means migrating off Yjs/Hocuspocus wholesale | The entire file plane, plus a CRDT migration | **No** — solves the lane Maude already has working, not the one that hurts |
| **y-sweet / Yjs ecosystem** ([storage docs](https://docs.jamsocket.com/y-sweet/features/storage), [repo](https://github.com/jamsocket/y-sweet)) | Solid Rust server, S3-compatible Y.Doc persistence | Persists *documents* to blob storage; no file/asset mirroring. Would replace Hocuspocus infra, nothing else. Yjs ecosystem has no blob-sync story — the ecosystem posture is "assets out-of-band, reference by id/hash" | Everything file-plane | **No** as sync engine; Yjs stays exactly where it is (the genuinely collaborative payloads) |
| **CouchDB/PouchDB replication protocol** ([spec](https://docs.couchdb.org/en/stable/replication/protocol.html)) | The protocol is old, fully specified, battle-proven | As an *engine*: file↔doc mapping, attachment memory behavior with tens-of-MB media, and a Worker-side CouchDB emulation over DO/R2 all cut against it. As a *spec*: `_changes`+checkpoint+`_revs_diff`+`new_edits:false` is exactly Patterns 1–3 and is small to implement natively | If embedded: the FS bridge + Worker server side (i.e., most of it) | **Adopt the protocol shape, not the engine.** The spec doubles as free design review for the journal/cursor/diff endpoints |
| **isomorphic-git as transport** ([site](https://isomorphic-git.org/)) | Mature JS git | Git gives CAS + atomic ref update (whole-tree snapshot pointer — a beautiful property), but: commit-granularity (not live), pack negotiation heavy per small change, needs a git server over R2 or a third-party remote (then the hub isn't canonical), binary conflicts manual, drags history | Live lane, conflict policy, UI heal | **No as primary transport; keep git as lane-of-record/backup** (autocommit + rehydrate already play this role well) |
| **rclone/bisync-style engines** ([bisync](https://rclone.org/bisync/)) | Mature but explicitly batch: lockfile, `.lst-err` lockout, `--resync` recovery, no watching | Go sidecar in .app + container is plausible (DDR-177-style), but desktop→R2 direct S3 access violates DDR-054 (credentials/presigned to the client); no event integration; failure model is "stop and resync" | Everything realtime + trust plumbing | **No** — but its prior-listings/conflict1-conflict2 model independently confirms Pattern 3 |
| **Syncthing (embed)** | Very mature Go daemon | Symmetric device mesh, no server authority; embedding a daemon contradicts the hub-mediated trust model and the self-contained .app posture | The hub role entirely | **No — but it is the single richest mechanism source** (index+sequence, tombstones, conflict naming, watcher-as-hint, event bus) |
| **WebDAV+RFC 6578 / remoteStorage** ([RFC 6578](https://datatracker.ietf.org/doc/html/rfc6578), [draft-dejong-remotestorage](https://datatracker.ietf.org/doc/draft-dejong-remotestorage/)) | Standards; sparse maintained TS server implementations for Workers | Gives namespace + sync-token, but no content addressing, no dedup, no conflict story beyond conditional PUT; we'd implement both ends anyway | Nearly everything | **No** — value is confirmation that even a 1999 protocol had to grow a cursor |
| **"S3-manifest protocol" (roll-your-own consolidation)** | n/a | Journal endpoint + CAS blob routes + WS poke over the existing hub. Maude already owns 80 % of the parts (`/_asset-probe` ≈ revs_diff, `GET /api/files` ≈ compacted journal, content-addressed asset names, sync WS) — they're just distributed across seven lanes | Journal storage (DO), decision table, path validation, heal bus — all things DDR-054 says we *must* own anyway | **Yes — this is the credible option.** Not "build more", but "collapse seven lanes into the three primitives prior art converged on" |

The decisive argument: DDR-054 requires the receiver to re-validate every path and forbids handing clients direct bucket access — which disqualifies every engine that wants to own the transport end-to-end, and leaves exactly the layer prior art says to standardize (journal + CAS + three-way table) as the layer Maude must implement itself. That layer is small: CouchDB's whole replication algorithm is a dozen HTTP interactions.

## 3. What mature systems deliberately DON'T do

1. **No master-master merge of ordinary file bytes.** Syncthing renames aside; bisync keeps both `.conflict*` copies; Unison flags and waits; Mutagen's default refuses lossy auto-resolution; CouchDB keeps all conflicting leaves. Merging is reserved for purpose-built data types (CRDTs, git's text merge — and even git stops at binary). → Maude's split is correct: Y.Doc lanes merge the collaborative payloads; the file plane must never try to be clever — hash-conflict ⇒ rename-aside, propagate the copy.
2. **No trusting filesystem watchers or timestamps for correctness.** Syncthing keeps hourly scans even with the watcher on; Mutagen rescans every cycle; bisync admits mtime+size misses content changes and offers checksums; Nucleus's entire design is "persist observations, converge three trees" instead of trusting an event stream; Node itself documents `fs.watch` as "not 100% consistent across platforms" ([caveats](https://nodejs.org/api/fs.html#caveats)) and inotify drops events on queue overflow and has no true recursive watch ([inotify(7)](https://man7.org/linux/man-pages/man7/inotify.7.html)). → The container watcher gap is a known *class*; nobody fixes it with a better watcher.
3. **No big blobs inside the history/CRDT store.** git → git-annex exists precisely for this; Dropbox splits journal from block CAS; CouchDB special-cases attachments into multipart streams; automerge-repo simply has no asset story; y-sweet persists docs, your assets are your problem. → Don't be tempted to stuff media into Y.Docs to "reuse the live lane" — reuse the live lane's *socket* for pokes instead (Pattern 4).
4. **Scoped-down metadata fidelity.** Syncthing syncs ownership/xattrs only as opt-in advanced options ([ownership](https://docs.syncthing.net/advanced/folder-sync-ownership.html), [xattrs](https://docs.syncthing.net/advanced/folder-sync-xattrs.html)); Dropbox's rewrite explicitly abandoned legacy "few consistency guarantees" behaviors in favor of a strict, testable model. → DDR-115's versioned-vs-runtime taxonomy is the same move; the redesign should make the classifier THE single membership oracle (one copy, not four).
5. **Exactly one serving truth per node; every other copy is a cache or an explicitly tracked replica.** Nobody runs two half-authoritative stores on one node. git-annex is the exception proving the rule: when content plurality is wanted, it is *explicit* — location tracking + `numcopies` in the git-annex branch — never implicit mirror hooks. → checkout = serving truth (DDR-224 already landed there), bucket = write-behind CAS/durability, full stop.
6. **No deleting on ambiguity, no in-place partial writes.** Tombstones carry versions (Syncthing `deleted` + version vector) so an old delete can't beat a new edit; downloads assemble in temp files and rename atomically (`.syncthing.<name>.tmp` → rename); bisync would rather hard-stop and demand `--resync` than guess. → Matches invariants §7; keep tombstones versioned in the journal, keep atomic materialization.
7. **No payload in notifications** (Dropbox longpoll carries nothing; Syncthing indexes carry metadata only) — so notification infrastructure never becomes a second data path with its own consistency bugs. → Maude's fast-lane is today a second data path; under Pattern 4 it degenerates into a poke.

## 4. The "last hop": how consumers/UI learn a file changed

The uniform answer: **the sync engine owns an event bus; the filesystem is never the bus between processes that already know about the write.**

- **Syncthing** exposes `GET /rest/events` — a long-poll bus with strictly increasing event IDs (`LocalIndexUpdated`, `ItemStarted`, `ItemFinished`, `FolderCompletion`…) — as *the* supported way for GUIs/integrations to learn about sync activity; nobody watches the folder to know Syncthing finished ([event API](https://docs.syncthing.net/dev/events.html)). Internally the FS watcher exists only to notice *third-party* writes, batched 10 s, backed by hourly scans ([syncing docs](https://docs.syncthing.net/users/syncing.html)).
- **Dropbox** delivers server-side change awareness by longpoll-on-cursor + fetch ([low-latency post](https://dropbox.tech/developers/low-latency-notification-of-dropbox-file-changes)); local kernel events (FSEvents/etc.) are input for detecting *user* edits, not the app-integration surface.
- **CouchDB/PouchDB** collapse the two entirely: the same `_changes` feed drives replication *and* live UIs — one journal, machine and human consumers alike.
- **Firebase/Supabase** emit change events from the metadata layer (object-finalize triggers; the `storage.objects` table via logical replication) — never from watching storage bytes ([Firebase](https://firebase.google.com/docs/functions/gcp-storage-events), [Supabase](https://github.com/orgs/supabase/discussions/2794)).
- Why they all avoid the FS as a bus: `fs.watch`/inotify are advisory — platform-inconsistent, non-recursive on Linux, lossy on overflow, and atomic tmp+rename emits events on the temp name plus a rename that naive watchers miss ([Node caveats](https://nodejs.org/api/fs.html#caveats), [inotify(7)](https://man7.org/linux/man-pages/man7/inotify.7.html)). Everyone also solves **self-echo** at this layer: the writer records what it wrote (Syncthing updates its own index directly on writes it performs), so its own events are distinguishable from foreign ones.

**Maps onto Maude's container gap (ground truth §3 prime suspect):** the hub PUT already *knows* it wrote a file — hoping the studio child's recursive `fs.watch` spots the rename is exactly the anti-pattern. The fix prior art prescribes is the one Maude already half-has: `announceWrite` generalized from doc-projection writes to **every write door**, feeding one internal bus that fans out to (a) the journal/WS poke for peers and (b) the `canvas-hmr` `asset` heal for browser tabs. Same on desktop: the puller announces its own materializations instead of relying on the macOS watcher (which currently works by luck of FSEvents' semantics). FS watching then retains exactly one job on each node — detecting writes by processes *outside* the sync system (user's editor, agent tools) — and, per Syncthing/Mutagen, stays backed by a periodic cheap reconcile because watchers are hints. "Viditelnost ≠ doručení" (critique #5) dissolves when UI-heal and peer-notify are two subscribers of the same bus that the delivery receipt (Pattern 1) also reads: on-hub ✓ = journal append, at-peers ✓ = cursor advance + hash ack, UI-healed ✓ = heal-subscriber ack — three subscribers, one event, one truth.
