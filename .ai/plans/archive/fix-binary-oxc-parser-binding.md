# Feature: fix-binary-oxc-parser-binding

Keep oxc-parser. Work around a Bun 1.3.4+ regression in `--compile` NAPI native-binding embedding by setting `NAPI_RS_NATIVE_LIBRARY_PATH` from a Bun-embedded asset path before oxc-parser loads. Per-target entry stub generated by `build.ts` — zero changes to canvas-pipeline / canvas-edit / canvas-lib-inline / handoff.

## Description

Every `@1agh/maude-<slug>` binary published since v0.17.0 crashes on startup with `Cannot find native binding ... oxc-parser/src-js/bindings.js:575`. Initial assumption (parser swap to `@babel/parser`) was a sledgehammer. Spike (logged below) found the real cause: **Bun 1.3.4 introduced a regression in `bun build --compile` NAPI native binding embedding**. Bun 1.3.3 produces a working binary with the same source; 1.3.4 through 1.3.14 (current) do not. The current CI uses `oven-sh/setup-bun@v2` unpinned → it picked up 1.3.14 → broken binary.

The workaround is contained, verified end-to-end on Bun 1.3.14, and preserves the speed + ecosystem alignment that motivated the oxc-parser choice in the first place (DDR-009 spirit).

## Problem

`bun build --compile --target=bun-darwin-arm64 server.ts` on Bun 1.3.4+ produces a binary in which `oxc-parser/src-js/bindings.js` walks its platform candidates via `require()` and finds none — both `require('./parser.darwin-arm64.node')` (local) and `require('@oxc-parser/binding-darwin-arm64')` (sibling package) fail at runtime. The NAPI-RS auto-generated loader throws.

Bun's bundler under the regression appears not to embed the matching `.node` file even when the platform binding package is statically importable. This affects every NAPI module shipped via the standard NAPI-RS optionalDependencies pattern.

## Spike summary (see § Spike log at end)

| Strategy | Bun 1.3.3 | Bun 1.3.14 |
|----------|:---------:|:----------:|
| 1. Baseline — bare `import { parseSync } from 'oxc-parser'` | ✅ | ❌ |
| 2. Static-import of platform binding package alongside `oxc-parser` | ✅ | ❌ |
| 3. **`NAPI_RS_NATIVE_LIBRARY_PATH` + asset import via `with { type: 'file' }`** | n/a | ✅ |

Strategy 3 is the verified fix. Implementation is mechanical: 7 small generated entry files (one per build target), no edits to the canvas pipeline.

## Solution

### Loader-bypass mechanism

oxc-parser's bindings.js (`node_modules/.pnpm/oxc-parser@0.131.0/node_modules/oxc-parser/src-js/bindings.js`, lines 69-77) honors `NAPI_RS_NATIVE_LIBRARY_PATH` BEFORE its platform-detection switch:

```js
function requireNative() {
  if (process.env.NAPI_RS_NATIVE_LIBRARY_PATH) {
    try { return require(process.env.NAPI_RS_NATIVE_LIBRARY_PATH); } catch (err) { loadErrors.push(err) }
  } else if (process.platform === 'android') { /* ... */ }
  // ...
}
```

Bun's `import binding from "X.node" with { type: 'file' }` syntax (Bun 1.0+, stable) embeds the file as an asset in `--compile` output; at runtime, the import resolves to a virtual path like `/$bunfs/root/parser.darwin-arm64-XXXX.node`. Combining the two: set the env var from the embedded asset path before any oxc-parser module evaluation.

### Per-target entry generation

Each `bun build --compile --target=<X>` needs a different embedded binding. `with { type: 'file' }` requires a literal string path — can't be dynamic. Solution: `build.ts` generates a tiny entry file per target at compile time, then passes it as the bundle entry instead of `server.ts`:

```ts
// dist/.compile-entries/server-<slug>.ts   (gitignored; regenerated each build)
import bindingPath from '@oxc-parser/binding-<slug>/parser.<slug>.node' with { type: 'file' };
process.env.NAPI_RS_NATIVE_LIBRARY_PATH = bindingPath;
// Re-export everything from the real server entry; module-evaluation order is
// preserved by ESM, so the env var is set before any downstream module touches
// oxc-parser.
import '../../server.ts';
```

7 of these files cover all release targets. They live in `plugins/design/dev-server/dist/.compile-entries/` (a sibling of the existing `dist/maude-<slug>` outputs) — gitignored, regenerated each build, never read by humans.

### Dev mode (no compile)

Under plain `bun run server.ts` (dev mode), oxc-parser auto-loads correctly — the regression is `--compile`-only. Dev path is unchanged; the per-target entries exist solely for the compile pipeline.

### Upstream Bun bug report

Filing this with `oven-sh/bun` is part of T7 because (a) the workaround imposes per-target build complexity, and (b) future Bun versions may fix the regression and let us drop the workaround cleanly. Bisect already done (1.3.3 last-good, 1.3.4 first-bad) — that's the report's core asset.

### Step 5 — workaround discovery

Read oxc-parser's `bindings.js` top section: confirmed `NAPI_RS_NATIVE_LIBRARY_PATH` env var is honored BEFORE the broken platform-detection switch.

Bun's `import x from "Y.node" with { type: 'file' }` (stable since 1.0) embeds a file as an asset in `--compile` output; at runtime the import resolves to `/$bunfs/root/<filename>-<hash>.node`.

Combined into `spike-asset.ts`:
```ts
import bindingPath from '@oxc-parser/binding-darwin-arm64/parser.darwin-arm64.node' with { type: 'file' };
process.env.NAPI_RS_NATIVE_LIBRARY_PATH = bindingPath;
console.log('binding path at runtime:', bindingPath);
const { parseSync } = await import('oxc-parser');
const code = `function App() { return <div/>; }`;
const r = parseSync('test.tsx', code, { sourceType: 'module' });
console.log('OK parsed:', { errors: r.errors.length, hasProgram: !!r.program });
```

Built with Bun 1.3.14: **works**. Runtime output:
```
binding path at runtime: /$bunfs/root/parser.darwin-arm64-8tq3jdqq.node
OK parsed: { errors: 0, hasProgram: true }
```

### Step 6 — verify static-import variant (production pattern)

`spike-realistic.ts` separates the init into its own module so downstream code can use static `import { parseSync } from 'oxc-parser'`:

```ts
// init-oxc.ts
import bindingPath from '@oxc-parser/binding-darwin-arm64/parser.darwin-arm64.node' with { type: 'file' };
process.env.NAPI_RS_NATIVE_LIBRARY_PATH = bindingPath;

// spike-realistic.ts
import './init-oxc.ts';
import { parseSync } from 'oxc-parser';
import MagicString from 'magic-string';
// ... parse + magic-string usage
```

Built with Bun 1.3.14: **works**. `{ errors: 0, hasProgram: true, magicStringWorks: true }`.

ESM module evaluation order guarantees `init-oxc.ts` runs first (it has no dependencies; downstream modules import it as their first line). `oxc-parser`'s bindings.js then evaluates with `NAPI_RS_NATIVE_LIBRARY_PATH` already set.

### Conclusion

Production fix is mechanical: generate one tiny entry stub per `--target`, point Bun at the stub as compile entry. No source-file edits to the canvas pipeline. No parser swap. Build-time-only change.

## Retro

- **What worked:** the spike was the right detour — saved 1-2 days that would have gone to a babel migration that was the wrong fix. Spending 30 min on a 3-line repro + bisect produced a definitive answer (Bun 1.3.3 vs 1.3.4) that no amount of source-reading would have.
- **What I missed first time:** the first generator pass put env-var assignment in entry top-level code, not realizing ESM hoists imports past it. Spike-realistic.ts had the right pattern (separate init module) but I didn't carry it into the generator. Caught in T3 first-build smoke (binary still crashed) — fixed by splitting init + entry into two files. `test/compile-entry.test.ts` now asserts `initIdx < serverIdx` so this regression class is gated.
- **Process to keep:** "investigate before refactor" — when a parser/binding/native-module bug shows up, check tooling regression bisect FIRST. The babel plan would have shipped 120 lines of pipeline edits for a Bun-side bug.
- **Adjust for next time:** when a plan recommends "swap a dependency" before a spike, default to spiking. The earlier plan-rewrite cycle was a direct result of the user pushing back on the parser swap — instinct was right, would have saved a plan if I had spiked unprompted.
