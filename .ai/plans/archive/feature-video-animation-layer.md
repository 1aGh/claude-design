# Feature: Video & animation layer — Remotion-authored video comps (in-house bundled) + capture-first GIF/MP4 export

Validate docs and codebase patterns before implementing. Pay attention to existing naming, utils, and imports.

## Description

Extend the design plugin from static mocks to **marketing videos and animations**: a new **video-comp canvas kind is a genuine Remotion composition** (authored by the AI using Remotion's official LLM corpus — system prompt, llms.txt, ~427-snippet skills package, `@remotion/transitions`), previewed/scrubbed via the embedded `@remotion/player`; users **drop video/audio clips onto the canvas** and direct edits through the existing ACP chat ("udělej z toho animaci, přidej titulky", "spoj tyhle 4 videa + transition + hudba" — which is literally `<TransitionSeries>` + `<Audio>`); a **simple timeline panel** (sequences/scrub/retime — NOT an NLE) rides next to the existing inspector; artboards with motion export to **GIF/MP4** through the existing export engine.

**Architecture decision (research + 3:0 debate + user ratification, 2026-07-02): HYBRID — Remotion for authoring + preview, Maude's own capture spine for export.**

- **Remotion ships in-house** (`remotion`, `@remotion/player`, `@remotion/transitions` — pure JS → `RUNTIME_PACKAGES` pre-bundling; users never npm-install anything). Remotion's **Free License covers individuals and companies ≤3 people, unlimited commercial use** — most of Maude's audience pays nothing. For-profit orgs of 4+ people need their own Remotion Company License; per the T&C reading (license-text research 2026-07-02) the likely tier for "making videos for themselves in a local tool" is **Creators ($25/seat, no minimum)** — the Automators "embedding the Player" trigger is narrowed in the T&C to *"embedding … on a website to dynamically display compositions"*, which a local design preview is not. The obligation attaches to the **user** ("the party that owns or controls the Remotion codebase" — the comps live in their project), not to Maude; T&C explicitly permits the AI shape: *"acceptable for services to generate Remotion code through artificial intelligence"* + *"allowing end-users to edit Remotion code is permitted if the code was initially generated by the service"*. Handled by **disclosure** (first-use notice + docs + the Remotion LICENSE file shipped alongside the bundle). Remotion is source-available, NOT MIT — never call it MIT. Structural precedent: Remotion's own **Editor Starter FAQ** uses exactly this model (each deploying org licenses per its own headcount, no pass-through).
- **What we deliberately do NOT ship:** `@remotion/renderer` (Chrome-Headless-Shell download + per-platform compositor binaries), `@remotion/web-renderer` (mandatory licenseKey param + always-on telemetry). Instead, **export renders the comp through Maude's own capture spine**: a Remotion comp is deterministic *by construction* (`useCurrentFrame()`), so Playwright steps the Player frame-by-frame and **mediabunny** (MPL-2.0) + **gifenc** (MIT) encode MP4/GIF in-page — zero native binaries, zero telemetry, zero licenseKey infrastructure.
- The same capture spine also exports **ordinary animated artboards** (CSS/WAAPI/motion mocks — which Remotion's renderer could never touch), seeked via `document.getAnimations()`.
- The earlier debate default ("no Remotion at all") was **superseded by user ratification**: the debate over-weighted the 4+ org burden (it's the user's relationship with Remotion, disclosure-manageable) and the "own Remotion code" clause (aimed at hosted SaaS laundering renders through one license, not a local tool where each user renders under their own status). What the debate got right is preserved: no renderer binaries, no telemetry, capture spine owns export.

## User Story

As a **designer/founder using Maude** I want **to drop clips into a canvas, direct animation edits via chat (with Claude using Remotion's mature, well-known API), tweak timing on a simple timeline, and export the artboard as MP4/GIF** so that **I can produce marketing videos and animations in the same canvas-first loop I already use for static mocks — without installing or configuring anything extra**.

## Problem

- Canvases already animate (motion/CSS/WAAPI are bundled) but there is **no video authoring vocabulary** (clips, sequences, transitions, music) and **no deterministic export clock**.
- The asset write surface (`POST /_api/asset`, DDR-088) accepts **images only** — video/audio can't land on the canvas.
- The export engine (DDR-041) has **no temporal formats** — PNG/PDF/SVG/HTML/PPTX only.
- There is no UI to see/scrub an animation's structure; the only lever is re-prompting the AI blind.
- A bespoke animation format would have **zero training-data corpus** — Claude already knows Remotion deeply; teaching it a home-grown timeline IR wastes that.

## Solution

Six moves:

1. **Remotion in-house** — add `remotion`, `@remotion/player`, `@remotion/transitions` to `RUNTIME_PACKAGES` (pre-built `dist/runtime/*.js`, `.min-sizes.json` floors, Remotion LICENSE passthrough). License disclosure: one-time notice in the shell + docs ("free for individuals & ≤3-person companies; 4+ orgs need their own Remotion license").
2. **Video-comp canvas kind** — a canvas artboard whose content is a Remotion composition component (`useCurrentFrame`/`interpolate`/`<Series>`/`<TransitionSeries>`/`<Video>`/`<Audio>`) + comp meta (fps/duration/size). Preview mounts it in `<Player>` (free scrub/controls). A thin canvas-lib wrapper exposes `window.__maude_seek__(frame)` → Player `frame` prop for capture/scrub. Deterministic by construction.
3. **Video/audio asset intake** — widen the DDR-088 asset route (magic-byte sniff for mp4/webm/mov/mp3/wav/m4a, deliberate cap raises, streaming write); drop/paste inserts Remotion `<Video src="assets/…">`/`<Audio>` into comps, plain `<video>` into ordinary artboards.
4. **GIF/MP4 exporters** — new `exporters/video.ts` + `bin/_video-playwright.mjs`: Playwright Chromium (already the export engine) steps frames (`__maude_seek__` for comps; `document.getAnimations()` currentTime for ordinary artboards; per-frame `<video>.currentTime` + `seeked` await) → screenshot per frame → frames piped into the page → **mediabunny** encodes MP4 (H.264/AAC, wasm-AAC or Opus/WebM fallback), **gifenc** encodes GIF. Audio mixed once via `OfflineAudioContext` from the comp's `<Audio>`/`<Video>` sources. Desktop-agnostic: capture never touches WKWebView.
5. **Timeline panel** — a minimal maude-styled shell panel: play/pause/loop + playhead + scrub (drives Player via postMessage seek) + **sequence rows** (parsed from the comp TSX per skill conventions — `<Sequence from durationInFrames>` blocks; WAAPI introspection rows for ordinary artboards via `animation.effect.getKeyframes()`); dragging a sequence block retimes `from`/`durationInFrames` through the existing canvas-edit source-patch machinery (same pattern as CssKnobs). Per-keyframe `interpolate()` dot-editing is **deferred** to a follow-up.
6. **Agent skills** — a `video-comp` authoring skill that leans on **Remotion's official LLM guidance** (system prompt rules: frame-driven values only, no CSS animations in comps) + Maude conventions (assets from `assets/`, no network fetch, parseable `<Sequence>` structure); routing cues in `/design:new`/`/design:edit`; motion-critic extension with a **live 2-sample motion proof** (freeze-frames lie — DDR-094 lesson).

## The determinism contract (load-bearing constraint)

All three debate seats named the same top risk: **capture is only frame-perfect if every animated value is a pure function of the frame index.**

- **Video comps get this for free** — Remotion's own iron law (`useCurrentFrame()`; CSS animations/transitions are forbidden inside comps per Remotion's official LLM guidance). The skill enforces it; the Player `frame` prop is the seek.
- **Ordinary artboards** keep the softer contract: animations must be WAAPI/CSS (seekable via `document.getAnimations()`); no rogue `requestAnimationFrame`/`Date.now()` in animated values; `<video>` elements seeked per frame, never free-running during capture.
- Preview and capture share ONE seek implementation (`__maude_seek__`), driven by rAF in preview and externally in capture.
