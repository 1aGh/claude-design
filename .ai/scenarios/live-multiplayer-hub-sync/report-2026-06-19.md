## Findings (real — surfaced by the scenario)

### F1 — Cold-start simultaneous-seed **duplicates** the TSX body (correctness) ⚠️
When **both** servers seed the same canvas's `Y.Text` from their own (identical) disk copy **simultaneously** — before either adopts the hub's doc — the Yjs CRDT treats them as two distinct insertions and **duplicates the whole file** (two `export default` → canvas build 500 → blank render). **Sequential** connection (server A establishes the hub doc, B joins and adopts) is **clean** (verified: export count = 1 on both). The realistic flow (B clones from A, joins after A) avoids it, but a genuine simultaneous cold-start on the same canvas is a real race.
**Recommend:** harden cold-start seed reconciliation so the second seeder **adopts** the hub doc (or the shared-doc DDR-064 convergence path) instead of merging its own seed. Track as a follow-up bug.

### F2 — Editing-presence needs a **browser open on the editing side** (design gap) ⚠️
In `shared-doc:off` mode (the proven two-doc path, active here), the Task-2 `setAgentEditing` projects onto the **registry room**, which only exists once a browser has that canvas open (to create + hub-bridge it). So an agent edit on a canvas **nobody is viewing locally** does not propagate its "is editing" badge (the **TSX changes still sync** via the sync runtime regardless). Realistic — collaborators usually view what they edit — but a gap.
**Recommend:** also project agent editing onto the sync-runtime's hub awareness (not only the registry room) so it crosses without a local browser. Track as a follow-up.

### F4 — The observer's update is a **full iframe reload** → presence blinks, not seamless (UX) ⚠️ **load-bearing**
The user's explicit bar: *"vše musí fungovat seamless … jestli to nijak neproblikává."* It does **not** fully meet that bar. When a teammate's synced TSX change lands on the observer's disk, the canvas iframe does a **full `location.reload()`** (`client/hmr.mjs:62`, HMR `mode: "module"` — the code comment literally says *"State is lost"*). Verified visually (`evidence/05→06→07`):
- ✅ The change **does render** for the second user ("LIVE UPDATE ✦" → "FLICKER PROBE 2"), and an **"editing — SyncTest.tsx"** activity badge shows on the artboard during the change.
- ⚠️ But the reload **blinks the collaborator presence**: the peer avatars/cursors **disappear during the reload and reappear after** (captured: 5 avatars present → **gone** mid-reload → back). Any in-canvas state (scroll, selection, transient UI) resets too.
- ⚠️ **Not optimistic / not a hot-swap.** The observer waits the round-trip (~1–4 s) then a full reload — not a smooth in-place content swap.
- On this *simple* canvas the content itself didn't show a white flash (the browser held the prior paint), but the reload is real (presence reset proves it); a **heavier canvas would visibly flash** on every synced keystroke-batch.

**Recommend (to hit "seamless"):** move cross-peer TSX-sync rendering off `location.reload()` to a **module hot-swap** (re-import + remount the canvas subtree, preserving the collab provider + presence layer) so cursors/avatars don't blink and heavier canvases don't flash. This is the single biggest gap against the "seamless" bar. _High priority._

### F3 — Phantom peers on rapid reconnect (cosmetic)
3× "TE" avatars appeared from my repeated connect/disconnect cycles — stale awareness states not GC'd promptly (the known awareness-timeout window). Cosmetic; clears on timeout.

## Native (computer-use) — dogfood ceiling

The existing `Maude.app` builds (`/Applications` + `target/release`, both **Jun 17**) **predate phase-30** (grep: no `dc-edit-ring`/`setAgentEditing` in the bundle). Per **DDR-106** the native app bundles + serves the **identical `apps/studio` source**, so the phase-30 multiplayer code verified comprehensively on web **is exactly what native runs** — only the Tauri shell (window/sidecar/keychain, untouched by phase-30) differs. A full native pass = a fresh `Maude.app` release build + hub-link, driven via computer-use + system `screencapture` (the WKWebView workaround). That's the documented native-app verification ceiling.

## Recommended follow-ups

1. **F1 (bug):** cold-start simultaneous-seed duplication — harden seed reconciliation. _High priority — multiplayer correctness._
2. **F2 (gap):** editing-presence requires a local browser on the editing side — project onto sync-runtime awareness.
3. Save idempotent per-platform **runners** so this becomes a repeatable scenario (boot hub + 2 servers + drive the two-tab flow).
4. **Native pass:** rebuild `Maude.app` with phase-30 + hub-link + computer-use drive (dogfood ceiling) — offer to the user.
